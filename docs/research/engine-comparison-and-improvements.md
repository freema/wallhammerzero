# Give the engine eyes before the city

The Wallhammer Zero design holds up at its core. Layers as CMake targets, generational handles instead of a generic ECS, generator determinism from M0 and the generator as an ordinary source of cells match how Godot, Wicked Engine, Unreal PCG and Horizon work. But the comparison with real engines, postmortems and AI workflows reveals three structural gaps. **First, the tools for observing and controlling the engine arrive late.** The debug server, state digests, MCP and the studio are planned "from M3/M5", even though the code is written by an AI that cannot see the screen, and the owner, as art director, has no tool other than the studio. **Second, the architecture lacks layers that every general engine has:** a server-shaped simulation (player commands instead of raw input), a type registry with versioned serialization, an explicit data handoff protocol for the renderer and a second implementation of the port for the world shape. **Third, there are two different roadmaps (M0–M7 and M0–M8)** and both postpone the riskiest verification (style, scale, cars, draw cost on Metal) until after the infrastructure. The report therefore proposes one plan, M0–M9. Log, CVars, crash handler, headless run and a tool registry with both CLI and MCP transports are in M0. The draw cost through SDL_GPU on Metal is measured in M1. The scale table is frozen in M2 on a "metrics zoo" scene with owner approval. The engine test scenes (city block, planet seed) come in M4 and M5, before streaming hardens around a flat grid. Every milestone is a machine-checkable file `milestones/Mx.json`. The technology stays (C17, SDL3, SDL_GPU), but the RHI is shaped from M1 so that a native Metal 3 backend can be added, and the renderer plans for cluster culling and index compaction. All of this applies to the period after the analysis ended (D11). None of it is a prototype.

## Custom engines took three to ten years and won with tools and verifiable steps

No comparable custom engine was built quickly. **Factorio went from the start of development in 2012 to version 1.0 in August 2020** ([Kotaku](https://kotaku.com/factorio-reaches-1-0-after-eight-years-of-development-1844744187)). **Flax wrote its first code in 2012 and released 1.0 in December 2020** ([Flax](https://flaxengine.com/blog/flax-1-0-released/)). Gustafsson spent roughly three years on voxel experiments and another year looking for a game before Teardown came about, and he wrote the engine and pipeline "from scratch in C++ for this game specifically" ([Game Developer](https://gamedeveloper.com/design/combining-bombastic-heists-with-a-fully-destructible-voxel-world-in-i-teardown-i-)). Media Molecule described the development of Dreams as an exploration of "mostly abandoned renderers" ([Media Molecule](https://www.mediamolecule.com/blog/article/alex_at_umbra_ignite_2015_learning_from_failure_video)). Blow has worked on Order of the Sinking Star since 2016 with a team of about ten full-time people and ten contractors ([Engadget](https://www.engadget.com/gaming/ten-years-after-the-witness-jonathan-blows-next-massive-puzzle-game-is-almost-ready-for-primetime-015727378.html)). No Man's Sky had an average of six people during development ([GamesRadar](https://gamesradar.com/no-mans-sky-how-the-biggest-game-ever-made-almost-never-happened)). Our documents contain no time estimate. AI speeds up writing code, but the bottleneck from our third report remains verification by one person, and that does not get faster with the speed of the model.

Postmortems of general engines show a pattern that we state here only as facts. **The Machinery ended in August 2022 with no reason given and licenses lapsed within 14 days** ([GameFromScratch](https://gamefromscratch.com/the-machinery-game-engine-appears-to-have-shut-down/)). Autodesk ended Stingray as of January 2018, saying customers were "increasingly standardizing on Unity and Unreal Engine" ([Geo Week News](https://www.geoweeknews.com/news/autodesk-shutters-game-engine-development-cites-popularity-engines)). The Bitsquid line still lives on inside Arrowhead in Helldivers 2 ([80.lv](https://80.lv/articles/helldivers-ii-was-built-on-an-archaic-engine-that-you-can-t-access-anymore/)), and Godot was an in-house engine for years before it was opened in 2014 ([Godot README](https://github.com/Yinimi/godot)). The research originally drew from this the recommendation to build the engine for one game. **The owner rejected it in D19, because the project takes a different production route: AI writes the code, code generates the content and the owner is the art director. D15 stands unchanged.** The report therefore takes over only the lessons that do not depend on this choice. The first lesson is **test scenes as engine verification**, not as narrowing down to one game. The second is middleware for the non-differentiating parts: Noita stands on Box2D and FMOD ([80.lv](https://80.lv/articles/noita-a-game-based-on-falling-sand-simulation/)), Tiny Glade on a modified ECS from Bevy ([80.lv](https://80.lv/articles/exclusive-tiny-glade-developers-discuss-bevy-proceduralism-publishers-cozy-games/)). The third is **tools right at the start**. Remaley writes "your tools are what help you iterate" ([Mason Remaley](https://gamesbymason.com/blog/2023/make-your-own-game-engine/)), and Noel Berry builds only a thin layer on top of SDL3, with editors in ImGui with reflection over game data and hot reload on top ([Noel Berry](https://noelberry.ca/posts/making_games_in_2025/)).

The closest analogy to our way of working is not game engines but Anthropic's long agentic projects. **Sixteen parallel agents wrote, in two weeks and for under 20,000 USD, a C compiler of ~100,000 lines that compiles Linux 6.9 and passes ~99% of the GCC torture tests.** Its optimized output is worse than GCC `-O0`, though, the code quality is "well short of an expert" and CI was added only after new features kept breaking old ones ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). The key was a nearly perfect verifier. The Linux kernel as "one large task" could not be parallelized until GCC served as a known-good oracle. The second experiment keeps state in files: a JSON list of features that all start as failing, the agent may change only the `passes` field and "it is unacceptable to remove or edit tests". JSON was chosen because models rewrite it less than Markdown. Typical failures were trying to do everything at once and declaring done prematurely ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). For us this means that **the roadmap must be a machine-checkable artifact** and every area of the engine needs its own oracle, which splits a large goal into many independent failures.

| Area | Oracle (analogy to GCC for the compiler) |
|---|---|
| detmath | against libm within a declared ulp tolerance + golden hash on 3 OSes |
| Job system | same result hash as the single-threaded reference |
| RHI | null backend against the command stream of the Metal backend |
| Streaming | same set of visible instances as "load everything" |
| LOD/HLOD | error in pixels against full detail below a threshold |
| Physics | replay against recorded golden trajectories |
| Generators | lints (connectivity, floating parts, palette histogram) against the family specification |
| Scale | ratio lint against `ScaleBible` (see the section on D16) |

Reading the existing plans reveals concrete gaps. The two roadmaps differ in content: M4 has a "synthetic city" once and a generated one the other time, and the renderer and the characters are elsewhere. M1 builds a Chase-Lev deque, parking and QoS without a single consumer, and the criterion for done is a microbenchmark. M3 in the procedural roadmap carries the cooker, VFS, resource DB, Merkle cache, hot reload of generators, the complete texture pipeline and BC compression. **The owner drives a car for the first time in M5 and the first verdict "street against GTA III" arrives in M6.** The art risks (the painted WoW look, cars from code, sameness, faces) are thus verified only at the end, even though they are exactly what can change direction. The planetary half of D15 has no milestone. Debug UI, GPU timing, audio, text and HUD, input mapping, crash reporting and the networking decision have no place in any milestone, and saving arrives only in M8. Some assumptions have also gone stale: measurement No. 12 from the third report (Vulkan on Mac via KosmicKrisp) and the same plan in the first report **no longer apply after D20**. KosmicKrisp requires macOS 26 ([LunarG](https://www.lunarg.com/the-state-of-vulkan-on-apple-oct-2026/)) and the development Mac stays on macOS 15.8.1.

## SDL_GPU stays, but the RHI and the renderer are shaped for native Metal

As of November 2026, no cross-platform layer callable from C offers bindless, real multi-draw indirect on Metal, fine timestamps and first-class Metal all at once. **SDL_GPU closed bindless again as "not planned" on 23 June 2026.** According to the maintainers, the community proposal from August 2026 has open problems (different handle sizes, resource cycling, barriers), and as a replacement they recommend texture arrays, atlases or Vulkan directly alongside SDL ([SDL #11148](https://github.com/libsdl-org/SDL/issues/11148)). wgpu has texture binding arrays with non-uniform indexing and timestamps on Metal, but `MULTI_DRAW_INDIRECT_COUNT` only on DX12 and Vulkan ([wgpu Features](https://docs.rs/wgpu/latest/wgpu/struct.Features.html)). Diligent's Metal backend is commercial, NVRHI has no Metal at all and sokol_gfx has a Vulkan backend only experimentally since December 2025 ([floooh](https://floooh.github.io/2025/12/01/sokol-vulkan-backend-1.html)). The Vulkan-only route through KosmicKrisp has been conformant with Vulkan 1.4 since September 2026, but it runs only on macOS 26 over Metal 4 ([LunarG](https://www.lunarg.com/the-state-of-vulkan-on-apple-oct-2026/)), so D20 rules it out. The weighted matrix from the research (the scores are judgment, not measurement) ranks the current route extended with a planned native backend highest:

| Option | Metal quality | Bindless | MDI on Metal | Works on macOS 15 | Weighted sum (max 175) |
|---|---|---|---|---|---|
| A: SDL3 + SDL_GPU behind a thin RHI (today) | 3 | 2 | 2 | yes | 120 |
| **B: A + planned native Metal 3 backend** | 5 | 4 | 4 | yes | **147** |
| C: SDL3 + wgpu-native | 3 | 4 | 2 | yes | 123 |
| D: SDL3 + sokol_gfx | 3 | 1 | 1 | yes | 123 |
| F: custom Vulkan 1.4 + Metal right away | 5 | 5 | 5 | yes | 136 |
| G: Vulkan-only via KosmicKrisp | 3 | 5? | 4? | **no (macOS 26+)** | 116 |

The missing bindless is manageable for a stylized open world of the GTA III / WoW class. **GTA V renders 4,155 draw calls per frame on DX11-class hardware without bindless** ([Courrèges](https://www.adriancourreges.com/blog/2015/11/02/gta-v-graphics-study/)). The real problem is the **CPU encoding cost, which on Metal grows with the number of indirect records**. One source from WebGPU, where MDI is also missing, gives roughly 57 ms against 5 ms in native Vulkan with MDI for the same load ([gpuweb #5175](https://github.com/gpuweb/gpuweb/issues/5175)). The current plan, one fixed indirect slot per object with a zero instance count for discarded ones, does not address this cost. Haar and Aaltonen showed a better way: cluster culling and **index buffer compaction in a compute shader**, after which there is one indirect draw per combination of pipeline × bucket texture array ([SIGGRAPH 2015](https://advances.realtimerendering.com/s2015/aaltonenhaar_siggraph2015_combined_final_footer_220dpi.pdf)). The number of draws then depends on materials and passes, not on objects, and the technique works the same on SDL_GPU, wgpu and native backends. Native Metal mainly adds indirect command buffers filled by a compute kernel, so the CPU loop disappears entirely ([Apple](https://developer.apple.com/documentation/metal/indirect-command-encoding.md)). The recommendation is therefore: **build the RHI from M1 on three portable concepts after Aaltonen's "No Graphics API"** ([Aaltonen](https://www.sebastianaaltonen.com/blog/no-graphics-api)). They are handles resembling buffer addresses (emulated on SDL_GPU as a storage buffer index + offset), a material texture table (bucket texture array + layer on SDL_GPU, argument buffer natively) and an "indirect draw stream" object (a loop on SDL_GPU Metal, ICB natively, `drawIndirectCount` on Vulkan). **The draw cost measurement moves from "before M6" to M1.** A native Metal 3 backend with Tier 2 argument buffers, ICB, MetalFX and timestamps at encoder boundaries gets an explicit trigger. Both Metal 3 and Tier 2 argument buffers work on macOS 15 ([WWDC21](https://developer.apple.com/videos/play/wwdc2021/10286)). Whether SDL3 allows creating a native Metal layer next to its window, nobody has verified yet.

The C17 language remains defensible, but only with safeguards against the errors that AI makes. A summary of an analysis of 86,726 faulty LLM code samples (a secondary source) states that **16.7% of translation errors in Rust would be silent memory errors in C/C++** and that out-of-bounds errors and overflows survive iterative feedback ([study summary](https://codex.danielvaughan.com/2026/08/13/unreliable-in-practice-llm-generated-code-errors-codex-cli-posttooluse-verification-memory-safety-input-validation/)). After the changes in version 0.15, Zig measurably confuses models ([akitaonrails](https://akitaonrails.com/en/2026/01/11/ai-agents-comparing-top-llms-on-the-zig-challenge/)) and for Odin no data on LLM quality exist. Rust would mean restarting the whole analysis. The research found no benchmark of C against C++ for LLMs. **The definition of done must therefore include ASan, UBSan and TSan in CI, `-Wall -Wextra -Wconversion -Werror`, clang-tidy, bounds-checked array macros in the debug build and fuzzing of loaders.** As a recorded alternative to D4 we recommend "C-like C++20" (no exceptions and RTTI, `std::span`). It would ease integrating Jolt, but would cost a slower build and a style that drifts apart. For shaders the weak spot is the toolchain: **SDL_shadercross has no releases and downloads a prebuilt DXC only for Linux and Windows**, so on the Mac DXC is built from source ([SDL_shadercross](https://github.com/libsdl-org/SDL_shadercross)). The shadercross commit therefore needs to be pinned, DXC built once and stored in `.tools/`, and the source kept in pure HLSL. Slang has been maintained by Khronos since November 2024 ([Khronos](https://www.khronos.org/news/press/khronos-group-launches-slang-initiative-hosting-open-source-compiler-contributed-by-nvidia)) and Valve deployed its SPIR-V output in CS2 and Dota 2 ([Khronos](https://members.khronos.org/document/dl/33712)). Its output for Metal was "experimental" in the source found, though, so Slang deserves only a pilot in M1–M2 as a possible single front end with reflection.

D20 also changes the split of tests. **GitHub's hosted macOS runners have 3 vCPU M1 and 7 GB RAM** ([GitHub Docs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)) and their paravirtual Metal device in practice leads to GPU hangs ([llama.cpp PR](https://github.com/bernardladenthin/java-llama.cpp/pull/14)). So only the null GPU backend, builds, unit tests, replay and generator golden hashes will run on them. Pixel goldens will run in Linux CI via lavapipe, forced by the `VK_DRIVER_FILES` variable ([Mesa](https://docs.mesa3d.org/envvars.html)), and locally on the M4 Pro. Real Vulkan and D3D12 are verified at checkpoints on the owner's test machines. WARP as software D3D12 for Windows CI is "fully conformant" with levels 12_0 and 12_1 ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/directx-warp)), but whether it can be selected through SDL_GPU is unverified.

## The architecture lacks three layers that every general engine has

The basis of the design is confirmed by the two closest models. Godot builds on "servers" addressed by opaque RIDs, which can be worked with directly ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html)). Linietsky explicitly writes that Godot is not ECS and that for bulk processing it is better to go to the servers directly ([Godot blog](https://godotengine.org/article/why-isnt-godot-ecs-based-game-engine/)). Wicked Engine uses "ECS-light": an entity is a `uint64_t` and every component type has a manager with dense arrays and no generic scheduler ([wiECS.h](https://raw.githubusercontent.com/turanszkij/WickedEngine/master/WickedEngine/wiECS.h)). Static instances in tens of thousands per cell should not be entities in any engine, and rejecting flecs in the core is therefore right. But all the compared general engines have layers above their subsystems that we lack.

**The first missing layer is a server-shaped simulation.** In version 1.3, Mojang "kicked out single-player, and made it a shell on top of multi-player", which required separating server and client logic after the fact ([Minecraft Wiki](https://minecraft.wiki/w/Java_Edition_1.3.1/Development_versions)). Luanti and Veloren both run singleplayer as a local server from day one, and Veloren has the world generator in a separate crate that works without the client or the server ([Veloren book](https://book.veloren.net/contributors/developers/codebase-structure.html); [Luanti wiki](https://wiki.luanti.org/Terminology)). We do not need networking code now, we need only the right shape. The input of the simulation should be **player commands** (`player_cmd` with a player ID and a tick), not raw SDL events. The same channel then serves replay, the agent, AI and eventual networking. The simulation must not depend on `render`, `audio` or the camera, a headless `server` target will run in CI and streaming plans for multiple sources, as UE World Partition does ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition-in-unreal-engine)).

**The second layer is a data model with a schema and versions.** Wicked registers every component type with a name and a version, serializes records `[name, version, jump offset, data]` and skips unknown types on read ([wiECS.h](https://raw.githubusercontent.com/turanszkij/WickedEngine/master/WickedEngine/wiECS.h)). The Machinery derived undo, copy/paste and version compatibility from a single data model ([The Truth](https://ruby0x1.github.io/machinery_blog_archive/post/the-story-behind-the-truth-designing-a-data-model/)). Its save system stands on unique persistent IDs and a change log ([Save Game pt. 1](https://ruby0x1.github.io/machinery_blog_archive/post/save-game-system-part-1/)). Our design today forbids global reflection. That rule makes sense inside systems, but **at the persistent and editable boundary of the engine every compared engine needs reflection**. We recommend a small type registry (name, version, fields with types and offsets). From it come the chunked save and the cell diff format, recipe migrations, an automatic inspector, JSON Schema for MCP tools and future replication. The same registry also solves the **third gap, the composition of dynamic actors**. An NPC, mount or quest item gets a component manager of one type with a dense array in the style of Wicked and Bitsquid. The game DLL may register its own types, but no generic queries across multiple components and no own scheduler arise. Without that, every game on top of the engine would build its own object model, and that goes against D15.

Another hole is less visible. The design has `FrameParams` and `render_world_add_instances()`, but it **does not say who may read what, how changes propagate and when memory may be freed**. Unreal states the rule precisely: the render thread "can never touch the memory of UPrimitiveComponent directly", changes go through `MarkRenderStateDirty()` and deletion waits for a fence ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/threaded-rendering-in-unreal-engine)). Bevy deletes the entities in the Render World every frame and keeps persistent data in resources ([Bevy cheatbook](https://bevy-cheatbook.github.io/gpu/intro.html)). We recommend writing down three channels: persistent render instances (created and destroyed by command and released after the GPU fence), a change queue (material, visibility, breakage) and a per-frame arena for dynamic actors that is discarded whole. Render-prep never dereferences a simulation handle. Thanks to this, the pipelining sim N+1 ‖ render-prep N in the scaling milestone will be just a switch, not a refactor. Extensibility is similarly missing from the design. **O3DE Gems insert their own passes into the default pipeline** ([O3DE wiki](https://github.com/o3de/o3de/wiki/%5BAtom%5D-Work-With-Passes-In-Gems)) and the planet will need an atmosphere and aerial scattering that the city does not need. Without a declarative description of modules (`eng_module_desc`: dependencies, hooks into frame phases, render graph slots, asset handlers), the `runtime` mediator would gradually grow into a god object. Doom Eternal also shows that a pre-built frame job graph is easier to tune than ad hoc spawns ([Wikipedia: id Tech 7](https://en.wikipedia.org/wiki/Id_Tech_7)).

The port for the world shape under D15 has no model in open-source engines. World Partition is a 2D grid, and Veloren and Luanti are flat. The closest templates are found outside game engines. **Proland has one flat quadtree pipeline and a swappable `Deformation` (identity, sphere, cylinder) with a local tangent frame** ([Proland](https://proland.inrialpes.fr/doc/proland-4.0/core/html/classproland_1_1Deformation.html)). S2 has hierarchical 64-bit cell IDs over 6 cube faces and 31 levels, including neighbor queries across edges ([S2](https://s2geometry.io/devguide/s2cell_hierarchy.html)). The port should therefore abstract only the cell key `(face, level, x, y)` with `face = 0` for a flat world, neighbors, conversion of a cell to a local frame with an "up" vector and a priority metric for streaming. **The current coordinates `int32 cell_x, cell_y + float` are specific to a flat grid** and must be generalized to `cell_key + local float3` before they seep into the `cell_blob` format, generated entity IDs and saves. Related to this is the persistence model, which is still missing. Minecraft stores the generated output, so visited areas freeze and generator improvements do not reach them ([Minecraft Wiki](https://minecraft.wiki/w/Region_file_format)). Space Engineers stores only changes and regenerates the rest identically from the seed ([Marek Rosa](https://blog.marekrosa.org/2014/12/space-engineers-super-large-worlds_17/)). Luanti introduced block timestamps late, and maps from version 5.11 and older often lack them ([Luanti API](https://github.com/luanti-org/luanti/blob/master/doc/lua_api.md)). Our bit-exact determinism makes "store only deltas" the natural choice, but the decision must be made before the streaming milestone. We do not recommend a scripting language now. But `eng_api` should be a stable, versioned C ABI with POD types, so that a Lua adapter on the server side can be added later after the Luanti model.

## The pipeline is strong in tech art but weak on the art director's side

All documented production pipelines have the same division: a tech-art team builds generators and artists control them by parameters directly in the game editor. Far Cry 5's procedural tools were built in Houdini and were "fully integrated into the Ubisoft game editor", because "not every square meter of the world will receive the attention of a level artist" ([80.lv](https://80.lv/articles/houdini-procedural-world-generation-of-far-cry-5/)). **Embark on The Finals found that a modular set of cooperating HDAs works better than one all-embracing one, and iteration took 4–6 minutes per change.** All the pieces also shared one blockout mesh as spatial context ([80.lv](https://80.lv/articles/how-embark-studios-built-procedural-environments-for-the-finals-using-houdini)). UE PCG has hierarchical generation with grids of different sizes and cleanup beyond radius × multiplier ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-pcg-generation-modes-in-unreal-engine)), which is a commercial counterpart of our L3–L0 hierarchy. Infinigen has 182 generators with 1,070 parameters, its canonical form is code and it samples parameters from distributions tuned on examples, for creatures on 30 hand-modeled heads and bodies ([Infinigen](https://ar5iv.labs.arxiv.org/html/2306.09310)). Architecturally we are thus not outside of practice, and our cross-OS determinism is stricter than what UE PCG publicly promises. But the half for the user is missing, because live panels are in the plan only "optionally from M3". Without them, every art change is a trip through the agent.

Code as the authoring format is the right choice for us. LLMs write runnable code reliably and graphs only shallowly, and even Infinigen only transpiles graphs into code. But graphs give the user three things we must replace: a preview of intermediate steps, exposed parameters and direct manipulation. We propose a hybrid. **Every `gen_*` declares a parameter schema in C** (`name, type, unit, min, max, default, dist, group, art_facing, doc`) and from it we automatically generate recipe validation, canonical serialization for the hash, an ImGui panel, documentation for the agent and JSON Schema for MCP. Each family exposes to the owner at most 8–12 `art_facing` parameters, because fully exposed HDAs overload artists ([core.ac.uk](https://core.ac.uk/download/232282292.pdf)), and higher "macro" parameters such as the age or wealth of a district. In the dev build every operator writes its name, parameters, hash and a thumbnail into a "recipe trace", so `gencli trace` draws the graph from the run with previews like Substance, just without editing. Runtime generation samples only from approved **presets with distributions**, which the owner adds and removes. The owner also needs the operations pin, reroll, seed ban, parameter nudge and stamp right in the cell preview. These are written to `content/world/overrides`. Embark's shared blockout translates for us into a "building context" data structure (mass, openings, floors, orientation) that all kit generators read.

Against "procedural sameness", practice uses not better noise but hand-designed building blocks and readability rules. Spelunky assembles hand-designed room templates by role on the critical path, by an informal estimate roughly 80% of the layout by hand and 20% random ([Tiny Subversions](https://www.tinysubversions.com/2009/09/spelunkys-procedural-space/index.html)). Embark, on the other hand, unified the interiors in Monaco because varied ones confused players ([80.lv](https://80.lv/articles/how-embark-studios-built-procedural-environments-for-the-finals-using-houdini)). For us the role of templates is taken over by curated presets. For the range of variability we propose our own numeric oracle. For each family, 500–1,000 seeds are generated, 2–4 descriptors are computed (height, silhouette aspect ratio, dominant hue, outline complexity) and a lint guards both sides: too narrow a range (sameness) and outliers (chaos). It is complemented by a district distinguishability lint, in which the distance between districts must be greater than within them, and quotas for the occurrence of prominent kit pieces per km². In addition to numbers, the style bible must contain words and images: a shape language, a list of forbidden patterns and approved anchor renders for each family.

Our AI workflow rules (oracles, then a separate evaluator, then the owner) match the best public practice. But they lack calibration. Anthropic found that agents "reliably skew positive when grading their own work". A separate evaluator could be tuned toward skepticism with few-shot examples with scores from the author and weights shifted toward the criteria the model itself fails at, yet it still sometimes "talked itself into approving" errors it had found earlier. Before every sprint the generator and the evaluator negotiated a "done" contract, in the third sprint with 27 criteria. **The solo run cost 20 min and 9 USD with a non-working main feature, the full harness 6 h and 200 USD** ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Godogen uses a cheap model from another vendor, Gemini Flash, as the default visual QA ([Godogen](https://www.skills.sh/htdt/godogen/visual-qa)). **BlenderRAG raised, by retrieval of 500 verified examples, the compilation success rate from 40.8% to 70.0% and the CLIP match from 0.41 to 0.77** ([BlenderRAG](https://maxrondelli.github.io/BlenderRAG/)). Six additions follow. The evaluator gets a rubric for each family and a few-shot set of 6–10 renders with the owner's score and the criterion "generic look". It first lists the flaws and only then the score. For every iteration a cheap second evaluator from another vendor will run, and disagreement between the two is escalated to the owner. For each family an `acceptance.md` is created before generation, which the owner approves. The owner's decisions will be logged via a paired A/B interface into `review/decisions.jsonl`. Every golden hash change creates a before and after gallery. Approved generators will form a library of examples for retrieval. Finally, when upgrading the model, it is necessary to test which parts of the harness can be switched off.

For textures under D14, more mature tools are available than report 2 counted on. **StableMaterials generates a tileable PBR set (basecolor, roughness, metallic, height, normal) in four steps and its code and models are public** ([arXiv](https://arxiv.org/html/2406.09293v3)). Substance 3D Sampler derives a parametric material from an image and attaches Content Credentials to Firefly outputs ([80.lv](https://80.lv/articles/adobe-s-substance-3d-sampler-4-4-sources-texture-imagery-from-prompts)). Since January 2026 Steam requires disclosing AI content that "ships with your game, and is consumed by players" ([PC Gamer](https://www.pcgamer.com/software/ai/steam-updates-ai-disclosure-form-to-specify-that-its-focused-on-ai-generated-content-that-is-consumed-by-players-not-efficiency-tools-used-behind-the-scenes/)). Embark got into a controversy even though it claims it did not use generative AI for visuals ([PC Gamer](https://pcgamer.com/gaming-industry/arc-raiders-use-of-ai-highlights-the-tension-and-confusion-over-where-machine-learning-ends-and-generative-ai-begins)). D14 should therefore allow the AI to be the source of a whole set of maps, because height derived from brightness is wrong for dark protrusions. A family should be generated in one batch with the same reference board. Provenance is extended with the model version, the license and terms valid at the date of generation, a C2PA manifest, the approver and a `player_facing` flag, and `gencli provenance-report` produces the basis for the disclosure. Whether the output of deterministic generators written by Claude falls under disclosure is our interpretation, not legal advice.

## Scale keeps the human characters, only the space around them grows and distances get shorter

The real anchors for D16 fit into a short table. The ergonomic reference for level design is a **1.75 m character with an eye height of 1.68 m and a door of 0.91 × 2.03 m** ([Level Design Book](https://book.leveldesignbook.com/process/blockout/metrics)). The structural floor height is roughly 3.1 m in residential and 3.9 m in commercial buildings ([Wikipedia: Storey](https://en.wikipedia.org/wiki/Storey)). NACTO recommends urban lanes of 10 ft (3.05 m) and advises against lanes wider than 11 ft ([NACTO](https://nacto.org/publication/urban-street-design-guide/street-design-elements/lane-width/), taken from a search summary). A German motorway lane is 3.75 m ([Wikipedia: Lane](https://en.wikipedia.org/wiki/Lane)). The visible curb height is 100–200 mm ([Wikipedia: Curb](https://en.wikipedia.org/wiki/Curb)). A block in Manhattan measures about 80 × 274 m, in Chicago and Melbourne 100 × 200 m ([Wikipedia: City block](https://en.wikipedia.org/wiki/City_block)).

Games deviate from reality in two separate ways, and neither changes the size of the characters. The openings and spaces around the player grow and the distances get shorter:

| Source | Door / player height |
|---|---|
| Reality (USA) | 1.16 |
| Unreal (community metrics) | 1.25 |
| Unity (community metrics) | 1.39 |
| Source (Valve Developer Community / Level Design Book) | 1.50 / 1.56 |

Source: [Level Design Book](https://book.leveldesignbook.com/process/blockout/metrics). The figures for Source differ between the two sources. Skyrim has a character "about 128 units, or six feet tall". Kit footprints must be mutual multiples, because 384-unit rooms "will eventually create gaps and/or overlaps", and a uniform door frame is set right at the start as a standard for AI and animation ([Game Developer](https://www.gamedeveloper.com/design/skyrim-s-modular-approach-to-level-design)). The whole world of Skyrim is roughly half of Manhattan (Level Design Book). The failure of the previous project, giant characters in a small city, is exactly the opposite error: the character grew, but the openings did not. **The ratio of two objects at the same distance does not depend on the FOV, so the camera does not fix a relative scale error. Only the table and ratio lints fix it.** The camera does decide readability, though. The horizon in perspective intersects every object at camera height, and when the camera is at eye height, the horizon must cross standing characters in the head area. This test can be automated. A third-person camera with a shoulder arm of length L also needs free space of roughly L plus the collision radius. That is why games with such a camera have larger doors and corridors.

The design has two layers. **The engine fixes** 1 unit = 1 m, one "up" axis (Y or Z, one must be chosen), the `ScaleBible` schema, the `scale_derive()` function, the lint framework, a texel density of 128/256 px/m and a "scale rig" in every review render. The rig consists of a 1 m grid, p5/p50/p95 mannequins, a standard door, a reference sedan and a horizon line, and it is rendered from the game camera and from a camera behind the car. The hash of the table enters the key of the Merkle cache, so a scale change invalidates exactly what depends on it, and no generator may contain a length literal. **Each game (project) determines** about ten primary numbers and everything else is derived from them. The following values are **proposals, not measured data from GTA III or WoW**. They await owner approval on a scene with reference shots of GTA III and WoW that the owner will supply:

| Key | Real anchor | Proposed default stylized profile | Derived consequence (proposal) |
|---|---|---|---|
| `hero_height` | 1.75 m | 1.80 m | capsule r ≈ 0.30–0.35 m |
| `k_opening` (doors, corridors, ceilings) | 1.0 | 1.20 (1.10–1.35) | door ≈ 2.5 × 1.1 m |
| `k_storey` | 1.0 | 1.10 (1.0–1.2) | residential floor ≈ 3.4 m, ground-floor shop ≈ 4.6 m |
| `k_lane` | 1.0 | 1.15 (1.0–1.3) | lane ≈ 3.5 m, street with two lanes and parking ≈ 19 m between facades |
| `k_distance` (only block counts and lengths) | 1.0 | 0.5 (0.3–0.7) | long side of a Manhattan-style block ≈ 140 m |
| `module` | — | 0.5 m | all kit dimensions are multiples |
| `k_vehicle` | sedan ≈ 4.6 × 1.8 m (unverified) | 1.0–1.05 | cars stay almost real |
| stairs, curb, railing, seats | 0.17/0.28 m; 0.15 m; 1.0–1.1 m | **do not scale** | contact dimensions of the body, otherwise the character feels small |

Lints work on three levels: a bounding box per class, ratios between classes computed from the generated outputs (door/tallest NPC ≥ 1.10, floor/door 1.3–1.9, lane/widest vehicle 1.25–1.6, car roof/hero 0.75–0.95) and world statistics (histograms of street widths, block lengths and time between intersections at the target speed). They also include passing a capsule and camera probes through generated doors, alleys and corners, a grid lint (multiples of `module` are an error, not a warning) and a numeric horizon test over the headless render of the scale rig. For a planet, **the radius is a parameter of the world shape, not a scale**. Light No Fire targets an Earth-sized planet ([PC Gamer](https://www.pcgamer.com/hello-games-grand-follow-up-to-no-mans-sky-light-no-fire-is-an-open-world-the-size-of-the-actual-earth)), and there the drop d²/2R is only 7.9 cm over 1 km. On a planet with a radius of 100 km, though, a 256 m cell drops by 0.33 m. Roads and building foundations therefore have to be fitted into the local tangent frame of each cell, and a lint guards the maximum gap under the foundations. We take the procedure from Bethesda, where the footprint of a kit is agreed in a "proof" phase lasting 1–3 weeks before detail is created ([Game Developer](https://www.gamedeveloper.com/design/skyrim-s-modular-approach-to-level-design)). **The table is frozen in M2 on a "metrics zoo" scene, before mass generators exist.** Later changes will go through DECISIONS.md and cache invalidation.

## Debugging works through a digest instead of a screenshot and a step instead of real time

Logging in all big engines has the same skeleton: a channel × level filter changeable at runtime, several outputs and in-memory history. **Unreal has seven levels, switches categories via `-LogCmds` and also from the console, and since version 5.2 it supports structured `UE_LOGFMT` with up to 16 named fields** ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine)). Wicked formats into a 1024-byte buffer and for crash handlers has a lock-free, allocation-free iterator ([wiBacklog.h](https://raw.githubusercontent.com/turanszkij/WickedEngine/master/WickedEngine/wiBacklog.h)). Unity in `-nographics` mode explicitly states "Output logs are turned off in this mode" ([Unity](https://docs.unity.com/en-us/engine/current/manual/unity-editor/command-line-arguments/player)). For us that is an anti-pattern, because **headless is the main mode for the agent and its log must be the most complete**. The design: JSON Lines into `runs/<id>/log.jsonl` with records `{seq, t_ns, frame, tick, thr, lvl, ch, msg, src, kv}` and, in parallel, readable colored output on stderr. A static table of at most 64 channels with an atomic level is tested before the arguments are evaluated. The release build has a compile-time floor, `LOG_ONCE` and `LOG_EVERY_N` prevent spam and per-frame error counts go into the digest. The owner's experience with godot-mcp shows that an error repeating every frame can escape a whole session if you look only at images (skill godot-game-testing). The most valuable context is supplied by `ENG_SCOPE("cell", id)`. It attaches to every record and assert, so the report "assert in bake.c:88" changes into "assert in bake.c:88 while generating cell (12,−3), asset car.sedan, seed 7".

Headless has two modes and we need both. The first is a null RHI without a GPU device (Unreal `-nullrhi`, Godot `--headless`), the second an offscreen render on a real or software device with readback to PNG (Unreal `-RenderOffScreen`) ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-command-line-arguments-reference); [Godot](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)). SDL_GPU does not need a window, "you can render offscreen entirely", and it reads back via `SDL_DownloadFromGPUTexture()` and a fence ([SDL wiki](https://wiki.libsdl.org/SDL3/CategoryGPU)). Determinism is ensured by a fixed step driven by the frame count, not by clocks, following Godot (`--fixed-fps` + `--quit-after`) and Unreal (`-deterministic`). The workhorse will be a single command `wz --gpu=null --seed 7 --script scenarios/drive_loop.wzs --frames 1800 --dump runs/x/`, whose script contains assertions (`expect stream.late_cells == 0`). It works without a socket, without latency and without random failures, and is the same in CI and for Claude.

For controlling a running engine, CVars and named commands with help text have proven themselves, settable from the command line, config, console and socket. Quake registers them by name and the console can both read and set them ([Quake cvar.h](https://raw.githubusercontent.com/id-Software/Quake/master/WinQuake/cvar.h)). **Unreal recommends detecting changes by comparing with the last value, because the callback "can deadlock"**, and keeps a priority of sources from the constructor to the console ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/console-variables-cplusplus-in-unreal-engine)). The most important lessons, however, come from the agents. godot-mcp offers freeze, step and step-until on the game clock, JSON state digests and a separation of read and write tools ([godot-mcp](https://github.com/satelliteoflove/godot-mcp)). The owner knows from practice that tens of seconds pass between two tool calls, that inputs must "run with the step" and that **one 1280×720 frame costs ~1,200 tokens that stay in context for the whole session**. Anthropic advises returning concise, paginated output with errors that make the next step clear, and respecting the 25,000-token cap in Claude Code ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)). Scripting against the API instead of carrying intermediate results through context reduced consumption in one example from ~150,000 to ~2,000 tokens ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)). From this come roughly ten method namespaces: `sim.pause/step/step_until` (the engine with `--agent` starts paused and inputs are part of the step), `state.digest` (every subsystem has `xxx_debug_state()` with a size limit), `log.tail` (cursor `since_seq`, losses are always reported), `cvar.*`, `cmd.exec`, `shot` (returns a path and numeric brightness statistics, not an image), `query.raycast/cell/entity`, `debugdraw.dump`, `replay.save`, `bug.bundle`, `prof.capture` and `gpu.capture`. **A "run arbitrary code" tool is deliberately missing**, because blender-mcp executes arbitrary Python over an unauthenticated socket ([blender-mcp](https://github.com/ahujasid/blender-mcp)). All mutations (keyboard, script, RPC) go through `eng_cmd`, are applied at the tick boundary and are recorded into the replay. A session driven by Claude is thus itself a reproducible bug.

Debug draw is owned in C (im3d is C++ and would violate D4) and can be dumped as JSON, so the agent "sees" cell boundaries or path nodes numerically. The human inspector runs in Dear ImGui only in the dev build. GPU capture is provided by the RenderDoc in-app API on Windows and Linux ([RenderDoc](https://renderdoc.org/docs/in_application_api.html)), and on Metal by a programmatic capture whose details are unverified. The agent only produces and archives the capture for the owner, because it cannot read it itself. Tracy is suitable for profiling: **its C API costs ~2.25 ns per zone and compiles to nothing without `TRACY_ENABLE`**, and it has a CLI capture and a CSV export that the agent can read ([TracyC.h](https://raw.githubusercontent.com/wolfpld/tracy/master/public/tracy/TracyC.h); [manual](https://raw.githubusercontent.com/wolfpld/tracy/master/manual/tracy.tex)). The manual does, however, state higher overhead on Apple platforms and a downloaded version confirming only OSX x64. GPU time through SDL_GPU stays coarse (fence to fence). Budgets that fail CI must therefore be **deterministic counters** computed in the RHI front end: draw calls, triangles, uploaded bytes, binds and allocations by tag on named views. Budgets in milliseconds will run only on the M4 Pro with stored baselines.

Repeatability stands on replay. Riot records the inputs and configuration of every match and **replays forty minutes of a match in under three minutes**. It originally introduced determinism for the Delta Checker tool for fast repeatable tests ([Riot](https://www.riotgames.com/en/news/determinism-league-legends-introduction)). Our `.wzr` format carries in the header the build hash, seed and CVars marked `REPLAY`, in the body inputs by tick and every K ticks a 64-bit hash of each subsystem. Playback then reports "first differing tick T, subsystem phys". A hard rule applies to streaming: the simulation reads only data resident at the tick boundary, so a replay with artificially delayed I/O must produce the same hashes. The crash handler (signals and SEH, alternate stack, backtrace, last ~200 log records, the `ENG_SCOPE` stack) belongs in M0. sentry-native with the crashpad backend and the `none` transport (MIT, no server) will add minidumps later ([sentry-native](https://github.com/getsentry/sentry-native)). A bug bundle (log, replay, CVars, digest, statistics, screenshot, build) is created from a crash and from the owner's keyboard shortcut, and `wz --repro bugs/<dir>` replays it to the faulty tick with the debug server open. The test pyramid consists of utest.h in CTest with the labels `fast/gen/replay/gpu/perf` ([utest.h](https://github.com/sheredom/utest.h)), exact CPU hashes on 3 OSes, lints, scenarios, counter budgets, image goldens for each backend compared with the FLIP metric ([NVlabs/flip](https://github.com/NVlabs/flip)) and nightly fuzzing of generators with lints as properties. Microsoft confirms that even WARP and hardware do not match pixel for pixel, only within the tolerances of the specification ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/directx-warp)), so pixel hashes are never compared between backends.

## One tool registry serves the studio, MCP and CLI

**As of November 2026, three large editors have a built-in MCP server.** Roblox Studio uses a stdio launcher with about 25 tools and every call carries a `studio_id` ([Roblox](https://create.roblox.com/docs/en-us/studio/mcp.md)). Unreal 5.8 has an experimental HTTP server at `127.0.0.1:8000/mcp` without authentication, finds tools via meta-tools, executes calls serially on the game thread and can generate `.mcp.json` into the project ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-mcp-in-unreal-editor)). Unity has a stdio relay with a socket to the editor, but **the 2.19 documentation states "Unity MCP server is deprecated. Use the Unity command-line interface (CLI) instead."** ([Unity](https://docs.unity3d.com/Packages/com.unity.ai.assistant@2.19/manual/integration/unity-mcp-overview.html)). The specification meanwhile changes quickly. The 2026-07-28 revision removed sessions and the `initialize` handshake, introduced a mandatory `server/discover`, recommends a deterministic tool order for the prompt cache and passes state between calls through explicit handles in arguments ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). There is no official SDK for C or C++ ([MCP SDKs](https://modelcontextprotocol.io/docs/2026-07-28/sdk.md)). Claude Code as the main client has a default cap of 25,000 tokens on output, tool search on by default, server instructions truncated to 4,096 characters, the flag `anthropic/requiresUserInteraction` for forced confirmation and, in beta, long-running tasks ([Claude Code docs](https://code.claude.com/docs/en/mcp)).

The D17 research recommended "CLI first, MCP optional", the D18 research MCP from M0. **D18 makes MCP mandatory and the two recommendations can be merged: one tool registry in the engine and thin transports over it.** Unity's retreat to the CLI shows why this matters. If clients turned away from MCP, the switch costs nothing. The registry (`eng_tools`) holds the tool descriptions:

```c
typedef struct eng_tool_desc {
    const char *name, *title, *description;      /* keywords at the start of the description */
    const char *input_schema, *output_schema;    /* JSON Schema 2020-12 from the type registry */
    uint32_t    flags;   /* TOOL_READ_ONLY | TOOL_MUTATES | TOOL_LONG | TOOL_NEEDS_OWNER | ... */
    eng_tool_result (*call)(const struct eng_tool_args *a, struct eng_tool_ctx *ctx);
} eng_tool_desc;
```

Calls are queued and the main thread executes them between frames, just as Epic serializes on the game thread. Tools are registered by the runtime, the studio and the game DLL, and after a hot reload the registration is refreshed with a `list_changed` notification. There are three transports. `wzmcp` is a small C17 EXE with stdio JSON-RPC (yyjson, MIT, a single `.h/.c` pair ([yyjson](https://github.com/ibireme/yyjson))), which finds the running studio via `.wz/session.json` or starts a headless engine. `engctl` and `gencli tool <name> <json>` are CLIs for Bash, CI and scripts. The third transport is the studio console. The debug server from D17 communicates over a unix socket with 0600 permissions or a named pipe in `.wz/` with a token, and its internal messages have the form of an MCP tool call, so one implementation serves all. This removes an open port, and with it attacks via `Origin` and DNS rebinding, which Epic handles only with loopback. HTTP on `127.0.0.1` with an `Origin` check (response 403 according to the 2025-11-25 revision ([MCP changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog))) will be added only for clients that cannot do stdio. The set grows from three tools in M0 (`wz_status`, `golden_check`, `log_tail`) to roughly thirty in eight sets (session, project, gen, recipe, quality, world, view, time, debug, play, ui, review). Images are returned as a path or resource link and judged by a subagent. `golden_accept` requires owner confirmation. `review_request` is a long-running task that the owner completes by a click in the studio, because elicitation works only in an interactive terminal. Live project data is exposed as resources: `wz://project/style`, `wz://project/scale` and `wz://gen/{id}/schema`.

The studio is a separate binary `wz_studio`, built from the same static libraries as the game, plus the module `eng_editor`, on which nothing lower may depend. That is the Godot rule `editor/ → scene/ → servers/ → core/` ([Godot](https://docs.godotengine.org/en/latest/engine_details/editor/introduction_to_editor_development.html)). **Play runs the game as a subprocess** following Fyrox, "so the editor won't crash if your game does" ([Fyrox](https://fyrox-book.github.io/beginning/editor_overview.html)), and connects to it through the debug server. Headless CI thus takes the same path as Play. The Machinery had authority in memory and listed a git-friendly on-disk format as an open problem ([The Truth](https://ruby0x1.github.io/machinery_blog_archive/post/the-story-behind-the-truth-designing-a-data-model/)). We choose the opposite direction: **the authority is text recipes in git, and every change from a panel, from MCP and from a text editor goes through `recipe_patch`**. It writes a record (object, property, old, new, author `owner` / `ai:claude` / `file-watch`) into a single undo stack for the whole project, so the owner reverts with one click what the agent changed. The art director needs a viewport with camera presets, a scale rig and debug views, a recipe browser, a parameter panel generated from the schema, a contact sheet with A/B and the buttons Approve, Reject and Note, the state of lints and golden hashes, and **notes pinned into the world with position, camera and a screenshot**. Notes are the main channel from the owner to Claude. Modeling gizmos come only with manual overrides. For the studio UI the most suitable is Dear ImGui via dear_bindings (`dcimgui.h`) ([dear_bindings](https://github.com/dearimgui/dear_bindings)) with the official backend `imgui_impl_sdlgpu3`, which since August 2025 takes `SDL_GPUTexture*` as `ImTextureID` ([imgui](https://github.com/ocornut/imgui/blob/master/backends/imgui_impl_sdlgpu3.h)). C++ stays inside the `imgui_c` adapter, just like Jolt. We will build the game UI on Clay (C, zlib, flexbox-style layout without allocations, output is render commands) ([Clay](https://github.com/nicbarker/clay)) and text via SDL_ttf 3 with HarfBuzz and `TTF_CreateGPUTextEngine` ([SDL_ttf](https://github.com/libsdl-org/SDL_ttf); [wiki](https://wiki.libsdl.org/SDL3_ttf/TTF_CreateGPUTextEngine)). A ready-made Clay renderer for SDL_GPU is not verified. RmlUi is a fallback for menus with a lot of text, but it has a C++ API and its SDL GPU backend has no filters or clip masks ([RmlUi](https://github.com/mikke89/RmlUi)). The game UI must be able to dump a `ui_tree` (ID, box, text, focus) from the start and render itself headless, otherwise the agent cannot verify it.

The project system takes from Godot one root manifest and a file system without an asset database ([Godot](https://docs.godotengine.org/en/stable/tutorials/best_practices/project_organization.html)), and from Unreal `Config/`, which overrides engine defaults, and the deletable `Saved/` ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-directory-structure)). A project is a folder `projects/<game>/` with `wz.project` (the `eng_api` version, `engine_rev`, `world_shape`, game module, gen-packs), `CLAUDE.md`, `.mcp.json`, `style/` (style bible, `scale.cfg`, references), `content/`, `source_images/` with provenance, `game/`, `ui/`, `config/`, `review/` and `tests/golden/`. Caches and `.wz/` are in gitignore. The engine in the monorepo offers the templates `city`, `planet` and `empty`. **CI builds and tests the golden hashes of all projects on every engine change. This is the main technical safeguard that we do not tailor the engine to one game, and it is fully in line with D15 and D19.** The context for AI has three layers: a short `CLAUDE.md` with rules, live MCP resources and server instructions up to 4,096 characters (first `wz_status`, images via a subagent, mutations via `recipe_patch`).

## Conclusion

The comparison shifts the center of gravity of the plan. The existing roadmaps counted on the engine being built first and only then looked at. Real projects and agentic experiments show the opposite: **the product of the first milestones is not a renderer but a verification loop**. It includes oracles for every area, digests instead of screenshots, stepped time, one tool registry and a studio in which the owner approves in batches. The scarcest resource of the project is not the performance of the M4 Pro or the speed of the model, but the hours of the art director's attention. Every decision in the plan below is therefore measured by how much of the owner's work it converts into a number, a lint or a single click.

The second shift concerns D15. Generality is proven not by declaration, but by **two implementations behind every port that D15 names, and two projects in CI**. The city block and planet seed test scenes are, from this point of view, engine tools, not a game. They fill the role that an anchor game played in the history of general engines, and yet they do not violate D19 in any way. At the same time, three numbers turn out to be more expensive than any architectural decision, and therefore they need to be known early: the draw cost on Metal through SDL_GPU, the frozen scale table and the real throughput of the owner's review. The last of these remains mainly unknown. The research found no data on how many renders per hour an art director can reliably judge, and the plan must measure this value from M2.

## Unified milestone plan M0–M9

This plan replaces M0–M7 from the architecture report and M0–M8 from the procedural graphics report and takes effect once the owner ends the analysis (D11). Each milestone builds permanent code in its final module with tests, without throwaway prototypes. Each has a file `milestones/Mx.json`, whose items the agent may only switch to `passes: true`, and only after a successful command. Items with `owner_gate: true` may be switched only by the owner, in the studio via `review_request` or by hand. The owner's review budget is part of the milestone, gates are grouped into fixed dates and are deferred as a sheet, not individually.

```json
{ "milestone": "M2", "owner_review_budget_h": 6,
  "items": [
    { "id": "M2.lavapipe_golden", "desc": "the reference scene passes FLIP on lavapipe",
      "cmd": "ctest -L gpu -R zoo_lavapipe", "expect": "exit 0", "passes": false },
    { "id": "M2.scale_freeze", "desc": "the owner approved ScaleBible on the metrics zoo next to GTA III/WoW",
      "cmd": "wz_review status scale_bible", "expect": "approved", "owner_gate": true, "passes": false } ] }
```

| Milestone | Content | Test scene and measurement | Done when (machine-checked) | Owner gate |
