# Comparing the Wallhammer Zero architecture with real engines and proposed improvements

Notes written 2026-11-05. The design under comparison: `docs/research/open-world-engine-architecture.md` (layers as CMake targets, ports only on 5 seams plus a game port, the `runtime` mediator, archetypes/instances/handles instead of ECS, work-stealing jobs without fibers, cells of 128–256 m, a thin RHI over SDL_GPU, a light render graph, the game as a hot-reload C DLL), `docs/research/procedural-graphics.md` (the `asset_provider` port, `eng_gen_*` targets, the generator as a cell source, determinism on the CPU only) and `docs/DECISIONS.md` (D15: general engine, city and planet, world shape behind a port).

Dates on sources: where a source gives a date, it is given with it. The Godot documentation was read in version 4.7 (stable, 11/2026). The Bevy cheatbook is for Bevy 0.9 and calls itself outdated.

## 1. Engine by engine: what they do differently and what to take from it

### Takeaway
Our design is closest to Godot (isolated "servers" addressed by opaque handles) and Wicked Engine (simple typed component managers without a generic scheduler). But it differs from all the compared *general* engines in that it has **no general game object model above the "servers", no data model for an editor and no extension mechanism for plugins**, and in that the simulation is not separated from the client from the start, as it is in Veloren, Luanti and Minecraft since version 1.3. For a one-team game this is fine. For D15 ("general engine") these are the three biggest holes.

### Cited Findings

**Godot 4 (servers, RID, scene on top)**
- Servers are "low-level APIs to control rendering, physics, sound, etc." The scene system is built on top of them and "it can be completely bypassed", but it cannot be compiled out. — [Godot docs 4.7: Using Servers](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html)
- RIDs are "opaque handles to the server implementation. They are allocated and freed manually". Resources are not reference counted through them, so a resource can be freed under a RID if you do not hold a reference to it separately. — [Godot docs: Using Servers](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html)
- Servers "will often run asynchronously for performance". A call that returns a value forces synchronization, and if it is made every frame, it kills performance. — [Godot docs: Using Servers](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html)
- Juan Linietsky (26 Feb 2021): Godot is not an ECS, "Godot does composition at a higher level than in a traditional ECS". Nodes are "just interfaces to the actual data being processed inside servers". For games that need cache-friendly processing (city builders, sandboxes, large strategy games) he recommends processing less per frame, calling servers directly, GPU compute, or a third-party ECS (Godex). — [Godot blog: Why isn't Godot an ECS-based game engine?](https://godotengine.org/article/why-isnt-godot-ecs-based-game-engine/)
- Below the servers lies RenderingDevice with drivers for Vulkan, D3D12 and Metal (already cited in our first report). — [Godot internal rendering architecture](https://docs.godotengine.org/en/latest/engine_details/architecture/internal_rendering_architecture.html)

**Wicked Engine (one developer, C++)**
- `Entity` is a `uint64_t`, 0 is invalid, and IDs are handed out from a global atomic counter. The header warns that values change between runs and must be serialized through `SerializeEntity()` for persistence. — [wiECS.h (master, read 11/2026)](https://raw.githubusercontent.com/turanszkij/WickedEngine/master/WickedEngine/wiECS.h)
- `ComponentManager<T>` is a `final` template with two parallel dense arrays `components` and `entities` and an entity → index lookup table (bucket hash per 64 entities). `Remove()` is swap-with-last, `Remove_KeepSorted()` shifts, and `MoveItem()` reorders (because of hierarchies). — [wiECS.h](https://raw.githubusercontent.com/turanszkij/WickedEngine/master/WickedEngine/wiECS.h)
- `ComponentLibrary::Register<T>(name, version)` holds the name and version of each type. Serialization writes records `has_next, name, jump offset, version, data`. On read, versions are collected first and unregistered types are **skipped by offset**. Entities are remapped on load (`EntitySerializer::remap`). — [wiECS.h](https://raw.githubusercontent.com/turanszkij/WickedEngine/master/WickedEngine/wiECS.h)
- The author's blog (September 2019) describes an ECS used for a year. He never wanted more than one component of the same kind per entity. — [Wicked Engine: Entity-component system](https://wickedengine.net/2019/09/entity-component-system) (the page returned 404 when fetched in 11/2026, content only from a search engine snippet)

**The Machinery (Our Machinery, C, discontinued 2022)**
- "The Truth" (7 Nov 2018): data are **objects with typed properties** (bool, int, float, string, buffer, reference, sub-object, sets). The in-memory representation is authoritative and the disk is just a backup ("the in-memory representation of the data is considered authoritative"). Large binary data are opaque buffers. — [Gray: The Story behind The Truth](https://ruby0x1.github.io/machinery_blog_archive/post/the-story-behind-the-truth-designing-a-data-model/)
- The model gives undo/redo and copy/paste ("can be defined in terms of the data model"), real-time collaboration by serializing changes over the network, forward and backward compatibility without per-version code, and references through unique IDs. Sub-objects are cloned, references are not. — [The Truth](https://ruby0x1.github.io/machinery_blog_archive/post/the-story-behind-the-truth-designing-a-data-model/)
- Scenes in The Machinery are **built on an ECS and the ECS itself is a plugin**. The editor is built around it. The renderer knows nothing about meshes or lights. Component plugins implement `tm_ci_shader_i` (lights, probes, decals) and `tm_ci_render_i` (renderable objects) and insert their own modules into the render graph. The goal is "hundreds of thousands of them each frame". — [Our Machinery: ECS and Rendering (23 Oct 2018)](https://ruby0x1.github.io/machinery_blog_archive/post/ecs-and-rendering/)
- The archive also contains "Syncing a data-oriented ECS with a stateful external system" (8 Jun 2019), "Multi-Threading The Truth" (16 Oct 2017) and the three-part "One-Click Save Game System" (2021). — [blog archive](https://ruby0x1.github.io/machinery_blog_archive/)

**Bevy (Rust, ECS + plugins)**
- The renderer "operates independently from all the normal app logic" and has its own ECS World and schedule. It synchronizes with the main World in the **Extract** phase, which copies the needed data into the Render World. The renderer then "can only use data that is stored there". — [Bevy cheatbook: Render architecture (Bevy 0.9, outdated)](https://bevy-cheatbook.github.io/gpu/intro.html)
- Every frame **all entities in the Render World are deleted, resources stay**. Data that lasts across frames belongs in resources. The architecture appeared in Bevy 0.6 and pipelined rendering (render of frame N ‖ update N+1) was only planned when the page was written. — [Bevy cheatbook](https://bevy-cheatbook.github.io/gpu/intro.html)

**Unreal Engine (game/render thread, proxy)**
- The renderer runs in its own thread "a frame or two behind the game thread". At the end of `Tick()` the game thread blocks until the render is within this window. — [Epic: Rendering thread](https://dev.epicgames.com/documentation/en-us/unreal-engine/threaded-rendering-in-unreal-engine)
- "The rendering thread can never touch the memory of UPrimitiveComponent directly." A component has a render-side `FPrimitiveSceneProxy` created at registration. Changes go by message and game code must call `MarkRenderStateDirty()`. Dynamic data, for example bones, is copied into a heap allocation that the render thread owns and frees. — [Epic: Rendering thread](https://dev.epicgames.com/documentation/en-us/unreal-engine/threaded-rendering-in-unreal-engine); [FPrimitiveSceneProxy API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/FPrimitiveSceneProxy?lang=en-US)
- Communication goes through a render command queue (`ENQUEUE_RENDER_COMMAND`), `FRenderCommandFence` and `FlushRenderingCommands`, which is allowed only in the editor. Rules: a UObject is not dereferenced on the render thread, because "the game thread may delete … while the rendering thread is processing a command that references it". Deletion is deferred through a fence. — [Epic: Rendering thread](https://dev.epicgames.com/documentation/en-us/unreal-engine/threaded-rendering-in-unreal-engine)
- `GetDynamicMeshElements` "should not modify the proxy but simply collect a description of things to render". — [FPrimitiveSceneProxy::GetDynamicMeshElements](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/FPrimitiveSceneProxy/GetDynamicMeshElements)

**idTech 7 / Doom Eternal**
- Axel Gneiting (id Software, tweet 21 Mar 2020): Doom Eternal **has no main thread and no render thread**, "everything is implemented as jobs", one worker per core. According to the search report he estimated roughly ~100 jobs per frame and mentioned jobs spawning jobs and **pre-built job graphs**. — [Wikipedia: id Tech 7 → tweet](https://en.wikipedia.org/wiki/Id_Tech_7), [tweet](https://twitter.com/axelgneiting/status/1241487918046347264) (the tweet itself was not verified by fetch, the figure of ~100 jobs and the job graphs come from a search engine summary)
- The job system was rewritten for id Tech 7 so that no core has to be reserved for scheduling. — [Wikipedia: id Tech 7](https://en.wikipedia.org/wiki/Id_Tech_7) citing the [IGN video, 28 Feb 2020](https://www.youtube.com/watch?v=9S5ABf53rDo)

**O3DE (Gems, Atom, frame graph)**
- Atom RPI defines scenes, passes, the render pipeline as a **tree of passes**, and the CPU simulation. GPU work is recorded in passes. — [O3DE: RPI system](https://docs.o3de.org/docs/atom-guide/dev-guide/rpi/rpi-system/)
- The RHI frame scheduler builds the frame graph up front for hazard tracking, memory aliasing and synchronization between queues. Systems supply "scopes" through a `ScopeProducer` with three steps: declare dependencies, compile resources and build the command list. — [O3DE frame scheduler (prerelease docs)](https://development--o3deorg.netlify.app/docs/atom-guide/dev-guide/rhi/frame-scheduler); [ScopeProducer API](https://docs.o3de.org/docs/api/gems/atom/class_a_z_1_1_r_h_i_1_1_scope_producer)
- **Gems insert their own passes into the default pipeline** through a mapping of pass templates loaded from assets, for example LyShine (UI), AtomHair and Terrain. — [O3DE wiki: Work With Passes In Gems](https://github.com/o3de/o3de/wiki/%5BAtom%5D-Work-With-Passes-In-Gems) (the wiki may be outdated)

**Flax Engine**
- Supports C#, C++ and visual scripting. The engine is in C++, the editor in C#. Hot reload of C# and C++ in the editor, visual scripts are a binary asset with a graph and reload without compilation. The build of the engine and the game is driven by its own tool, Flax.Build. — [Flax docs: Scripting](https://docs.flaxengine.com/manual/scripting/index.html); [C++ Scripting](https://docs.flaxengine.com/manual/scripting/cpp/index.html); [Visual Scripting](https://docs.flaxengine.com/manual/scripting/visual/index.html)

**Veloren (Rust, voxel open world)**
- The project is split into crates: frontends `voxygen` (3D client) and `server-cli`, backends `server`, `client` and `world`, utilities `common` and `network`, and plugins `plugin-rt`, `plugin-api` and `plugin-derive`. Frontends are a "first-class abstraction". — [Veloren book: Codebase structure](https://book.veloren.net/contributors/developers/codebase-structure.html)
- The `world` crate is "the core world generation implementation" and is designed so that the world can be generated and simulated **without a client or a server**. — [Veloren book](https://book.veloren.net/contributors/developers/codebase-structure.html)
- Singleplayer starts a local server in the background and the client connects to it. Shared ECS components (specs) are in `common`. — secondary sources: [rustutils](https://rustutils.com/tools/veloren/), [DeepWiki](https://deepwiki.com/veloren/veloren) (I did not read the official chapter on ECS)

**Luanti (Minetest, C++ + Lua)**
- Singleplayer starts a server limited to one player in the background and the client connects to it, so the game is both client and server. The engine has a client-server architecture for both single- and multiplayer. — [Luanti wiki: Terminology](https://wiki.luanti.org/Terminology); [Luanti docs glossary](https://docs.luanti.org/about/glossary/)
- Mods are in Lua and "run solely on the server side". Definitions and media are sent to clients automatically. The client-side Lua API is experimental. — [Luanti Lua API](https://api.luanti.org)

**Minecraft Java (retrofit)**
- In version 1.3 (2012) Mojang "kicked out single-player, and made it a shell on top of multi-player". Snapshot 12w18a was the first in which singleplayer ran on a local server, "because server and client logic were separated". — [Minecraft Wiki: 1.3.1 development versions](https://minecraft.wiki/w/Java_Edition_1.3.1/Development_versions); [Tom's Hardware](https://www.tomshardware.com/uk/news/Minecraft-Mojang-PC-Gaming-Block-Building-Notch,16214.html)

**Vintage Story (C#)**
- Code mods are C# against `VintagestoryAPI.dll`. The wiki covers blocks, items, block entities, world access, networking, commands, GUI, world generation and monkey-patching through Harmony. Hot reload in Visual Studio works only for "compiled" mods. — [VS wiki: Code Mods](https://wiki.vintagestory.at/index.php/Modding:Code_Mods); [Mod Types](https://wiki.vintagestory.at/index.php/Modding:Mod_Types)
- The guide advises not to keep static references to game objects, because they can hold the whole world in memory. — [VS wiki: Modding Efficiently](https://wiki.vintagestory.at/index.php/Modding_Efficiently)

### Inferences
- **Godot confirms our foundation.** Isolated subsystems with opaque handles, above which you can go directly, are the same as our `render`/`phys`/`audio` with handles. But Godot adds the **scene tree as a general composition for the game user**. We have only `eng_api` with `world.spawn/despawn`. For D15 the layer "how a game composes its objects" is missing, and every game would otherwise write it again.
- **Wicked is the best "ECS-light" model for a one-author C engine.** A typed manager with dense arrays, an entity as a number, no generic scheduler and no queries over archetypes, plus **versioned, skippable serialization by type name**. It is basically Bitsquid's data manager owned by a system, which we already recommend, plus a type registry. That registry is exactly what our design forbids ("global reflection is not built") and what is needed for save, editor and network.
- **The Unreal proxy and Bevy extraction solve the same thing as our FrameParams + `render_world_add_instances()`**, but each defines an explicit life cycle. In Unreal it is a persistent proxy, a dirty flag and messages. In Bevy it is a persistent resource and per-frame entities that are thrown away every frame. Our design has both channels (persistent cell instances through runtime and dynamic transforms through FrameParams), but **it does not describe the rules**: who may read what, how a change of material or visibility of a static instance propagates, and when memory that render-prep points to may be freed. Without that, pipelining in M7 breaks.
- **Doom Eternal shows that "no main thread" is an achievable end state.** For us SDL holds this back (the swapchain on the window thread, a command buffer tied to a thread), so a single submit thread is forced. What we can take is a "pre-built frame job graph": the same list of jobs every frame is easier to tune and profile than ad hoc spawns.
- **O3DE and The Machinery let modules and plugins insert passes into the render graph.** For D15 this is essential. A planet needs atmosphere, aerial scattering and distant terrain, a city needs different passes. Our render graph is designed as an internal matter of `render` and lacks an extension point.
- **Veloren is the closest analogy to our whole stack**: an open world with procedural generation, a `world` crate independent of both client and server (= our pure `gen_*`), a client and server separated from the start, a plugin API. It differs in having a network boundary from the start.

### Gaps
- I did not read the Wicked Engine graphics device abstraction (`wiGraphicsDevice.h`) or the job system (`wiJobSystem`) in this session. Their comparison with our RHI and job system is not verified. Our first report cites the Wicked job system (blog 2018).
- I did not verify in detail the Godot RenderingDevice and the rendering server thread (`RenderingServerDefault`, command queue).
- Unreal World Partition is described in our first report. I did not read new sources on it.
- I found neither the GDC 2019 talk "First Light – Bringing DOOM to Stadia" nor any primary presentation on the idTech 7 job system. The figure of ~100 jobs comes from a tweet relayed by a search engine.
- I did not read the official Veloren chapter on ECS and on singleplayer. The local server claim comes from secondary sources.
- I did not re-read Gregory's Game Engine Architecture (the chapter on the runtime object model and world chunks) in this session; only the first report cites it, via an excerpt.

## 2. Concrete holes in our design (editor, scripting, data, save, network, audio, UI, hot reload, profiling, crash reporting, extraction)

### Takeaway
The most serious holes for a "general engine" are three. (1) **There is no separation of simulation from presentation as client/server**, although Minecraft shows that adding it later means rewriting the game loop. (2) **There is no data model with a schema and versions** for recipes, cell diffs and save, from which an inspector, undo and migrations would follow. (3) **There is no extension mechanism** (plugins or Gems) for features and passes. Scripting (Lua and the like) and the editor are less urgent if `eng_api` is designed from the start as a stable C ABI.

### Cited Findings
- **Network / server-authoritative:** In 2012 Minecraft turned singleplayer into "a shell on top of multi-player", which required separating server and client logic. Tom's Hardware gives the cost: even in solo the game both simulates and emulates the world. — [Minecraft Wiki](https://minecraft.wiki/w/Java_Edition_1.3.1/Development_versions); [Tom's Hardware](https://www.tomshardware.com/uk/news/Minecraft-Mojang-PC-Gaming-Block-Building-Notch,16214.html)
- Luanti and Veloren both run singleplayer as a local server from the start. Luanti mods live only on the server. — [Luanti wiki](https://wiki.luanti.org/Terminology); [Luanti API](https://api.luanti.org); [Veloren book](https://book.veloren.net/contributors/developers/codebase-structure.html)
- The Machinery treats multiplayer as a "bonus" requirement of the save system. Tracking changes per member means that "only the actual member that changed will be sent across the network (instead of the full struct)". — [Our Machinery: One-Click Save Game System pt.1 (21 Jun 2021)](https://ruby0x1.github.io/machinery_blog_archive/post/save-game-system-part-1/)
- **Save system:** In The Machinery the Gamestate mirrors the live state of the application and records changes of persistent objects. A save is the serialization of these changes. Every persistent object needs a unique ID and references go through persistent IDs. The game decides when to push changes, and it is enough that they are pushed at the moment of saving. Part 1 does not deal with format versioning. — [Save Game pt.1](https://ruby0x1.github.io/machinery_blog_archive/post/save-game-system-part-1/)
- Wicked handles versions per component type (`ComponentLibrary`, `GetVersion()`) and skips unknown types by jump offset. — [wiECS.h](https://raw.githubusercontent.com/turanszkij/WickedEngine/master/WickedEngine/wiECS.h)
- **Data model / editor:** The Truth gives undo, copy/paste, collaboration and version compatibility "from the data model". It also lists open problems: runtime data generation, partial loading of large projects and a git-friendly on-disk representation. — [The Truth](https://ruby0x1.github.io/machinery_blog_archive/post/the-story-behind-the-truth-designing-a-data-model/)
- **Scripting and modding:** Luanti uses Lua on the server only. Vintage Story uses C# code mods plus Harmony patching and, according to the wiki, also JSON content mods (mod types). Flax has C#, C++ and visual scripts with hot reload. Godot GDScript is the first language (generally known, not verified here). — [Luanti API](https://api.luanti.org); [VS Mod Types](https://wiki.vintagestory.at/index.php/Modding:Mod_Types); [Flax Scripting](https://docs.flaxengine.com/manual/scripting/index.html)
- Veloren has its own plugin API (`plugin-api`, `plugin-rt`) separate from the engine. — [Veloren book](https://book.veloren.net/contributors/developers/codebase-structure.html)
- **DLL hot reload is painful:** our first report cites Machinery (patching function pointers, a silent crash when a signature changes, API versioning later). Vintage Story has hot reload for only one type of mod. — [Machinery: DLL Hot Reloading](https://ruby0x1.github.io/machinery_blog_archive/post/dll-hot-reloading-in-theory-and-practice/); [VS Code Mods](https://wiki.vintagestory.at/index.php/Modding:Code_Mods)
- **Render extraction:** Bevy deletes render entities every frame and keeps persistent data in resources. Unreal keeps a persistent proxy, propagates changes through `MarkRenderStateDirty()` and copies dynamic data into allocations owned by the render thread. Deletion waits for a fence. — [Bevy cheatbook](https://bevy-cheatbook.github.io/gpu/intro.html); [Epic: Rendering thread](https://dev.epicgames.com/documentation/en-us/unreal-engine/threaded-rendering-in-unreal-engine)
- **UI in the engine:** O3DE ships the game UI (LyShine) as a Gem that inserts its own passes. — [O3DE wiki](https://github.com/o3de/o3de/wiki/%5BAtom%5D-Work-With-Passes-In-Gems)

### Inferences
Assessment of each hole (state in our design → recommendation):

1. **Client/server split (network).** State: nothing. `game_fixed_update(mem, input, dt)` is a singleplayer loop and input goes straight into the game. Recommendation: **not** network code from day one, but **yes** the shape. (a) Game state and simulation (`world` + game) must not depend on `render`, `audio` or the camera. This already partly holds thanks to the rule "neighbors do not link to each other". (b) The input to the simulation is **player commands** (`player_cmd` with a player ID and a tick), not raw SDL input. The same channel then serves replay, network and AI. (c) A headless `server` target (null GPU + null audio) is almost free thanks to the planned null adapters, it is enough to keep it in CI from M5. (d) Streaming strategies count on **multiple streaming sources** (several players). UE World Partition has it, our design mentions only a second predictive source. Minecraft shows that separating later is expensive. Veloren and Luanti show that an open world with a generator in this shape can be built from the start. For D15 (a planet à la Light No Fire, where multiplayer can be expected) it is the cheapest insurance.
2. **Data model + schema + versions.** State: recipes are a "simple key-value format", cell diffs are loosely described, save is `save()/load()` per system after Bitsquid with no mention of versions. Recommendation: **a small type registry** (name, version, a list of fields with types and offsets), not the full The Truth. From it derive: (a) a chunked save and diff format in the style of Wicked `[name, version, size, data]` with skipping of unknown chunks, (b) migration of recipes when the generator version changes, (c) an automatic inspector in the debug UI, (d) future per-field replication as in Machinery. Bitsquid's "no global reflection" makes sense for the internal data of systems, not for **persistent and editable data at the engine boundary**. There every compared general engine needs reflection (Godot, Unreal, O3DE, Flax, Machinery).
3. **Extension mechanism (plugins/Gems).** State: the `runtime` mediator is a hand-written composition root with a static registry, a dynamic registry is deferred. Risk for D15: every new feature (planet, atmosphere, vegetation, water, UI) will add lines to `runtime/init.c` and `frame.c`, and the mediator turns into a god object. Recommendation: **a declarative module description** (`eng_module_desc`: name, dependencies, `init/shutdown`, hooks into named frame phases, registration of passes in the render graph and of asset handlers and providers), linked statically. The mediator then walks the table. It is Machinery's "load_xxx(reg)" without DLLs and an O3DE Gem without Gem tooling. The render graph gets an extension point "a module registers a pass into a named pipeline slot" after the O3DE and Machinery model.
4. **Scripting and modding.** State: the game is a C DLL with hot reload. Assessment: for our workflow (code is written by Claude, the owner is the art director) a C DLL is better than Lua. It is faster, typed, debuggable and shares determinism. But for a *general* engine with a modding community a native DLL cannot be sandboxed and is ABI-fragile, as both Machinery and Harmony patching in VS show. Recommendation: **do not add a scripting language now**. But design `eng_api` as a stable, versioned C ABI with POD types and no callbacks into internal structures, so that a Lua or Wren adapter can be added later as another driving port, similar to Luanti (server side only). Data mods (recipes in `content/`) are already a modding surface comparable to JSON mods in VS and are worth documenting as such.
5. **Editor / inspector / runtime debug.** State: `eng_debug_api` is mentioned, the editor "in parallel from M5", nothing else. Recommendation: in M1–M2 add an **immediate-mode debug UI** (an inspector over the type registry from point 2, visualization of cells, streaming state, frame graph dump, job timeline). A full editor is not needed, because content comes from recipes and generators and the "editor" is mainly the review render and live editing of a recipe. From the Machinery design the only thing worth taking is the idea that undo and recipe hot reload are operations on data, not on files.
6. **Render extraction vs FrameParams.** State: we have the concept (FrameParams after Gyrling, `render_world_add_instances()` on cell activation, POD packets). But the explicit protocol is missing. Recommendation: write down three channels after Unreal and Bevy. (a) **Persistent render instances** (cell statics) are created and destroyed by a command through runtime and are freed only after the GPU fence. (b) **Dirty updates** for a change of state of a persistent instance (material, visibility, breakage) are a command queue, not a direct write. (c) **Per-frame extract** for dynamic actors (transforms, poses) into an arena tagged with the frame number, which is thrown away whole as in Bevy. Plus the Unreal rule: render-prep never dereferences a simulation handle, only a copy. This makes the pipelining sim N+1 ‖ render-prep N in M7 a switch-on, not a refactor.
7. **Audio and UI.** Audio has a port (`eng_audio`) but no defined model (voices, bus, 3D emitters, music streaming). Game UI (HUD, menus, text, localization, fonts) is **not in the design at all**, although O3DE ships it as a separate Gem with its own passes. For a general engine it is a mandatory item and belongs in the milestone plan.
8. **Profiling and crash reporting.** State: `profile.h` hooks in `core`, `gpu_timer` is a no-op. Recommendation: design the hooks so that they can be attached to an external profiler (zones, naming of threads and jobs, allocations). Crash reporting (minidump/symbolization on 3 OSes) is missing from the design. But for solo development a handler is worth having that at least writes the log, the seed, the build version and the last N frames of replay input. Deterministic replay is our biggest debugging trump and the crash dump should refer to it.
9. **Asset hot reload.** Shaders, the gen DLL and recipes have hot reload planned. Hot reload of *cooked* assets works automatically through the refcount graph and cache invalidation. Fine.

### Gaps
- I did not collect sources for Tracy, Superluminal, Sentry or Crashpad in this session. The concrete choice of a profiler and crash reporter needs to be verified (C API, license, macOS ARM64).
- I did not read parts 2 and 3 of the Machinery save system series (versioning, ECS integration).
- I found no source that quantifies the cost of the client/server retrofit in Minecraft (number of months, regression bugs). Only the fact and the qualitative impact are documented.
- Whether Light No Fire will be multiplayer is not verified here.

## 3. "No ECS" vs ECS for a general engine (D15)

### Takeaway
Rejecting a *generic ECS framework with its own scheduler* in the core is defensible. Godot is a general engine without ECS and recommends going straight to servers for bulk processing, which is exactly our model. The problem is elsewhere: **above archetypes, instances and handles we have no general model of composing game objects**, and every compared general engine has one (Godot nodes, Unreal actors and components, O3DE and Machinery and Bevy and Veloren ECS, Wicked ComponentManager). Without it, future games will build their own object model on top of `eng_api`, and each differently.

### Cited Findings
- Godot: "Godot does composition at a higher level than in a traditional ECS." Composition through a node hierarchy. For performance-critical cases it recommends servers directly or a third-party ECS. — [Godot blog, 26 Feb 2021](https://godotengine.org/article/why-isnt-godot-ecs-based-game-engine/)
- Wicked: a per-type `ComponentManager<T>` with dense arrays and a `uint64` entity, no generic queries across several components. Systems iterate the array of one manager and look up other components through lookup. — [wiECS.h](https://raw.githubusercontent.com/turanszkij/WickedEngine/master/WickedEngine/wiECS.h)
- The Machinery: ECS as a plugin, an editor built around the ECS and a renderer that reads component data through plugin interfaces. — [Machinery: ECS and Rendering](https://ruby0x1.github.io/machinery_blog_archive/post/ecs-and-rendering/)
- Bevy: ECS is also in the renderer (Render World), extraction copies between two ECS worlds. — [Bevy cheatbook](https://bevy-cheatbook.github.io/gpu/intro.html)
- Veloren: ECS components shared by client and server in `common` (secondary source). — [rustutils](https://rustutils.com/tools/veloren/); [Veloren book](https://book.veloren.net/contributors/developers/codebase-structure.html)
- Our own arguments against ECS (first report): the flecs scheduler overlaps with our job system and spatial structures do not live in an ECS, as the ECS FAQ also says. — [ECS FAQ](https://github.com/SanderMertens/ecs-faq); [flecs](https://github.com/SanderMertens/flecs)

### Inferences
- **Where we are right:** static instances (tens of thousands per cell, released at once) should not be entities in any engine. Even Unreal holds them as instanced data and Godot recommends servers. Spatial and streaming must be owned by `world`. This holds unchanged.
- **Where this makes future games harder:** (1) Gameplay objects such as an NPC, a mount, a fortress or a quest item want a composition of properties (health, inventory, AI, interaction). Today it is "a pool of actors with a fat header + an array of states", but adding a new kind of state means changing the engine, not the game. (2) Save, network and the inspector need to walk an object's components uniformly, which requires a type registry (see section 2). (3) Modding needs to add new components without recompiling the engine.
- **Recommendation (a middle way, not flecs):** for **dynamic actors** introduce a Wicked-style layer: `eng_entity` (the generational handle we already have), a **component type registry** (name, version, size, field description, save/load/replicate callbacks) and a **single-type component manager with a dense array** after Bitsquid, owned by a system or the game. The game (DLL) may register its own component types. Do not add generic multi-component queries or a scheduler of our own, systems are ordinary jobs. Static instances stay SoA in cells. The result resembles Wicked and Bitsquid, not Bevy, and keeps all our arguments against ECS. At the same time it removes the biggest drawback of "no ECS" for a general engine.
- The variant "flecs only in `game`" (the first report allows it) is worse. Save, network and the inspector would then live in the game DLL and every game would solve them again, which goes against D15.

### Gaps
- I found no primary source with a quantitative comparison of ECS vs. non-ECS productivity for a one-developer team. Arguments on both sides are qualitative (Godot blog, ECS FAQ).
- I saw the concrete handling of parent-child relationships (transform hierarchies) in Wicked (`MoveItem` for ordering) only in the API, not in a usage description.

## 4. Abstraction of world shape (flat grid vs cube-sphere), in brief

### Takeaway
None of the compared general engines (Godot, Unreal World Partition, O3DE, Bevy, Flax) **has world shape as a replaceable port**. World Partition is a 2D grid, and Veloren and Luanti have flat worlds. A port for world shape according to D15 is therefore our own innovation with no model in an open-source engine and should be as narrow as possible.

### Cited Findings
- UE5 World Partition uses a 2D runtime grid of cells and multiple streaming sources (cited in our first report). — [UE World Partition](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition-in-unreal-engine)
- The Veloren `world` crate generates and simulates the world separately from both client and server. It is a model for separating the generator from the topology. — [Veloren book](https://book.veloren.net/contributors/developers/codebase-structure.html)

### Inferences
- The port should abstract only the **cell key and its neighbors, the conversion key ↔ local frame (origin, "up" basis) and the selection of cells for a streaming source**. A flat grid has the key `(x, y, lod)`, a cube-sphere `(face, x, y, lod)` or a quadtree node. The other modules (`gen_world`, strategies, cell+float coordinates, physics gravity) work in the local frame of the cell. Our coordinate design `int32 cell_x, cell_y + float offset` is, however, specific to a flat grid and must be generalized to `cell_key + a local float3 within the cell`. **This must be decided before M4**, because it leaks into the `cell_blob` format, into the IDs of generated entities `hash(level, coordinates, …)` and into save files.
- The detail (cube-sphere, octree, gravity) is covered by another researcher.

### Gaps
- In this session I did not collect sources on how planetary engines (Outerra, Space Engineers, Kerbal, No Man's Sky) abstract topology. Another researcher covers it.

## Summary of proposals (for the report writer, ordered by priority)

1. **Simulation shaped as a server from the start** (player commands instead of raw input, a headless server target in CI, multiple streaming sources). Cheap now, expensive later (Minecraft 1.3).
2. **A type registry + versioned chunked serialization** (Wicked `ComponentLibrary`) as the basis for save, cell diffs, recipe migrations, the inspector and future replication. Revise the rule "no global reflection": it holds inside systems, not at the persistent boundary.
3. **Wicked/Bitsquid-style components for dynamic actors**, which the game may also register. No flecs and no scheduler.
4. **An explicit extraction protocol** (persistent render instances + a dirty queue + a per-frame arena, deletion after the fence), taken from the Unreal proxy and Bevy extraction, written down before M5 so that pipelining in M7 is just a switch-on.
5. **A declarative module description and an extension point in the render graph** (O3DE Gems and passes, Machinery plugins), so that the `runtime` mediator does not grow with every feature for D15.
6. **A stable, versioned C ABI `eng_api`**, so that a scripting adapter can be added later (Lua as in Luanti, server side only). No scripting language now.
7. **Add game UI, debug UI and an inspector to the milestones, a crash handler linked to replay, and profiler hooks** compatible with an external profiler.
8. **A pre-built frame job graph** (Doom Eternal) instead of ad hoc spawns, for debugging and profiling.
9. **Generalize the coordinates `cell_x, cell_y + float` to `cell_key + a local frame`** and decide it before M4 (D15).
