# Destruction of procedurally generated geometry, and how to make it deterministic

Context: Wallhammer Zero (C17, SDL_GPU without bindless, Jolt with `CROSS_PLATFORM_DETERMINISTIC`, tier A generators bit-identical on macOS-ARM64/Linux-x64/Windows-x64 with `detmath`, no `<math.h>`, `-ffp-contract=off`, integer/fixed-point simulation logic, seeded named RNG streams; Manifold is already planned in `eng_gen_mesh` with `PAR=OFF` for cutouts). Research date 2026-11-06. Source strength is flagged per item: **[primary]** = paper, official docs, source repo; **[secondary]** = press or third-party write-up; **[weak]** = forum or speculation.

Note on coverage: about 25 tool calls were used. ## 1. Pre-fracture vs runtime fracture: methods, cost, robustness, libraries, licences

### Takeaway
Shipped games overwhelmingly pre-fracture (offline Voronoi/slicing into chunks + a bond graph) and only choose *which* bonds break at runtime; true runtime geometric fracture exists in research (VACD, fracture modes) but costs milliseconds per event and depends on robust booleans. For a code-generated world the "pre-fracture" step can run inside the generator at stream/cook time, so the trade-off becomes "fracture at generation time (tier A, cached) vs fracture at impact time".

### Cited Findings
- NVIDIA Blast's authoring extension (`NvBlastExtAuthoring`) offers a FractureTool with three modes: Voronoi fracturing, slicing, and "cutout" fracture (slicing driven by an image); its Voronoi site generator must be given the fracture mesh because sites must not be generated outside it **[primary]** — [Blast Asset Authoring docs](https://nvidia-omniverse.github.io/PhysX/blast/docs/api/extensions/ext_authoring.html)
- Blast's fracture tool relies on a boolean algorithm; input meshes "should be closed, without self-intersections or T-junctions", otherwise results are "unpredictable". It ships a MeshCleaner to remove self-intersections and open edges, a ConvexMeshBuilder for collision hulls, and a BondGenerator with an "exact" interface mode and an "Average" mode for chunks that interpenetrate (e.g. noisy cut surfaces) **[primary]** — [Blast Asset Authoring docs](https://nvidia-omniverse.github.io/PhysX/blast/docs/api/extensions/ext_authoring.html)
- Blast (in the NVIDIA-Omniverse/PhysX repo) is licensed BSD-3-Clause **[primary]** — [GitHub licence API for NVIDIA-Omniverse/PhysX](https://github.com/NVIDIA-Omniverse/PhysX); its README documents build scripts only for Windows (`build.bat`) and Linux (`build.sh`), no macOS **[primary]** — [Blast README](https://github.com/NVIDIA-Omniverse/PhysX/tree/main/blast)
- Müller, Chentanez, Kim, "Real Time Dynamic Fracture with Volumetric Approximate Convex Decompositions", ACM TOG 32(4) art. 115, SIGGRAPH 2013 (DOI 10.1145/2461912.2461934): visual meshes are represented as a volumetric approximate convex decomposition (VACD); artist-made *generic* fracture patterns are aligned to the impact point and intersected with the convex pieces; supports *partial* fracture at multiple locations; contributes a VACD algorithm, an approximate convex hull construction, and island detection after partial destruction to determine support structures **[secondary summary of primary]** — [SIGGRAPH history archive](https://history.siggraph.org/?p=108389); [3DVF summary](https://3dvf.com/actualite-6536-siggraph-2013-fracturation-dynamique-temps-reel-nvidia-html/)
- Sellán, Luong, Mattos Da Silva, Ramakrishnan, Yang, Jacobson, "Breaking Good: Fracture Modes for Realtime Destruction", ACM TOG 2022 (SIGGRAPH Asia): defines "fracture modes" by analogy with vibration modes, solved as a sparsified eigenvalue problem for the n lowest-energy modes; modes are precomputed into prefracture patterns and at runtime any impact is *projected onto the modes* to give an impact-dependent pattern "without online crack propagation simulation" **[primary]** — [arXiv 2111.05249](https://arxiv.org/abs/2111.05249); [project page](https://www.dgp.toronto.edu/projects/breaking-good/)
- A TUM seminar review of Breaking Good notes that in 3D the precomputation needs a tetrahedral mesh, while realtime applications prefer triangle meshes for input/output **[secondary]** — [TUM report](https://cvg.cit.tum.de/_media/teaching/ws2022/3dcv/material/report_kurupakuluvenkat_nikhita.pdf)
- Older quasi-static runtime fracture (Müller, McMillan, Dorsey, Jagnow, "Real-Time Simulation of Deformation and Fracture of Stiff Materials", Eurographics CAS 2001): static FEM analysis only at the instant of impact, fracture plane perpendicular to the max-tensile-stress eigenvector, disconnected parts become rigid bodies; static analysis took 10–80 ms for 1000–4000 tetrahedra on a dual 400 MHz SGI Octane 2, rigid body integration 10–20 ms/step; the authors list as a limitation that only behaviour at the instant of contact is considered **[primary]** — [Müller et al. 2001 PDF](https://matthias-research.github.io/pages/publications/fracture.pdf)
- Manifold (elalish/manifold): primary goal "guaranteed manifold output without caveats or edge cases", secondary goal performance; the author calls a mesh boolean robust to edge cases "an open problem for many years" and believes Manifold's is the first; it **requires manifold input** (error status otherwise; a `Merge` function fixes slightly non-manifold meshes); it includes a level-set function for SDFs that "improves significantly over Marching Cubes"; parallelism via TBB is optional and small problems fall back to serial; polygon triangulation is serial; C bindings (`manifoldc`) exist **[primary]** — [Manifold README](https://github.com/elalish/manifold); licence Apache-2.0 **[primary]** — [manifold-3d npm](https://npmjs.com/package/manifold-3d)
- Manifold's speed claims ("dramatically faster" than OpenSCAD) come from its own README, not independent benchmarks **[primary but self-reported]** — [Manifold README](https://github.com/elalish/manifold)
- Voro++ (Chris Rycroft, LBNL) computes each Voronoi cell individually (cell-based) rather than a global vertex/edge network **[primary]** — [voro GitHub](https://github.com/chr1shr/voro); its LICENSE is a BSD-style licence ("Redistribution and use in source and binary forms, with or without modification, are permitted…", Copyright 2008 Regents of the University of California / LBNL) **[primary]** — [Voro++ LICENSE](https://raw.githubusercontent.com/chr1shr/voro/master/LICENSE)
- Jolt has no fracture feature in its architecture docs. Relevant building blocks: `StaticCompoundShape` (built once, children in a tree) vs `MutableCompoundShape` ("can be constructed/changed at runtime and trades construction time for runtime performance", children in a list); removing a child invalidates previously obtained `SubShapeID`s for that compound; `ConvexHullShape` built from points with a convex radius (0 allowed; larger = faster but less accurate) **[primary]** — [Jolt Architecture.md](https://github.com/jrouwe/JoltPhysics/blob/master/Docs/Architecture.md); [Jolt docs](https://jrouwe.github.io/JoltPhysics/)
- Teardown avoids the mesh problem entirely: objects are voxel volumes on a regular grid, rendered by GPU ray marching through voxel volumes (no triangles), with voxel-specific SIMD/multithreaded collision; Gustafsson says dynamic destruction is "incredibly hard" in traditional games "primarily because the objects are only represented as surfaces" **[secondary interview]** — [80.lv interview](https://80.lv/articles/teardown-developer-breaks-down-multiplayer-and-voxel-destruction-tech)
- Teardown's larger levels are about half a billion voxels; storing every voxel's properties would push saves past half a gigabyte **[secondary, quoting the dev blog]** — [PCGH](https://www.pcgameshardware.de/Teardown-Spiel-73677/Specials/PC-Game-Test-Benchmark-Voxel-Dynamic-Destruction-1394545/2/)
- Rainbow Six Siege's RealBlast is described by Ubisoft as a "procedurally generated" destruction system; raycasts from the blast determine damage and destruction ranges; L'Heureux says destruction is material-based and built from procedural and prefragmented tools **[primary-ish: Ubisoft blog/interview]** — [Ubisoft news](https://www.ubisoft.com/en-us/game/rainbow-six/siege/news-updates/1QkezaGoRkDWqcQ6duGvtk); [Ubisoft interview with L'Heureux](https://news.ubisoft.com/en-us/article/4GHX2yepSaKkflLjLAlpwO/the-art-of-destruction-in-rainbow-six-siege-an-interview-with-julien-lheureux); GDC 2016 talk "The Art of Destruction in Rainbow Six: Siege" — [GDC Vault](https://gdcvault.com/play/1023307/contactUs)
- Control (Remedy, GDC Summer 2020, Johannes Richter, "Destructible Environments in Control: Lessons in Procedural Destruction") used a Houdini-based procedural pipeline; per a secondhand write-up each material has its own fracture geometry at several levels, Northlight runs destruction logic and NVIDIA physics simulates rigid bodies **[secondary]** — [GDC Vault](https://gdcvault.com/play/1030643/Destructible-Environments-in-Control-Lessons); [80.lv summary](https://80.lv/articles/gdc-talk-destructible-environments-in-control)

### Inferences
- **Method choice for WHZ.** Generated buildings are already a set of parts with known semantics (CGA scopes, kit pieces, WFC tiles). The cheapest robust option is *hierarchical pre-fracture inside the generator*: level 0 = the part itself (wall panel, slab, column, beam), level 1 = a seeded Voronoi or slicing pattern of that part, generated lazily the first time the part is damaged (or at cook time for hero assets). This avoids runtime booleans on arbitrary meshes.
- **Convex-first geometry avoids booleans.** Most kit parts are boxes or extrusions. Clipping a convex polyhedron by the half-spaces of a Voronoi cell is only plane clipping (add/sub/mul/div, no transcendental functions), which is bit-reproducible under the tier A rules if done in fixed-point or in IEEE floats with `-ffp-contract=off` and a fixed operation order. A cell-based approach (Voro++ style: each cell = initial convex box clipped by bisector planes of neighbours) maps naturally onto this; own C implementation is preferable to linking Voro++ (C++, double, not tier A audited) even though its BSD-style licence is permissive.
- **Non-convex parts** (wall with window opening, arch, SDF rock) can be handled as unions of convex pieces emitted by the generator itself (the CGA split already produces convex sub-scopes around openings), i.e. a "free" VACD in the Müller 2013 sense, instead of running V-HACD/CoACD on the final mesh.
- **Manifold** fits as a cook-time / tier A tool for genuinely non-convex cuts (Apache-2.0, C API, serial when `PAR=OFF`). Its "manifold input required" rule means generator output must be watertight before fracture; half-edge meshes from the grammar should be validated for that anyway.
- **SDF and voxels** are the right tool for organic rocks and terrain (fracture = subtract a seeded noise-displaced SDF and re-mesh with Manifold's level set or the existing mesher) but not for crisp architecture; Teardown-style voxel-everything is a different renderer and is out of scope given D5 (no bindless) and the triangle pipeline.
- **Blast** is useful as a reference design (chunk hierarchy + support graph + bonds + stress solver) rather than as a dependency: BSD-3 is fine, but it is C++, ships no macOS build scripts, and makes no determinism claims.

### Gaps
- No measured numbers found this session for per-fracture runtime cost of VACD (Müller 2013) — the paper PDF could not be retrieved; the often-quoted figures need checking in the paper.
- No independent benchmark of Manifold boolean timings on small game meshes (≈1–10k triangles); no statement found on whether Manifold's output is bit-identical across platforms/compilers (the planned `PAR=OFF` helps ordering but floating-point and its internal epsilon handling were not verified).
- CGAL licence (GPL/LGPL with commercial option from GeometryFactory) was not re-verified this session; treat CGAL as unsuitable for a closed engine until checked at [cgal.org/license](https://www.cgal.org/license.html).
- V-HACD / CoACD licences and timings not verified this session.

## 2. How a procedural building generator can emit destruction data "for free"

### Takeaway
Everything a destruction system needs — chunks, a support graph with bond areas, anchoring to the ground, material per chunk, damage levels — is exactly what Blast-style authoring tools try to *reconstruct* from meshes, and what a split grammar already *knows* at generation time. The generator should emit a destruction description alongside the render mesh.

### Cited Findings
- Blast's data model: chunks connected by bonds forming a support graph; each node needs mass, volume and position (can be filled from chunk data with a density); nodes representing the world are static **[primary]** — [Blast Stress Solver docs](https://nvidia-omniverse.github.io/PhysX/blast/docs/api/extensions/ext_stress.html)
- Bonds in Blast authoring are generated from geometry either by exact interface computation or by an "Average" approximation; a dedicated path (`buildDescFromInternalFracture`) exists because the fracture tool *knows* the interfaces it created **[primary]** — [Blast Asset Authoring docs](https://nvidia-omniverse.github.io/PhysX/blast/docs/api/extensions/ext_authoring.html)
- Blast external bonds (to non-destructible geometry) can be made permanent, so they never break **[primary]** — [Omniverse Blast Destruction extension](https://docs.omniverse.nvidia.com/app_code/prod_extensions/ext_blast.html)
- Control's pipeline assigned fracture geometry per material, with several levels **[secondary]** — [80.lv](https://80.lv/articles/gdc-talk-destructible-environments-in-control)
- Rainbow Six Siege destruction is material-driven; materials must react "logically and consistently to different stimuli" **[primary interview]** — [Ubisoft interview](https://news.ubisoft.com/en-us/article/4GHX2yepSaKkflLjLAlpwO/the-art-of-destruction-in-rainbow-six-siege-an-interview-with-julien-lheureux)
- Red Faction Guerrilla (Geo-Mod 2.0): knocking out enough support struts makes a building collapse under its own weight; designers had to act as structural engineers so structures would not crumble when placed **[secondary press/interviews]** — [Gamewatcher](https://www.gamewatcher.com/2009-24-03-volition-five-to-ten-years-ahead-of-everyone-with-red-faction); [CBS News Q&A](https://www.cbsnews.com/news/red-faction-guerrilla-q-a); [Red Faction Wiki](https://www.redfactionwiki.com/wiki/GeoMod_2.0) **[weak]**

### Inferences
Proposed generator output (a `destruct_desc` produced by `eng_gen_arch` next to the mesh, tier A, hashable, part of the Merkle cache key):
- **Nodes = grammar terminals / kit parts**, each with stable `uid64` derived from (building uid, grammar path / scope index). Fields: material id, mass (volume × density, fixed-point), centroid, convex pieces (already known from scope boxes), damage-state count, "is anchor" flag (touching terrain/foundation).
- **Bonds = shared faces between adjacent scopes**, known exactly from the split (a split along an axis creates a shared rectangle). Store contact area and normal (axis) — the inputs a stress solver needs for compression/tension/shear limits. This replaces Blast's geometric bond generator and its "Average" mode.
- **Load paths**: the grammar knows the role of each part (column, beam, slab, infill wall, facade ornament). Roles give default bond strengths and which bonds carry vertical load; infill/ornament can be marked "non-structural" so their removal never triggers collapse.
- **Damage states per part**: e.g. 0 intact, 1 cracked (shader mask only), 2 holed (part replaced by a sub-grammar evaluation with an opening at the impact cell — the CGA rule that makes window openings can make a breach), 3 fractured (seeded Voronoi of the part), 4 gone. State 2 is a cheap "procedural breach" that reuses the opening machinery instead of booleans.
- **Interior reveal**: because interiors are also grammar products, the generator can emit the "back face" content of each wall (room behind it, floor slab edge) only when a part reaches state ≥2, at the cost of one regeneration of that cell; it does not need to be resident beforehand.
- **Cut faces and caps**: for convex-clipped chunks the cap polygons are produced by the clipper itself; tag them with the part's *interior material* (brick core, concrete with rebar, wood grain) chosen by the recipe, and give them triplanar or box-projected UVs so no UV unwrap is needed at runtime.
- **Material per fracture face**: Voronoi site density and pattern type per material (glass = radial + concentric, concrete = Voronoi with clustered sites near impact, wood = slicing along grain axis, brick = cells snapped to the brick grid emitted by the facade generator).

### Gaps
- No published source found that describes a CGA/split-grammar system emitting a structural graph for destruction ("fracture from procedural models" search produced nothing specific). This appears to be an open design space; flag as original design rather than established practice.
- Red Faction Guerrilla's actual stress algorithm (GDC 2009 talk) was not found in primary form.

## 3. Structural integrity solvers: islands, stress, load paths

### Takeaway
Three tiers exist: (a) connectivity only — break bonds, flood-fill, any island no longer connected to an anchor falls; (b) heuristic load paths — propagate supported weight down the graph and break overloaded bonds; (c) iterative stress solvers over the bond graph (Blast). All three are graph algorithms on small graphs (hundreds to thousands of nodes per building) and can be written in integer or fixed-point arithmetic for tier A.

### Cited Findings
- Blast stress solver works "directly with the bond graph", iteratively spreading forces across bonds; separate tension, compression and shear limits per bond; inputs are per-node mass, volume, position plus per-frame forces (`addForce`, `addGravity`, `addCentrifugalAcceleration`, impact impulses on the nearest node); output is a count of overstressed bonds and generated bond-fracture commands **[primary]** — [Blast Stress Solver docs](https://nvidia-omniverse.github.io/PhysX/blast/docs/api/extensions/ext_stress.html)
- Blast stress solver cost is "linearly proportional to `maxSolverIterationsPerFrame`"; most setup work happens in `create()` using the initial graph; `graphReductionLevel` trades speed for quality and is marked experimental; actors with ≤1 graph node are ignored **[primary]** — [Blast Stress Solver docs](https://nvidia-omniverse.github.io/PhysX/blast/docs/api/extensions/ext_stress.html)
- Gravity in Blast's solver needs at least one zero-mass (infinite mass, fixed) node or an explicit support force; otherwise the structure behaves as if in free fall with no internal gravity stress **[primary]** — [Blast Stress Solver docs](https://nvidia-omniverse.github.io/PhysX/blast/docs/api/extensions/ext_stress.html)
- Omniverse Blast exposes per-bond elastic limit (damage starts) and fatal limit (instant break); negative tension/shear limits fall back to the compression limit **[primary]** — [Omniverse Blast Destruction](https://docs.omniverse.nvidia.com/app_code/prod_extensions/ext_blast.html)
- The Blast docs say nothing about determinism or floating-point behaviour **[primary, absence]** — [Blast Stress Solver docs](https://nvidia-omniverse.github.io/PhysX/blast/docs/api/extensions/ext_stress.html)
- VACD (Müller 2013) includes island detection after partial destruction to determine support structures **[secondary summary]** — [3DVF](https://3dvf.com/actualite-6536-siggraph-2013-fracturation-dynamique-temps-reel-nvidia-html/)
- Zheng & James 2010 used a "fast quasistatic stress solver" to drive fracture events **[primary project page]** — [Cornell FractureSound](https://research.cs.cornell.edu/FractureSound)
- Teardown's base game reportedly does not account for structural stability, so whole buildings can be held up by one voxel; a structural-integrity prototype was later confirmed **[secondary]** — [PressReader/PC PowerPlay](https://www.pressreader.com/australia/pcpowerplay/20220725/283141432486640); [80.lv](https://80.lv/articles/this-real-time-voxel-building-demolition-is-so-satisfying/)

### Inferences
- **Tier A recommendation**: run (a) every time a bond breaks (BFS from anchor nodes over unbroken bonds, nodes visited in ascending `uid64`, cost O(nodes+bonds), microseconds for 10³ nodes), and (b) a fixed-iteration Jacobi-style load propagation in Q16.16 or int32 milli-newtons, with a *fixed* iteration count (not "until converged") so the result is identical everywhere. Blast's "linear in iterations" property suggests a fixed small count (e.g. 8–32) is a sensible budget knob; exact numbers need measurement.
- Run the solver only on the *dirty sub-graph* (building touched this tick), at the simulation fixed step, in deterministic order of building ids; the output (list of bonds to break, list of islands to detach) is the gameplay-relevant state.
- Elastic/fatal limit pairs map directly onto the per-part damage states from section 2 (elastic exceeded → advance damage state; fatal → break bond).
- Keep Jolt out of the stress loop: Jolt contact forces are tier B1 and listener callbacks arrive in nondeterministic order (see section 4), so impact *inputs* to the solver should come from gameplay events (weapon, explosion with tier A parameters), not from Jolt contact impulses, unless they are sorted and quantized first.

### Gaps
- No primary numbers found for Blast stress solver per-frame cost on a given graph size, or its default iteration count.
- No primary description found of the Teardown structural-integrity prototype's algorithm (the voxagon devblog URL tried returned 404).

## 4. Deterministic gameplay outcome, cosmetic debris, regenerating fracture from (id, impact)

### Takeaway
Production games split destruction into an authoritative, compact *state* (which parts/bonds are broken, in what order) and non-authoritative *presentation* (debris motion). Teardown replicates destruction as deterministic commands and syncs physics by state; The Finals runs all destruction on the server and streams transforms. With seeded fracture from stable IDs, a fracture pattern never needs to be stored — only the command log.

### Cited Findings
- Teardown: voxel data is not sent ("simply too much data"); the server sends destruction *commands* that all clients apply in the same order to reach the same state; physics uses ordinary state synchronization; join-in-progress replays a bounded queue of commands and is disabled when too many changes have accumulated **[secondary interview with the developer]** — [80.lv](https://80.lv/articles/teardown-developer-breaks-down-multiplayer-and-voxel-destruction-tech)
- The Finals: destruction and movement run on Embark's servers; clients do not run physics or mispredict; the server sends resulting transforms for debris and moving platforms **[secondary]** — [PC Gamer](https://pcgamer.com/i-almost-dont-believe-the-destructibility-in-this-fps-is-real); [Seasoned Gaming](https://seasonedgaming.com/2022/09/27/embark-studios-emphasizes-destruction-and-chaos-in-the-finals/)
- A UE4 forum poster guessed that Siege generates destruction on the server and replicates a seed, explicitly without knowledge **[weak, speculation]** — [Unreal forum](https://forums.unrealengine.com/t/procedural-destruction-rainbow-six-siege-style/81885)
- Jolt determinism conditions: same API call order (bodies/constraints added, removed, modified in the same order) and same binary; with `CROSS_PLATFORM_DETERMINISTIC` (≈8% slower) results are identical across compilers (MSVC2022, clang, gcc, emscripten), configurations, OS and architectures, provided the same source and same defines (e.g. not mixing `JPH_DOUBLE_PRECISION`) **[primary]** — [Jolt Architecture.md, Deterministic Simulation](https://github.com/jrouwe/JoltPhysics/blob/master/Docs/Architecture.md)
- Jolt caveats relevant to destruction: broadphase queries are *not* deterministic (bounding boxes widened until maintenance); narrowphase results are consistent but arrive in varying order; contact/activation listeners are called from multiple threads in nondeterministic order; `GetActiveBodies` order is nondeterministic; the app should compile with precise FP (`-ffp-model=precise`, `/fp:precise`); cross-platform determinism is "less tested", verified each build on a list of targets including macOS clang ARM64 NEON, Linux clang x86-64 AVX2 and Windows MSVC x86-64 AVX2 **[primary]** — [Jolt Architecture.md](https://github.com/jrouwe/JoltPhysics/blob/master/Docs/Architecture.md)
- Jolt samples have a "Check Determinism" option that records state via `StateRecorder`, rewinds and re-steps to validate **[primary]** — [Jolt Architecture.md](https://github.com/jrouwe/JoltPhysics/blob/master/Docs/Architecture.md)
- Breaking Good shows impact-dependent patterns can be derived at runtime from precomputed data by projection, i.e. the pattern is a function of (object, impact) **[primary]** — [arXiv 2111.05249](https://arxiv.org/abs/2111.05249)
- Müller 2013 applies generic, artist-made fracture patterns aligned to the impact point, i.e. pattern = f(template, impact position) **[secondary summary]** — [SIGGRAPH archive](https://history.siggraph.org/?p=108389)

### Inferences
- **Canonical destruction event** (tier A, integer): `{tick, building_uid64, part_uid64, impact_cell (part-local position quantized to e.g. 1 cm in int16×3), impact_dir (quantized), energy (fixed-point), weapon/material class}`. The world's destruction state = ordered log of these events per streaming cell; it is tiny, saveable, replayable and network-friendly (the Teardown model, but on parts instead of voxels).
- **Seeded regeneration**: fracture seed = `hash(generator_version, part_uid64, damage_level, impact_cell)`; Voronoi sites from the named RNG stream `"fracture"`, biased towards the impact cell. Chunk geometry, chunk bonds and cap materials are then a pure tier A function and need not be stored — only the event. This fits the existing Merkle cache: fractured-part meshes are just another cacheable generator output keyed by the event.
- **Quantize at the boundary**: impact position/direction must be quantized before hashing (otherwise float noise from Jolt raycasts changes the seed). If the impact comes from a Jolt query, sort and quantize as the Jolt docs advise; better, compute weapon hits with own tier A ray-vs-convex code against the generator's convex pieces.
- **Cosmetic vs gameplay chunks**: chunks above a size threshold (can block a door, cover a player) are gameplay bodies — spawned in deterministic order into Jolt (tier B1, cross-platform deterministic if inputs identical); small chunks/debris are cosmetic: separate Jolt object layer or a cheap particle-rigid system, never read back by gameplay, may be culled per client. Final rest position of large gameplay chunks can be snapped/settled server-side and sent as state (The Finals model) if tier B1 cross-OS identity fails in measurement 27.
- Order of adding fracture bodies to Jolt must follow sorted `uid64` order to satisfy Jolt's "same API call order" rule.

### Gaps
- Teardown's handling of floating point in its deterministic command application (and whether it is cross-platform) is not stated in the sources found.
- No primary source on how RealBlast replicates destruction (seed vs results) — only forum speculation.
- No source found on deterministic Voronoi clipping in fixed-point specifically; feasibility is an inference.

## 5. Rendering damaged content without bindless

### Takeaway
The classic AAA answer for "damage without new geometry" is a mask: Frostbite 2 stored damage as a low-resolution volume distance field built from spheres and sampled per pixel. Combined with part-level swaps (intact → damaged mesh) and instanced debris, this fits an SDL_GPU renderer with texture arrays and no bindless.

### Cited Findings
- Frostbite 2 "Destruction Masking using Volume Distance Fields" (Robert Kihl, DICE, SIGGRAPH 2010 Advances in Real-Time Rendering): place spheres on the geometry where damage occurs, build a signed distance field in a volume texture (each texel = distance to the nearest sphere), sample it with trilinear filtering and take the mask surface at 0.5; ≈2 m per texel was "good enough"; predecessors shipped in Battlefield Bad Company, 1943 and Bad Company 2; targets PS3, Xbox 360, DX10/11 **[primary]** — [Kihl slides PDF](https://www.advances.realtimerendering.com/s2010/Kihl-Destruction%20in%20Frostbite(SIGGRAPH%202010%20Advanced%20RealTime%20Rendering%20Course).pdf); [Frostbite news](https://frostbite.com/frostbite/news/destruction-masking-in-frostbite-2-using-volume-distance-fields)
- Control: Northlight decides which events and particles react to destruction **[secondary]** — [80.lv](https://80.lv/articles/gdc-talk-destructible-environments-in-control)
- Project context: SDL_GPU has 16 samplers per stage and no bindless, so the engine plans materials as `Texture2DArray` **[primary, internal]** — `wallhammerzero/docs/research/procedural-graphics.md` citing [SDL_sysgpu.h](https://raw.githubusercontent.com/libsdl-org/SDL/main/src/gpu/SDL_sysgpu.h)

### Inferences
- **Crack/damage mask**: instead of a volume texture per building, pass a small per-instance array of damage spheres (e.g. ≤8 `float4` in a storage buffer indexed by instance id) and evaluate the min-distance in the pixel shader; this is Kihl's technique without the 3D texture and works without bindless. Add a crack detail layer from the material texture array, revealed by the mask.
- **Vertex damage**: per-vertex "damage" channel (already planned masks in vertices for buildings) for soot/char gradients written when a part changes damage state — one small vertex-buffer update per damaged part.
- **Part swap rather than per-pixel cutting**: damage states 2–3 are new meshes from the generator; keep them in the same vertex/index mega-buffer and material array as intact parts so they batch with them.
- **Debris**: chunks from one fracture share a material and come from a few templates; render as instanced draws with per-instance transform from the physics/particle system. Cosmetic debris older than N seconds or beyond a distance merges into a static "rubble" mesh (regenerable from the event log) or is despawned.
- **LOD/impostors**: a damaged building invalidates its far LOD/impostor; regenerate the HLOD for that streaming cell asynchronously from the new part states (cheap with the Merkle cache), and keep showing the old impostor with the damage-sphere mask applied until the new one arrives.
- **Draw calls**: with part-level batching per material array, the draw count grows with the number of *distinct* damaged meshes, not the number of chunks; a per-cell cap on live fractured parts (e.g. fold older ones into the rubble mesh) bounds it.

### Gaps
- No primary sources gathered this session on dust/smoke VFX budgets for destruction, debris instance counts in shipped games, or impostor regeneration after damage. These need a follow-up (e.g. Frostbite/Battlefield, The Finals, Control rendering talks).

## 6. Audio for destruction (brief)

### Takeaway
Physically based fracture sound is feasible at interactive cost by replacing per-fragment modal models with precomputed proxy soundbanks; for a game, a budgeted granular/modal synth driven by material + chunk size, with heavy voice culling, is the practical version.

### Cited Findings
- Zheng & James, "Rigid-Body Fracture Sound with Precomputed Soundbanks", ACM TOG 29(3), SIGGRAPH 2010: time-varying rigid-body sound models for brittle fracture, a fast quasistatic stress solver for fracture events, and precomputed soundbanks of *ellipsoidal* sound proxies looked up by inertia (reduced to a 2D table); example: glass table setting smashed into 300+ pieces using 4046 modal proxies, ≈500× speedup **[primary]** — [Cornell project page](https://research.cs.cornell.edu/FractureSound); [paper PDF](https://research.cs.cornell.edu/FractureSound/files/fractureSound.pdf)
- Chadwick, Zheng, James (SCA 2012) extended proxy soundbanks to acceleration noise for multibody debris scenes **[primary]** — [Eurographics DL](https://diglib.eg.org/handle/10.2312/SCA.SCA12.265-274)

### Inferences
- WHZ's `eng_gen_audio` (tier A generator) can precompute a small modal bank per material × size class (ellipsoid proxy idea), and the runtime mix (tier B2) triggers voices from collision events with a hard voice budget (e.g. loudest-N per frame, one "rubble bed" loop for the rest). Debris sound never affects gameplay, so it can stay tier B2.

- No game-industry numbers found for debris voice budgets.

## 7. Academic work overview

### Takeaway
The relevant line runs from quasi-static FEM fracture at impact (Müller 2001), through impact-aligned template patterns on convex decompositions (Müller 2013 VACD), to precomputed fracture modes projected at runtime (Sellán 2022), with sound (Zheng & James 2010) and rendering masks (Kihl 2010) as companions. No paper was found that specifically fractures *procedural (grammar) models* using the grammar's structure.
