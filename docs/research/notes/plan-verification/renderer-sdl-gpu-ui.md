# Plan verification: renderer, SDL_GPU and UI

Status as of 2026-11-06. Verified against primary sources (GitHub, the SDL wiki, Apple WWDC, the SDL source code). Secondary sources are marked. Nothing was installed or run.

## Conclusion

The plan holds. None of the decisions D5, D25, D27, D54 and D57 is refuted. Three known SDL_GPU limits still apply in version 3.4.20. Bindless has been definitively postponed to SDL4 since June 2026. Multi-draw indirect on Metal is a CPU loop. Queries (timestamp, occlusion) are missing, but they have milestone 3.6.0. Forward+ with clustered lights matches Apple's recommendation. But the phrase "without a depth prepass" holds only for Apple GPUs. On desktop GPUs (Linux, Windows), hidden surface removal does not replace it. The biggest gap is in the UI: Clay has no renderer for SDL_GPU, no text input and no tables, so `eng_ui` is more work than D57 suggests. The second gap is in the numbers: I found no trustworthy measurement of draw cost on Metal, of the cost of 4x MSAA, or of the light count on Apple Silicon, so measurements on M1 and M2 are still needed. New information: in September 2026 Aaltonen released his own library NoGraphicsAPI (Metal 4 and Vulkan 1.4), but it requires macOS 26 and C++20.

## Impact on the plan

1. **D5/D25, the text about limits.** Clarify: bindless is rejected permanently for SDL3 (not just "rejected 2026-06"). Queries come in SDL 3.6.0. On Apple Silicon, GPU time can be measured only per render pass. Until then, measure with our own counters, the Metal HUD log and Tracy (Xcode is not installed, D35). (https://github.com/libsdl-org/SDL/issues/11696)
2. **Material texture table.** Without bindless this means a few `Texture2DArray` with the same size and format and at most 16 samplers per stage. Account for this in the asset design (uniform texture sizes). (https://github.com/libsdl-org/SDL/blob/main/src/gpu/SDL_sysgpu.h)
3. **Indirect draw stream.** On Metal it is a loop. The plan must not rely on MDI for CPU performance. The main lever is instancing and merging into large buffers. Measuring draw cost on M1 remains decisive, no third-party number exists.
4. **D27, depth prepass.** Change the wording to "no prepass on Apple GPUs, an optional switch on Vulkan and D3D12". Fix the draw order: opaque, alpha test, transparent. Alpha-test vegetation weakens HSR, measure this on the city's trees. (https://developer.apple.com/videos/play/wwdc2020/10632/)
5. **Thin G-buffer.** If SSAO, reflections or screen-space decals come, the forward pass must write extra normals (like Doom 2016). Decide early, it changes the target formats.
6. **MSAA.** SDL_GPU cannot resolve depth or do memoryless. With 4x MSAA we need our own way to get single-sample depth for post effects. MSAA and TAAU exclude each other as the main path, see question 1.
7. **Lights.** Expect a cap on the order of hundreds of real lights in view (Unity 256, Godot 512). Handle the thousands of lights of the night city with levels of detail: distant lights as glowing sprites without lighting. Verify with measurement 1 on M2.
8. **RHI according to Aaltonen.** Keep the shape of the API (handles, table, draw stream), but do not expect a direct match. A native backend would today mean Metal 4 and macOS 26, not Metal 3 as in D25. The author's library is C++20, for a C17 engine only a model. (https://github.com/sebbbi/NoGraphicsAPI)
9. **D57, `eng_ui`.** Add three things to the scope that Clay does not provide: a renderer of Clay commands on top of SDL_GPU (batching, scissor, atlas), text input (cursor, selection, clipboard, IME) and a table with row virtualization. Pin Clay to a specific commit, development has stood still since May 2026.
10. **SDL_ttf.** The last release is a year and a half old and the GPU text engine has open bugs. Pin a commit from `main` and expect our own atlas fixes.
11. **RmlUi as a fallback.** An SDL_GPU backend exists, but only a basic one, and the library is C++. So the fallback means a C++ dependency in the game, not just in the studio.
12. **Studio.** Dear ImGui on top of SDL_GPU is risk-free. Use the tags of the `docking` branch and `dear_bindings`. The studio will need a C++ compiler (only for ImGui).
13. **D54, upscale.** FSR1 is clean in terms of license. The ratio of 1.6–1.8× is beyond the Quality mode. Consider a higher internal resolution for the Retina panel or a variable scale. The input to EASU must be anti-aliased, so FSR1 makes sense only with MSAA (or other AA) before it.

## Questions for the owner

1. **Anti-aliasing and upscale.** Do you want a sharp image via 4x MSAA and a spatial upscale (FSR1), or a softer image via TAAU, which occasionally leaves ghosts behind motion? Both paths at once make no sense.
2. **Light budget.** Is it enough if only the hundreds of nearest lights in the night city shine "for real" and the rest are just glowing points? Or is a thousand real lights in view a hard requirement?
3. **Lowest macOS.** Should the game run on macOS 15, or may we eventually require macOS 26? Whether a native backend with Metal 4 (and thus bindless) is a possible path at all depends on this.
4. **Development version of SDL.** May the engine build on the SDL development branch (3.5, later 3.6 with queries), or only on stable releases?
5. **Game UI.** Do you accept that `eng_ui` on top of Clay means writing our own renderer, text input and tables? Or do you want a short time-boxed experiment with RmlUi first (ready widgets, but C++ and an HTML/CSS style)?
