# Practitioner experience: building 3D games, engines and code-generated 3D assets with AI coding agents (2025 → Nov 2026)

Research date: 2026-11-05. Scope: real projects, write-ups and demos where the 3D graphics come from code (procedural meshes, shaders, textures written by code) and an AI coding agent wrote most of that code. Each source is dated. "Verified" means a primary source (author's own post or repo, or the event organiser) with visuals or a playable link. "Claim" means secondary coverage or self-reported numbers.

Note on model names: sources from mid/late 2026 name models such as Claude Opus 5, Opus 5.5, "Claude Fable 5", Sonnet 5 and "GPT-5.6 Sol Ultra". These notes repeat the names exactly as the sources give them.

## 1. Notable AI-coded 3D games and demos with procedural/code graphics: what they looked like, AI vs human share

### Takeaway
The public record is dominated by browser three.js games. They are low-poly, flat- or simply-shaded, built from primitives (boxes, spheres, cylinders), and playable within hours. Judges and authors consistently describe them as "impressive starting point, not a good/finished game". I found no publicly documented, visually notable AI-written native C/C++ 3D engine with procedural graphics. The closest analogues are TypeScript procedural generators (citygen, CityGrow) and engine-hosted projects (Godot).

### Cited Findings
**Early 2025 (Claude 3.7 Sonnet era): the three.js wave**
- (Mar 1, 2025) Lynn Cherny's newsletter "Claude Goes 3D" reports the new Claude (3.7 Sonnet) as "very good at three.js generation". Examples: levelsio's multiplayer flight sim (fly.pieter.com); a 17th-century ship-battle sim in three.js (Evan Jones); an image-to-3D navigable map made "in very few prompts with Claude 3.7 Sonnet" (websim); a "one shot" 3D city with moving cars and people running in CodePen (ozgrozer, codepen.io/ozgrozer/full/MYWjaVo); a driving sim. The author found visible artifacts: "towering tree pixels" they had to escape by pressing space. — [TITAA #64](https://arnicas.substack.com/i/158092241/a-poem)
- (Feb–Mar 2025) fly.pieter.com: Pieter Levels' MMO flight sim, which the site calls "100% made with AI". Reported tool stack: Cursor (primary), Grok 3, Claude 3.7 Sonnet, ChatGPT for debugging, three.js. The first playable version reportedly took ~3 hours of prompting by someone with no game-dev background. — [Indie Hackers](https://www.indiehackers.com/post/pieter-levels-used-ai-to-build-a-viral-flight-simulator-in-3-hours-with-no-background-in-game-development-7CPfMr1yRLEwH6cC8xhE); [fly.pieter.com](https://fly.pieter.com/)

**Mid/late 2026 (Opus 5 / 5.5 era)**
- (Aug 5, 2026) Simon Willison, "Raccoon Heist" one-shot with Claude Fable 5 in Claude Code for web, from a phone-written prompt. The agent chose three.js. Characters and scenery were procedural low-poly models built in code (e.g. a dog made of spheres and cylinders). Seven ground/wall textures and the title art came from gpt-image-2 via a script, with outputs committed as static files. Audio was procedural WebAudio. It took ~34 minutes and 7 commits. - (Sep 14, 2026) "CityGrow": a Claude Code "ultracode" (multi-agent dynamic workflow) session with Claude Opus 5, about 4 hours from a single prompt. - (2026, date only from footer) citygen (Tomas Liubinas): a procedural 3D city generator "built with Claude Opus 5.5 in Claude Code", "designed and directed" by the human. Plain TypeScript engine (no DOM/renderer dependency) with a seeded RNG/math/mesh-builder core. City package (organic/radial street grid → blocks → plots), house package (plot → house spec → mesh, seven historic Baltic styles such as Kaunas Art Deco and Vilnius Baroque), interior package (rooms, doors, stairs, cellars, attics). Day/dusk/night lighting, weathering, .glb export, vitest tests plus a headless house-generation CLI. 47 commits, 0 stars. Small but a close architectural analogue to the user's project. — [github.com/tomasliubinas/citygen](https://github.com/tomasliubinas/citygen)
- (Oct 15, 2026; vendor blog, so partly promotional) Opus 5 launch demos: a browser FPS by Matt Shumer with "custom code with no external assets", which community developers said had glitches and doubtful scalability ("not a shippable FPS"); a Godot photography sandbox, ~80% built in one day, voxel-styled partly to sidestep 3D assets ("Opus 5 accelerated implementation but did not solve the custom 3D asset pipeline"); a one-shot small horror game. — [SoonLab review](https://www.soonlab.ai/blog/claude-opus-5-game-development/) (links to [X post](https://x.com/mattshumer_/status/2081054356405731740), [Reddit sandbox](https://www.reddit.com/r/ClaudeAI/comments/1v6n9v0/making_a_photography_sandbox_game_with_opus_5/))
- Voxel engines: a C + Vulkan voxel "reality simulator" where AI generated "substantial portions of the code, shaders, tests, and documentation under the project creator's direction" ([vigasilva/voxel-engine](https://github.com/vigasilva/voxel-engine)); a voxel engine "designed and curated by Claude Fable 5, GLM 5.2 and Claude Sonnet 5" ([RickDeckardWebsim/VoxelEngine](https://github.com/RickDeckardWebsim/VoxelEngine)). ### Inferences
- The realistic visual ceiling seen in public, AI-built, code-only 3D is clean low-poly or stylised: primitive-composed characters, extruded/boxy buildings, simple lighting, sometimes lit windows or night modes. That ceiling is consistent across 18 months of model generations. Gains between generations show up mainly as more systems working together (traffic, zoning, interiors, audio) rather than as higher per-asset art quality.
- Where projects look "better", the extra fidelity usually comes from non-code assets: gpt-image-2 textures (Willison), Tripo 3D models (Vibe Jam sponsor, Godogen), or engine content (Godot). A pure code-graphics C engine gives up that crutch. It should therefore pick a style where primitives and procedural rules are the look: voxel, low-poly flat-shaded, or "3D pixel art" (low internal resolution plus palette quantisation).
- citygen's layout (seeded core → spec → mesh, renderer-independent, headless CLI, deterministic per seed) is the closest public template to the user's architecture, and it worked with Opus 5.5.
- For a project that is "Minecraft-like", describe it as an original voxel/open-world game, not as a clone of a named title. The reported Opus 5.5 guardrails target recreating specific existing games.

### Gaps
- No published, inspectable example of an AI-written native C17/C++ 3D engine with fully procedural graphics and a write-up of visual quality. Searches for C/SDL/Vulkan AI-written engine devlogs returned only older human-written clones (Craft, 2014 "Minecraft in 2500 lines of C").
- Vibe Jam 2026 winners and any breakdown of how many entries used code-only meshes vs generated models were not found.
- I did not view screenshots directly. Visual descriptions come from the authors' and judges' text.
- The fly.pieter.com revenue figures conflict and are unverifiable.

## 2. Developer write-ups on using Claude/GPT for procedural meshes, shaders, textures, animation and terrain/city: what worked first try, where it looped

### Takeaway
Across 2025–2026 write-ups the pattern holds. Models are strong at the code structure of procedural systems: seeded generators, specs → meshes, simulation logic, three.js boilerplate, lighting setups. They are weak at spatial and aesthetic judgement: exact placement, proportions, organic shapes, rigging, whether something actually looks right. Visual work stalls without an automated "eyes" loop. Once a loop is in place, the agent can iterate unattended.

### Cited Findings
- (Mar 13, 2026) Dave Snider, building Table Slayer and Counter Slayer (heavy 3D web apps): "Claude struggles with visual, spatial reasoning in 3D" but handles CSS and basic design language well. Early work meant hours of manually sending screenshots ("check this out, you did it wrong"). Claude claimed it could read binary STL natively and invented the contents. CSG unions/subtractions caused "a box can exist in the data without being visible". Debug-logging coordinates helps only slowly and usually after Claude "has already hit a wall". — [davesnider.com/claude-3D](https://davesnider.com/claude-3D)
- (May 6, 2026; vendor blog) Claude + Blender MCP. Works: primitives, transforms, basic lighting/camera, basic Principled BSDF materials, utility scripts. Hit or miss: modifier stacks, multi-object alignment, procedural texture nodes. Reliably fails or needs heavy correction: organic shapes and characters, animation curves and rigging, Geometry Nodes networks, "judgment calls on proportions and aesthetics". "Claude's spatial understanding is imprecise": objects land "approximately" where described and exact placement takes several correction rounds. — [MindStudio](https://www.mindstudio.ai/blog/claude-blender-mcp-real-world-performance)
- (2025–2026) Blender MCP (ahujasid) connects Claude to Blender for object creation, materials and scene inspection, and can pull Hyper3D Rodin generated models. A Reddit user found Claude handled geometry, lighting, camera and render settings, though "not everything in the prompt landed perfectly" on a simple scene. The add-on runs on Blender's main thread and blocks the UI on heavy scenes. — [archestra MCP catalog](https://archestra.ai/mcp-catalog/ahujasid__blender-mcp); [Reddit snapshot](https://reddit.sentinel-team.org/posts/1tare6x/snapshots/2026-05-16T01%3A22%3A27.604243Z)
- (Aug 2026) Willison's one-shot: the procedural low-poly geometry, flashlight cones and scene composition came out coherent first time. Failures were integration and layout bugs: a CSS `cssText` assignment wiped three.js inline canvas sizing, an overlay blocked taps, and a texture was likely misapplied. The agent found and fixed some of these itself via Playwright screenshots at multiple viewports. — [Simon Willison](https://simonwillison.net/2026/aug/5/raccoon-heist)
- (Sep 2026) CityGrow lessons. Writing a spec and contract first, including coordinate systems and layer heights, reduced integration errors between parallel agents. A pure, seeded simulation was testable without rendering (Node tests for road connectivity, population consistency, same-seed determinism). Traffic got a pass-through hack. The spec drifted from the implementation (agent-based road builders were swapped for a pre-planned grid without updating the spec). — [note.com/tank_ai](https://note.com/tank_ai/n/n3be99a4ad80e?hl=en)
- (Oct 2026) "Procedural geometry can look impressive in video, but consistent characters, environments, rigging, and audio still need other tools and human direction." Game feel, timing and difficulty still need human playtesting. — [SoonLab](https://www.soonlab.ai/blog/claude-opus-5-game-development/)
- (Mar 2026) Godogen README: GDScript errors "the parser can't check still fail at runtime, where it's found only by running". For Bevy, "its API moves between releases faster than model training data catches up", so the guide makes the agent "read the installed source instead of trusting memory". — [htdt/godogen README](https://raw.githubusercontent.com/htdt/godogen/master/README.md)

### Inferences
- Applied to SDL3/SDL_GPU, which is newer than most training data, the Godogen/Bevy lesson carries over directly. Vendor the SDL3 headers and examples into the repo and instruct the agent to read them rather than recall the API.
- Procedural mesh code (primitives, extrusions, L-system buildings, voxel meshing) is in the "works" zone. Proportion and style judgement, organic characters and skeletal animation/rigging are in the "fails" zone. They need either a strong parametric spec with numbers (heights, ratios, palette) or a deliberately simple style: blocky or segmented characters with procedural walk cycles instead of skinned organic meshes.

### Gaps
- I found no detailed first-hand write-up specifically about Claude/GPT writing HLSL/GLSL/MSL shaders for SDL_GPU, or about procedural IK. Evidence for shaders is indirect (three.js shader effects in demos; Blender node shaders "buildable but complex setups a struggle").
- No quantitative first-try success rates for any of these tasks were found.

## 3. Workflows that worked: headless render + screenshot review, references, specs, lints, golden images, MCP "eyes", agent visual loops

### Takeaway
The most consistently reported success factor is an automated render → capture → inspect → fix loop that the agent drives itself. It should have scripted camera presets, debug markers, multiple angles, and machine-readable scene state next to the pixels. The second factor is a written spec/contract (coordinate systems, units, seeds, file ownership) with tests on the deterministic, render-free parts. The strongest setups use a separate visual judge (another model or a forked context) that sees only pixels and references, not the code.

### Cited Findings
- (Mar 2026) Snider's working loop: let Claude "navigate the app, control the camera, add markers, capture screenshots and compare to the request" without asking the human. His `capture-view.ts` supports preset angles (iso/top/front/left), zoom, custom camera position and look-at, output path, and framing by object ID. He places red debug spheres at positions so screenshots carry spatial reference. Claude also reads project.json for positions and layout alongside the renders. He builds the tooling first to create "a shared language" for the project. — [davesnider.com/claude-3D](https://davesnider.com/claude-3D)
- (Mar 2026, Show HN) Godogen (htdt): the principle is "Proof over claims". The agent judges progress from the running game, not from a clean compile. Coverage reports a visual-QA agent that sees only screenshots, never code, and compares them against generated reference images. One variant uses Gemini Flash vision to catch z-fighting, missing textures and broken physics; another runs visual verification in a forked context with Claude's own vision. The README notes the best results came with Claude Code + Opus 4.6, while Sonnet 4.6 needed more guidance. Unattended runs end with a 15–20 s proof recording. — [godogen README](https://raw.githubusercontent.com/htdt/godogen/master/README.md); [gentic.news](https://gentic.news/article/how-godogen-s-claude-code-skills-solve-llm-game-development); [Gigazine](https://gigazine.net/gsc_news/en/20260317-godogen/)
- (Aug 2026) Willison's run: Playwright-driven screenshots at desktop, portrait-phone and landscape-phone sizes; scripted playthroughs; teleporting the player into the scenario under test (next to the dog); regression tests for each bug found; a `notes.md` build log; frequent commits. — [Simon Willison](https://simonwillison.net/2026/aug/5/raccoon-heist)
- (Sep 2026) CityGrow: spec plus contract first (coordinate systems, layer heights, file-ownership table), parallel agents per module, a final integrator agent, and seeded pure simulation with invariant tests. Lesson: parallel agents suit independent modules, while iterative single-file edits are cheaper in plain Claude Code. Keep the spec updated. — [note.com/tank_ai](https://note.com/tank_ai/n/n3be99a4ad80e?hl=en)
- (2026) citygen: renderer-independent TypeScript core, a headless generation CLI and vitest tests, so generation is testable without a GPU. — [citygen](https://github.com/tomasliubinas/citygen)
- (Oct 2026) Recommended workflow: one vertical slice with explicit controls, loop and win/loss conditions; engine version, run command and coding rules up front; file boundaries; testable requirements instead of "fun/polished"; a mandatory build-run-inspect-fix loop with screenshots; the human playtests; "Build the smallest complete version first." Use the top model for vertical slices, system design and hard debugging, and cheaper models for repetitive edits. — [SoonLab](https://www.soonlab.ai/blog/claude-opus-5-game-development/)
- (2026) Godot is the community consensus best-fit mainstream engine for agents because scenes are text and it runs headless. Unreal's binary assets were a repeated problem. — via search summary of [chierhu Medium survey](https://chierhu.medium.com/claude-code-for-game-development-7a88fcd19992) (page returned 403 to direct fetch, so this is unverified at full-text level)
- (2026) PixelStrata (Claude Code skills for 2D/3D pixel-art games) keeps project memory in files rather than chat: CLAUDE.md, docs/gdd.md, assets.json, docs/devlog.md. — [jasonmello/pixelstrata](https://github.com/jasonmello/pixelstrata)
- MCP "eyes": Blender MCP gives scene-state inspection and auto-returned script errors. The MindStudio review does not discuss viewport-screenshot feedback. — [MindStudio](https://www.mindstudio.ai/blog/claude-blender-mcp-real-world-performance)
- General vision-hallucination guidance: treat a model's "looks correct" as an unverified claim. Prefer deterministic checks (pixel diffs vs reference, engine-state assertions, a separate detector). — [CACM, Visual Hallucinations in LLMs](https://cacm.acm.org/news/visual-hallucinations-in-llms/); [DEV: claims-vs-detections verifier](https://dev.to/codewithbg/i-built-a-real-time-hallucination-prevention-system-for-llms-using-computer-vision-1age)

### Inferences
Here is how these workflows translate to a C17 + SDL_GPU engine. These are my synthesis, not sourced practice for C specifically.
- Build a headless/offscreen capture mode early: `engine --capture scene.json --cam iso|top|front|<pos,lookat> --seed N --out x.png`. It is the C equivalent of Snider's `capture-view.ts` and Godogen's proof captures.
- Emit a JSON scene/asset report next to each PNG (bounding boxes, triangle counts, normals sanity, palette histogram, min/max heights). The agent then reasons over numbers as well as pixels, as Snider did with project.json.
- Keep mesh/city/animation generators pure and seeded, independent of the GPU (citygen, CityGrow), so you can unit-test invariants and golden-hash them: same seed → same vertex buffer hash.
- Use golden images only for regressions, with a tolerance. For "does it look right", use a separate judge context that sees only screenshots plus reference images and a written style spec (Godogen pattern).
- Debug-marker overlays (axis gizmos, red spheres, normal lines, wireframe toggle) cost little and fix the "box exists but invisible" class of bugs.

### Gaps
- No public write-up found of golden-image/perceptual-diff testing specifically for an AI-built game. Practice is mostly agent-viewed screenshots.
- No measured comparison of "agent self-review" vs "separate judge model" for visual QA.
- I did not find Godot/Unity MCP server evaluations in depth within this scope.

## 4. Anthropic's own examples: feasibility of large AI-written codebases (C compiler, long-horizon)

### Takeaway
Anthropic's Feb 2026 C compiler experiment shows that agent teams can produce a ~100K-line working systems codebase. This depended almost entirely on near-perfect external verifiers (test suites plus GCC as an oracle), a terse, agent-oriented test harness, and progress files. It also showed a ceiling: late in the project, fixes regressed other features. A graphics engine lacks an equivalent oracle for "looks right", so the visual half must be made testable another way.

### Cited Findings
- (Feb 5, 2026) Nicholas Carlini, "Building a C compiler with a team of parallel Claudes": 16 parallel Claude Opus 4.6 instances, each in its own Docker container, nearly 2,000 Claude Code sessions over ~2 weeks, just under $20,000 in API cost (~2B input / 140M output tokens). Result: a ~100K-line clean-room C compiler in Rust. It builds bootable Linux 6.9 on x86/ARM/RISC-V, compiles QEMU, FFmpeg, SQLite, Postgres and Redis, passes ~99% of most compiler test suites including the GCC torture tests, and compiles and runs Doom. — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Lessons from the same post:
  - The verifier must be nearly perfect: "Claude will work autonomously to solve whatever problem I give it", so a bad verifier means it solves the wrong problem.
  - Context pollution: "The test harness should not print thousands of useless bytes". Keep output to a few lines, log details to files, put ERROR on the same line for grep, and precompute summaries.
  - Time blindness: Claude "can't tell time and, left alone, will happily spend hours running tests instead of making progress". The fix was a default `--fast` mode running a deterministic per-agent 1%/10% sample.
  - Agents maintained READMEs and progress files because each started in a fresh container.
  - GCC served as an oracle: most kernel files were compiled with GCC and a random subset with Claude's compiler, plus delta debugging, to localise bugs and parallelise.
  - Parallelism collapsed on one monolithic target: "Every agent would hit the same bug, fix that bug, and then overwrite each other's changes."
  - Specialised roles: dedup, performance, codegen optimisation, Rust code-quality review, docs. There was no orchestrator agent; lock files in `current_tasks/` plus git sync handled coordination.
  - Limitations: no 16-bit x86 backend (calls GCC), no mature assembler/linker, generated code slower than GCC -O0, Rust quality "reasonable but not expert-level". Fixes often broke existing features, suggesting it was near the limit of what Opus 4.6 could handle. "It is easy to see tests pass and assume the job is done, when this is rarely the case."
  - — all from [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler); cost and line counts corroborated by [The Register](https://www.theregister.com/2026/02/09/claude_opus_46_compiler/) and [InfoQ](https://www.infoq.com/news/2026/02/claude-built-c-compiler)
- Coverage disagrees on autonomy. Some outlets say "zero human input", while The Register frames it as "mostly works" and notes the creator's concerns about fully autonomous development. — [Analytics Vidhya](https://www.analyticsvidhya.com/blog/2026/02/claude-agents-built-c-compiler/); [The Register](https://www.theregister.com/2026/02/09/claude_opus_46_compiler/)

### Inferences
- A C17 engine of tens of thousands of lines written by Claude is within demonstrated capability, at least for Opus 4.6+ and therefore plausibly for Opus 5.5. This is conditional on giving each subsystem a machine-checkable oracle: unit tests for math (matrix/quaternion identities), deterministic generator hashes, an SDL_GPU validation layer with zero errors, frame-time budgets, and a reference-renderer comparison where possible.
- Carlini's harness rules map directly onto engine tests: terse output, grep-able ERROR lines, a `--fast` sampled mode, and progress/README files for fresh sessions.
- A single monolithic visual target (e.g. "the city looks good") behaves like the Linux kernel did: parallel agents collide. Split visual work into independently verifiable assets and modules.

### Gaps
- I did not find an Anthropic case study specifically about Claude building games, 3D or graphics engines. Searches turned up only the compiler work and launch-day demos referenced by third parties.
- No Anthropic data on Opus 5/5.5 long-horizon runs comparable to the compiler experiment was found in this pass.

## 5. Known failure modes: visual hallucination, style drift, performance, 3D maths bugs

### Takeaway
Documented failures cluster into four groups. (a) The agent asserts visual success that isn't there, or invents file contents. (b) Spatial imprecision and mis-layering: invisible geometry, wrong placement, overlays and cropping. (c) Spec and architecture drift as projects grow, with performance and coupling surfacing later. (d) Convention mismatches in 3D maths (handedness, quaternion component order, rotation order), which are a known general hazard, though I found no AI-specific documentation of them.

### Cited Findings
- **Visual self-overrating:** the agent called the cropped desktop title art "gorgeous" while the raccoon was cut out of frame. — [Simon Willison](https://simonwillison.net/2026/aug/5/raccoon-heist) (Aug 2026)
- **Fabricated perception:** Claude claimed to read binary STL natively and made up the contents. — [Dave Snider](https://davesnider.com/claude-3D) (Mar 2026)
- **Invisible-but-present geometry** (CSG): "a box can exist in the data without being visible". — [Dave Snider](https://davesnider.com/claude-3D)
- **Spatial imprecision:** placement is "approximately" right, exact layout needs several correction rounds, and proportions and aesthetics are weak. — [MindStudio](https://www.mindstudio.ai/blog/claude-blender-mcp-real-world-performance) (May 2026)
- **Vision models in general** describe objects that are not present. Low-level visual hallucination (the kind involved in judging a rendered frame) is "largely unexplored". — [CACM](https://cacm.acm.org/news/visual-hallucinations-in-llms/); [arXiv 2503.20673](https://arxiv.org/pdf/2503.20673)
- **Text-only judging fails:** "Text models cannot judge game feel, art quality, or visual glitches without vision tooling." — search summary of [chierhu Medium survey](https://chierhu.medium.com/claude-code-for-game-development-7a88fcd19992) (full text not accessible)
- **Spec/architecture drift:** the CityGrow spec went stale (file-ownership table still "todo", road design changed without a spec update), and around 30 magic tuning constants were baked into tests. — [note.com/tank_ai](https://note.com/tank_ai/n/n3be99a4ad80e?hl=en). The first architecture "may not be production-ready"; expansion exposes tight coupling and performance issues. Overreach: some users said it read unrelated files or made more changes than requested. — [SoonLab](https://www.soonlab.ai/blog/claude-opus-5-game-development/)
- **Regressions near the capability limit:** in the compiler project, fixes often broke existing features. — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- **Performance and robustness hacks:** CityGrow cars pass through each other in jams, and adaptive resolution was needed to hold ~60 fps. — [note.com/tank_ai](https://note.com/tank_ai/n/n3be99a4ad80e?hl=en). Blender MCP blocks Blender's UI thread on heavy scenes. — [Reddit snapshot](https://reddit.sentinel-team.org/posts/1tare6x/snapshots/2026-05-16T01%3A22%3A27.604243Z)
- **Style consistency:** consistent characters and environments still need other tools and human direction. — [SoonLab](https://www.soonlab.ai/blog/claude-opus-5-game-development/)
- **3D maths conventions (general, not AI-specific):** a Stride engine issue shows a right-handed engine clashing with left-handed quaternion maths, so rotations pointed the wrong way ([stride3d #378](https://github.com/stride3d/stride/issues/378)). Isaac Lab switched quaternion layout WXYZ → XYZW, breaking hard-coded values ([IsaacLab #5186](https://github.com/isaac-sim/IsaacLab/issues/5186)). "Beware the natural quaternion" covers order and convention traps ([possiblywrong](https://possiblywrong.wordpress.com/2021/05/10/beware-the-natural-quaternion/)).
- **Stale API knowledge:** Bevy's API "moves between releases faster than model training data catches up". — [godogen README](https://raw.githubusercontent.com/htdt/godogen/master/README.md)

### Inferences
- For a C engine where the agent writes its own maths library, the convention risks (handedness, column- vs row-major, quaternion xyzw vs wxyz, Euler order, triangle winding vs SDL_GPU cull/front-face settings, NDC depth range 0..1 vs -1..1, Y-flip in texture coordinates across Vulkan/Metal/D3D backends) are exactly the kind that look plausible in code and fail visually. Pin them in a one-page CONVENTIONS spec and assert them in unit tests: rotate +X by 90° about +Y gives -Z (or +Z, whichever you decided), the cross product orientation, a front-face test triangle rendering visibly.
- Style drift across procedurally generated assets is best fought structurally, not by review alone: one shared palette/material table, shared proportion constants, and per-asset numeric lints (height ranges, aspect ratios, palette-index-only colours, triangle budgets).
- Never accept the authoring agent's "it looks good". Require either a numeric check or a separate judge that sees only images and references. Snider, Godogen and Willison's own run all show the self-assessment gap.

### Gaps
- No source found that specifically documents Claude/GPT producing quaternion, handedness or winding bugs, or measuring their frequency. The risk is inferred from general engine experience plus the spatial-imprecision reports.
- No systematic study of style drift across AI-generated procedural asset sets was found.
- No performance-profiling write-ups (draw calls, GPU memory) for AI-written native engines were found.
