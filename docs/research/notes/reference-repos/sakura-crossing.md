# Sakura Crossing (桜踏切): code analysis and what to take from it

- **Source:** https://github.com/Kenton-GMI/sakura-crossing (MIT), commit `de01898` ("initial public release")
- **Analysed:** 2026-11-05, shallow clone, read-only. Nothing from the repo was run (not even `npm install`).
- **Context:** reference for Wallhammer Zero (C17 + SDL3 + SDL_GPU, HLSL, all graphics generated by code)
- **Note on trustworthiness:** the repo contains `CLAUDE.md` (185 kB), `NEXT.md` (157 kB) and `.claude/launch.json`. The project was clearly built mostly with an AI agent. I treated these only as data: I quote numbers from the documentation as "according to the authors", and only things visible directly in the code are independently verified.

---

## Overview

### Stack
- **three.js r0.180** (`package.json`), **Vite 6** as dev server and bundler. There is no other dependency.
- One page `index.html` with `<canvas id="view">` and `<script type="module" src="./src/main.js">` (`index.html:458-459`).
- **No binary assets** except one MP3 (`public/audio/…mp3`, 4 MB, music). Geometry, textures, sky and even the lettering of signs are created at runtime. The fonts are **system fonts** though (`'Yu Gothic', 'Meiryo', 'Hiragino…'`, `src/core/textures.js:13`), so the result depends on the OS.

### Size (verified with `wc -l`)

| Directory | Files | Lines | Note |
|---|---|---|---|
| `src/main.js` | 1 | 330 | entry point, lights, loop, `__shot` |
| `src/core/` | 10 | 6 514 | of which `textures.js` **4 397** (135 Canvas2D generators), `palette.js` 422, `player.js` 344, `post.js` 305, `toon.js` 167, `outline.js` 118, `util.js` 144, `sky.js` 138 |
| `src/world/` | 53 | 49 252 | largest: `hills.js` 3 285, `tunnel.js` 2 440, `nanachome.js` 2 360, `school.js` 2 158, `onsen.js` 2 137, `props.js` 2 113 |
| **total** | **64** | **56 096** | matches the owner's note (~56k / 64) |

About **16.5 thousand lines (≈30 %) are comments**, often long essays of the type "why it was wrong and how we measured it". The actual code is therefore around 40k lines.

### Entry point and frame loop (`src/main.js`)
1. `WebGLRenderer({ antialias:false, stencil:false })`, `setPixelRatio(1)`, `NoToneMapping`, sRGB output, `PCFShadowMap` (`main.js:25-36`).
2. Linear fog `Fog(PAL.fog, 44, 205)` (`:39`), camera FOV 46°, near 0.25, far 600 (`:41`).
3. Four lights (`:45-75`): a warm sun with a 2048² shadow map in an ortho box of ±34 m, a cool fill from the opposite side (1.08), a weak bounce from below (0.34) and a hemisphere light with a purple ground.
4. `buildSky()` and then `buildWorld()`. **The whole world is built synchronously at startup**: all builders, the merge and finally the bending onto a planet (`world/index.js:737`). There is no streaming and no LOD.
5. `frame()` (`main.js:207-253`) does:
   - `dt = min(clock.getDelta(), 1/20)`
   - `player.update`, `ebike.update`, `world.update` (crossing sequence, train, closure "updaters", CPU update of the petals)
   - **moves the lights into the local tangent frame of the planet under the player** (`seatLight`, `:150-157`, `:233-238`). The authors themselves call this a "physical cheat": wherever the player walks, the lighting looks the same.
   - moves the sky dome and the clouds together with the camera
   - does a raycast pick of interactive objects and updates the HUD
   - calls `pipeline.render()` and `requestAnimationFrame`
6. Keys: `O` and `G` switch the ink and grade passes off (`:203-204`), `P` toggles the orbital view of the planet.

## Architecture

### Modules
- **`core/`** is the "engine": materials (`toon.js`), post pipeline (`post.js`), outlines (`outline.js`), textures (`textures.js`), palette (`palette.js`), helpers and merge (`util.js`), sky (`sky.js`), player and collisions (`player.js`), HUD and audio.
- **`world/`** is the content:
  - **generator libraries:** `shops.js` (`makeShop`), `vehicles.js` (`makeVehicle`), `buildings.js` (`makeHouse`, fences and walls), `props.js` and `streetprops.js` (dozens of `makeX()`), `trees.js` (sakura, groves, cedars, bamboo, bushes)
  - **terrain:** `street.js` (height profile and terrain grid), `landform.js` (canal trench), `hills.js` (hill lattice), `lakeform.js` and `lake.js` (lake), `planet.js` (sphere and bending)
  - **~25 "district" modules** (`ichome.js`, `nichome.js`, `onsen.js`, `school.js`, …). Each places objects at specific coordinates **by hand**.
  - **two global "sweeps"**: `district.js` (furnishing the houses) and `traffic.js` (placement of all 18 cars in one table, so the distribution can be judged)

### How the generators are organised
All generators have the same shape:
```js
export function makeX(o) {          // o = plain object, everything has a default via ??
  const m = mats();                 // lazy cache of the module's materials
  const rng = rngKit(o.seed ?? N);  // deterministic PRNG per instance
  const parts = { wall:[], roof:[], trim:[], metal:[] /* …per material */ };
  const push = (k, geo, mx) => parts[k].push({ geometry: geo, matrix: mx });
  // … hundreds of push(…) with BoxGeometry/Extrude/Cylinder + trs(…) …
  for (const k in parts) g.add(new THREE.Mesh(bake(parts[k]), matFor[k]));
  g.position.set(o.x, o.y, o.z); g.rotation.y = FACE_RY[o.face];
  ctx.add(g); ctx.collide(…AABB…); return g;
}
```
The principle is **"bucket per material, then merge"**. One shop thus ends up as roughly 6 to 8 draw calls plus unmerged decals (signs, glass, interior plane).

### Data flow and world assembly (`world/index.js`)
- `buildWorld` creates **`ctx`** (`index.js:91-134`) with the callbacks `add`, `collide(x0,z0,x1,z1,top,bottom)`, `platform`, `cut`, `groundAt(x,z)`, `interact` and `update`. Builders therefore do not return data, they **write into shared lists** (colliders, platforms, cuts, interactables, updaters).
- **Order matters** (`index.js:249-327`, every step is commented). Hills go before the tunnel, the tunnel before the school, the lake before the shores, residential blocks before `buildDistrict`, cars only after all surfaces, because they settle via `ctx.groundAt`.
- Districts return **lists of spots for vegetation** (`sakura`, `grove`, `cedar`, `bamboo`, `petals`). These are collected and **planted at once** (`index.js:329-337`, `509`), so the whole world has one merged mesh of trunks and three instanced crowns.
- At the very end **`bakeToPlanet(root, { maxEdge: 4.0 })`** runs (`index.js:737`): the flat world is bent onto a sphere.
- Ground height: `heightAt(x, z, fromY)` = analytic `streetHeight + reliefAt + hillAt`, then `min` over the cuts and `max` over the platforms, only those within step reach of `fromY` (`index.js:773-793`). Thanks to this you can walk on the footbridge and also under it.

### Configuration and tables
- **`PAL`** (`core/palette.js`): over 210 named colours in one file. A narrow palette (warm off-white, grey-violet road, green to turquoise, light pink) and four saturated accents reserved for focal objects.
- **Def tables directly in code**: `houseDefs` (`index.js:144-232`), `poleDefs`, `sakuraSpots`, car `SPEC`, `traffic.js` (44 lines of `kind: '…'`), `PADS` and `KEEP` terrain masks. No JSON or data files, everything is a JS literal.
- Determinism comes from `mulberry32` and `rngKit(seed)` (`util.js:17-39`) with a seed on every object.

## Rendering pipeline

### Pass order (`core/post.js:270-296`)

| # | Pass | Target | Format | Note |
|---|---|---|---|---|
| 0 | Shadow map (three.js internal) | 2048² depth | – | one directional light, ortho ±34 m, PCF, bias −0.0004, normalBias 0.035 (`main.js:47-56`) |
| 1 | Scene (forward) | `rtScene` | **RGBA16F** + `DepthTexture` UInt32, Nearest | all materials, fog, sky dome (`post.js:211-224`) |
| 2 | **Ink** (fullscreen) | `rtA` | RGBA16F | reads colour and depth, ink from the second difference of linear depth (`post.js:22-98`) |
| 3 | **Grade** (fullscreen) | `rtB` | **RGBA8** | split-tone, warmth, lift, saturation, vignette and manual linear→sRGB (`post.js:100-144`) |
| 4 | **FXAA** (fullscreen) | backbuffer | – | simplified FXAA (5 luma taps and 2+2 samples along the direction, `post.js:146-190`) |

- Inverted-hull outlines are drawn **within pass 1** as a back-face shell with `renderOrder − 1` (`outline.js:72-105`).
- The colour pass is **pure forward** (MeshToonMaterial). There is no deferred, no G-buffer and no normal buffer.

### Resolution and AA (`post.js:243-268`)
- **Supersampling with a pixel budget:** `scale = forceScale || (dpr < 1.5 ? 1.5 : min(dpr, 2))`. When `w·h·scale² > 4.6 Mpx`, the scale is reduced to `sqrt(budget / (w·h))`.
- The internal RTs have the size `w·scale × h·scale`, but the **canvas runs in CSS pixels** (`setPixelRatio(1)`). On a HiDPI display it therefore renders 2× internally, the FXAA pass downsamples it bilinearly to 1× CSS and the browser then upscales again to physical pixels. Native resolution on a retina screen is never reached. The result is SSAA to CSS resolution.
- Ink thickness scales with resolution: `uThickness = 1.05 + 0.55·scale` (texels of the internal RT), so the line is roughly 2 output pixels wide (`post.js:267`).
- AA is a combination of mild SSAA (1.5–2×) and FXAA. MSAA is off (`antialias:false`).

### Materials (`core/toon.js`)
- **`cel(opts)`** (`toon.js:88-133`): `MeshToonMaterial` with `gradientMap(bands)`, `flatShading: true` by default, with a patched shadow hue. Cached by a **signature of the parameters** (`toon.js:108-112`). Materials with a map are not cached (`cache:false` appears 307× in the code).
- **`flat(opts)`** (`toon.js:138-161`): an unlit `MeshBasicMaterial` for sky, glass, emissive panels, signs, ink and interiors behind glass.
- The code has **888 calls of `cel({…})`** and **76 different `tint` values**. Every tint is a **separate shader program** because of `customProgramCacheKey` (`toon.js:78`). For us this is an anti-pattern (see below).
- There are practically **no surface textures.** Walls, roads, roofs and cars all have one flat colour. Textures are only signs, decals and "interiors".

### Lighting model
- **Toon BRDF** from three.js: `coord = dot(N, L) · 0.5 + 0.5` (half-Lambert), then a lookup into a 1D ramp with `NearestFilter`.
- A **patch** of `lights_toon_pars_fragment` (`toon.js:48-63`) tints the dark bands purple, see Key techniques.
- Ambient is a hemisphere light (`PAL.hemiSky` 0xdcecff, `PAL.hemiGround` 0xb6a6c6, intensity 1.12) plus two non-shadow-casting directional fill lights. This guarantees that "nothing in shadow ever goes black".
- Only the sun casts shadows. Some objects deliberately do not cast or receive shadows:
  - the planet does not cast, otherwise its own far hemisphere would shade the world (`planet.js:594-596`)
  - sakura crowns do not receive, so they do not go grey (`trees.js:172-185`)
  - transparent objects do not cast (`util.js:123-132`)
  - thin ledges do not cast, because of jagged shadows (`CLAUDE.md`, section Traps)
- **Mismatch between comment and code:** the header of `main.js:19-20` claims the shadow camera "follows the player on a snapped grid". But the code (`main.js:234-235`) has no texel-grid snapping, the light moves continuously with the player. So shimmering of shadow edges is to be expected when walking.

### Post
- **Ink:** see Key techniques.
- **Grade** (`post.js:122-141`):
  ```glsl
  float l = dot(c, vec3(0.2126, 0.7152, 0.0722));
  float k = smoothstep(0.02, 0.55, l);
  c *= mix(uShadowTint /*0xada8d0*/, uLightTint /*0xfff7e8*/, k);  // split-tone
  c += vec3(uWarmth, uWarmth*0.45, 0.0) * l * 0.35;               // warm tint
  c += uLift * (1.0 - k);                                          // never black
  c = mix(vec3(l), c, uSaturation /*1.12*/);
  c *= 1.0 - uVignette * pow(clamp(length(uv-0.5)*1.42,0,1), 2.6);
  ```
- **Sky** (`core/sky.js:12-56`): a back-face sphere, a 3-stop gradient (haze, mid, top) and a **soft quantisation** `t = mix(t, floor(t·26)/26, 0.35)`, which gives "airbrush" bands. The clouds are 22 billboard pairs of planes (a light front one and a darker back one, offset) with a Canvas2D texture of ellipses with a cut-off bottom (`textures.js:461-480`).
- **Fog** is linear 44–205 m. The ink fade runs 40–98 m, so the background dissolves into haze before it would thicken with lines.

## Key techniques in depth

### 1. Toon ramp and hue-shifted shadows
- **File:** `src/core/toon.js:15-80`
- **How it works:** ramps are 1D `DataTexture`s with `NearestFilter`:
  ```js
  const RAMPS = { 2:[96,255], 3:[92,178,255], 4:[80,142,202,255], 5:[74,124,172,214,255],
                  soft:[180,255], soft3:[172,214,255] };   // soft = light masses (blossoms)
  ```
  The patch replaces one line of the three.js shader:
  ```glsl
  // originally: vec3 irradiance = getGradientIrradiance(N, L) * directLight.color;
  vec3 celBand    = getGradientIrradiance( geometryNormal, directLight.direction );
  vec3 irradiance = celBand * mix( uShadowTint, vec3(1.0), celBand ) * directLight.color;
  ```
  In the formula `E = b · lerp(tint, 1, b) · L_color`, `b` is the band value of the ramp (0.36 / 0.70 / 1.0). For `b = 1` the result is the pure light colour. For a dark band it is a `b²`-ish darkening **multiplied by a purple tint** (typically `0x6f6790`, `0x5c5680`, `0x6a6288`). So besides darkening, the shadow also changes hue. The tint is per material: blossoms have pink tints (`0xe2c3d2`…) so they do not go grey, rusty things are warmer.
- **Combination:** the result is summed over three directional lights (sun, fill, bounce) plus the hemisphere. A shadow from the shadow map zeroes the sun's `directLight.color`, so the purple fill and hemi remain in shadow. That is why cast shadows are blue-violet, not grey (clearly visible in `docs/hero-1-crossing.jpg`).
- **Cost:** negligible ALU, one texture fetch per light. The real cost is in the **number of programs**: 76 tints × additional defines.
- **Limitations:**
  - The patch is a string replace in a three.js chunk (`src.includes(TOON_LINE)`), so it silently stops working on a three upgrade (`patchAvailable`).
  - The ramp is global, not per light.
  - `flatShading: true` everywhere, so the tone is quantised per facet. On the planet sphere this produced a stair-stepped terminator, so the authors forced radial normals there (`planet.js:567-586`).

### 2. Ink lines from the second difference of linear depth
- **File:** `src/core/post.js:22-98`
- **How it works:**
  ```glsl
  float dc = linearDepth(uv);  if (dc > uSkyDepth /*420*/) return col;   // sky without lines
  float sx = (dl + dr - 2.0*dc) / dc;     // 2nd difference, normalised by distance
  float sy = (du + dd - 2.0*dc) / dc;
  float convex  = max(0.0, sx) + max(0.0, sy);   // silhouettes, convex edges → strong
  float concave = max(0.0,-sx) + max(0.0,-sy);   // inner corners → weak (×0.42)
  float edge = smoothstep(uSens*0.32, uSens /*0.0042*/, convex);
  edge = max(edge, smoothstep(uConcave /*0.026*/, uConcave*3.4, concave) * uConcaveAmount);
  edge *= 1.0 - smoothstep(40.0, 98.0, dc);          // fade into haze
  vec3 line = mix(uInk /*0x39324f*/, col * 0.42, 0.22);  // the ink keeps a bit of colour
  ```
  The first difference would draw a smear on slanted surfaces, for example on a road seen at a sharp angle. **The second difference is zero on any plane** regardless of angle, so it reacts only to real silhouettes and breaks. The asymmetry between convex and concave imitates the animators' "contact lines", which are weaker.
- **Cost:** 5 depth taps and 1 colour tap per pixel at the (super-sampled) resolution. Cheap.
- **Limitations:**
  - It **sees only depth.** It will not draw an edge between two coplanar surfaces of a different colour or material. The authors work around this with geometry ("parapet, so a flat roof still has an edge to ink", `shops.js:~107`) and deliberate offsets (the shoulder line of cars, `vehicles.js` comment at `CW`). A lot of "detail" in the geometry exists only so the ink has something to find.
  - Thin and transparent things (petals, wires) must have `depthWrite:false`, otherwise they produce ink dots (`CLAUDE.md`, Traps).
  - The normalisation `/dc` and the fixed thresholds are tuned for near 0.25 and far 600.

### 3. Inverted-hull outlines (hero props)
- **File:** `src/core/outline.js`
- **How it works:** a back-face shell is added to the mesh and its vertices are shifted **in clip space** along a smoothed normal, so the line has a constant width in pixels:
  ```glsl
  vec4 clip  = projectionMatrix * mv;
  vec3 clipN = normalize((projectionMatrix * vec4(n, 0.0)).xyz);
  clip.xy += clipN.xy * vec2(res.y/res.x, 1.0) * uThickness * clip.w * 0.5;
  ```
  The normals are smoothed via `mergeVertices(geo, 1e-4)` and `computeVertexNormals()`, with a cache in a WeakMap (`:51-66`). Without this the shell would tear at the edges of boxes. InstancedMesh is supported too, where the shell shares `instanceMatrix`.
- **Where it is used:** train, crossing barriers, vending machines, kei truck. **In `makeShop`, though, also on all the merged `wall` and `roof` meshes** (`shops.js:379`). In total 150+ calls (`school.js` 26, `props.js` 18, …).
- **Cost:** **+1 draw call per outlined mesh** and the same number of extra triangles. The authors measured this themselves and turned the hull off for cars: "fifty extra shells is fifty extra draw calls in a scene that is measurably draw-call bound" (`vehicles.js:63-70`). According to `NEXT.md:1225` the hull on cars made +100 to +184 draw calls per view.
- **Limitations:** the clip-space shift breaks on concave shapes, smooth normals require welded geometry and the shell does not cast a shadow.

### 4. Procedural Canvas2D textures
- **File:** `src/core/textures.js` (4 397 lines, **135 exported generators**)
- **How it works:** `make(w, h, draw, {srgb, repeat, aniso})` creates a canvas, calls `draw(ctx2d)` and wraps the result in a `CanvasTexture` (`textures.js:16-32`). Results are cached by a key `cached('shopSign', …)`. There are also helpers `fitText` (shrinks the font until the text fits), `centered` (with letter-spacing) and `vertical` (vertical Japanese writing).
- **Kinds of textures:**
  - **signs and plates** (about 70 %): shop fascias, vertical signs, noren, menus, timetables, maps, vending machine price tags, street names, licence plates
  - **"interiors" behind glass**: `shopInterior` (shelves, cooling cabinets, counters), `litWindowTex`, `classroomTex`, `gymInterior`, `tatamiRoom`. These are flat 2D paintings on a plane set in a recess, darkened toward purple.
  - **masks and alphas**: `petalTex` (a bezier petal), `cloudTex`, `chainLinkTex` (chain-link fence as an alpha grid; mipmaps blur it in the distance into a "light veil" instead of moiré)
  - **repeated patterns**: `tactileTex` (tactile paving), `shutterTex` (blinds), `roadPaint` (止まれ, arrows, diamond)
  - The most common sizes are 512×256, 384×512 and 512×384, the maximum is 1024×256.
- **Explicit rule:** "crisp shapes and type, **never photographic noise**" (`textures.js:10`). No noise, no surface materials.
- **Cost:** CPU at startup, tens of MB of uncompressed textures. Every mapped texture is its own material, so its own draw call and bind, because nothing is atlased.
- **Limitations:** dependence on system fonts (non-deterministic across OSes), no atlases, no surface detail (brick, plaster, asphalt).

### 5. Shop and building generator (`makeShop`, `makeHouse`)
- **Files:** `src/world/shops.js:64-395`, `src/world/buildings.js:51+`
- **How it works (`makeShop`):**
  - Parameters: `x, z, y, w, d, face ('z+'|'z-'|'x+'|'x-'), kind (tenant), floors (1|2), h1, h2, roofKind ('gable'|other), recess, openW, awning, shutter (0..1), wall/roof (index into the palette), fascia, signBox, interiorMap`.
  - It is **always authored facing +Z** and the whole group is then rotated by `face`. The comment justifies it: "far less error-prone than branching on an axis inside every measurement".
  - The main volume is a box that **ends 0.9 m before the street line**. The resulting hole is framed by **piers and a lintel**. The recess gets: an interior plane (`flat`, darkened `0x8b8598`), glass with opacity 0.22, mullions and one slanted reflection (`shops.js:118-176`). The authors: "a glazed decal on a solid box reads as a sticker, every time".
  - The roof is either a gable (2 sloped slabs, a ridge and extruded gable triangles) or flat with a parapet, so the ink has an edge.
  - Optionally a half shutter (`shutter≈0.35`, "back in ten minutes"), a fascia or light box, an awning, lanterns, a menu, flowers.
  - Geometry is collected into `parts = {wall, trim, roof, metal, metalDark, tile}`, then `bake()` is called per key and a hull on wall and roof (`shops.js:374-380`). An AABB collider in world axes follows (`:386-391`).
- **Scope of use:** 15 calls of `makeShop` in 7 files ("one generator, nine tenants"). `makeHouse` has 6 call sites, but these pass whole def tables (`houseDefs` ~25 houses).
- **Cost:** roughly 6–8 merged meshes, 2 hulls and dozens of small unmerged meshes (signs, glass, lanterns, menus) per unit.
- **Limitations:** it is a parametric template, not a grammar. One type of mass (a box, optionally with a 2nd-floor setback), no general facade subdivision, no windows as a repeated module. Placement is **manual**: every unit has its coordinates set in a district module.

### 6. Vehicle generator (table-driven)
- **File:** `src/world/vehicles.js` (822 lines)
- **How it works:** a car type is a **row of the `SPEC` table** (`:132-223`), not a function. There are nine types: kei, keivan, hatch, sedan, wagon, minivan, van, boxtruck, minibus. A row describes only what the car "reads" as, according to the authors:
  ```js
  kei: { L:3.40, W:1.475, R:0.275, axle:[1.16,-1.19],
         sill:0.38, waist:1.00, roof:1.70,            // bottom, beltline, roof
         cab:[-1.60, 1.15], rakeF:0.42, rakeR:0.14,    // where the glazing starts + rake
         seams:[0.12,-0.80], handles:[-0.60,-1.40] },
  van: { …, side:[0.70,1.62] /* glazing only above the cab = van vs. minivan */ },
  boxtruck: { …, box:{ x0:-2.40, x1:0.28, y0:1.06, y1:2.46 } },
  ```
  Everything else is **derived**: wheel arches, bumpers, lights, licence plates, seams, handles, mirrors, wipers, wheels (tyre, rim 10 mm above the side, nuts).
  - The key primitive is `panel(arr, ax, ay, bx, by, w, t)` (`:245-253`): a **panel between two points of the side profile**. The angle is computed from the end points, not from a "guessed tilt", because according to the authors the box tilt was "inverted half the time".
  - Glass is placed **on** the wedge and shifted by 62 mm along the outer normal ("depth is built outward"). Otherwise it ends up inside the body.
  - The cabin is 0.14 m narrower than the body. The resulting step (the "shoulder line") gives the ink a horizontal line.
- **Output:** 7 merged meshes (body, deep, dark, brite, glass, lampF, lampR) plus the licence plate. A hull only with `o.hero`.
- The **`CAR` palette** (`:82-104`) contains real Japanese colours. Dark colours are **deliberately lightened**, because the rear of a car always faces away from the sun and the lower band of the ramp would merge it with the ink.
- **Placement** is in one table in `traffic.js` (18 cars, 8 on the roadway) with six rules ("never two cars facing each other across the roadway", "no two in the same shot at the same distance").
- **Cost:** roughly +100 to +184 draw calls per view for the whole fleet (`NEXT.md:1356-1366`).

### 7. Terrain: hill lattice, slope limiter, lake and leak check
- **Files:** `src/world/hills.js`, `src/world/lakeform.js`, `src/world/street.js`
- **Terrain layers:**
  1. `street.js`: an analytic profile `groundY(z)` (`street.js:75-77`, smoothsteps by z) and a 2 m terrain grid. The triangles of the canal trench are cut out of the grid (`cutTrench`).
  2. `planet.js`: a sphere 65 mm below the grid.
  3. `hills.js`: a **third surface above both**, which shows only where the field is positive. The boundary is the contour `field = 0`, a line and not a surface, so it has nothing to z-fight with.
- **Lattice:** `CELL = 1.5 m` (`hills.js:168`), a triangle mesh with a jittered diagonal (`flipped(i,j)`). The height is computed **only at nodes** (`nodeAt`) and `fieldAt` interpolates linearly over the same two triangles the mesh has (`:1796-1820`). **Walking and rendering are therefore served by an identical surface, bit for bit.** Flat shading, so every facet edge is a break that the ink pass draws.
- **Shape:**
  - the peaks are quartic bumps `h·(1−d²)²` on ellipses, combined by **screen blend** instead of a sum (two overlaps give a ridge, not double height)
  - a 2.6 m pedestal `PED` is subtracted from them, which determines where the slope starts
  - a keep-out mask over built-up area
- **Slope limiter** (`hills.js:1569-1640`): a relaxation that **only lowers**:
  ```js
  for (pass < 140) { worked = false;
    for each node k: cap = min over 4 neighbours ( NODES[n] + max(drop[k], drop[n]) );
                     if (cap < h) { NODES[k] = max(-SKIRT, cap); worked = true; }
    if (!worked) break; }
  // drop = slopeLimitAt(x,z)·CELL: 1.9 in the railway/canal corridor, otherwise 0.52
  ```
  Because it only lowers, all the guarantees are preserved (keep-out stays 0). It converges to the highest surface below the proposed one whose gradient is within the limit everywhere.
  - **A trap they describe:** a limiter pinned along a straight line produces a perfectly flat ramp like an embankment. The fix is to have steps in the keep-out boundary, so the foot can go diagonally.
  - After the limiter up to **three octaves of undulation** are added. The amplitude is proportional to the height (`h/2.4`, `h/1.6`, `h/0.7`), clamped to ≥ 0 so the hollows do not invert.
- **Toning without textures** (`faceTone`, `hills.js:2052`): every facet gets one of five tones according to slope, orientation to the sun (`lit`), height, the "cover" field and the jitter `tj`:
  - bare earth: slope > 0.88 + …
  - ススキ / bracken: drier cover
  - sunny lawn, medium and damp dark tone: by `key = lit + (h−7)·0.022 + cover·0.55`

  Every tone is a **separate non-indexed mesh**, neighbouring facets share exact positions, so no seams appear. The authors measured a distribution of 8/10/27/24/31 %.
- **Lake** (`lakeform.js`): the water is a **flat plane above the datum** (`LEVEL = 3.40 m`, `:119`) and is hidden wherever the terrain is higher. **The shore is the contour `field = LEVEL`**, so it is irregular for free. The depth `LEVEL − field` drives reeds, water lilies, tone bands and piers. The rim of the basin is derived from an authored shore polygon (`rimAt`) with a slope ≤ 0.50, so the limiter does not eat it.
- **Leak check** `lakeLeakCheck` (`lakeform.js:740-779`): a BFS flood fill of the area `field < LEVEL` from a seed in the middle of the basin on a 1.5 m grid. It returns how far beyond the shore the fill reached (`escaped > 30 m` means a leak) and the flooded area (compared with `lakeStats`). There is also **`hillSafety(world)`** (`hills.js:1910`), which samples `hillAt` over all colliders and platforms and reports the worst overlap of a hill into the buildings. Both functions are exported, but **they are not called anywhere in `src/`**: they are run manually from the console or from Node.
- **Cost:** the hills have ~45 000 nodes, ~60k triangles after bending and 6–8 draw calls (according to `hills.js:185-190`).
- **Limitations:** a height field has no holes, so tunnels are separate geometry with a "notch" in the lattice (`inNotch`) and caps. Three surfaces with gaps of 15–65 mm were a source of dozens of bugs (documented in `planet.js:413-446` and `hills.js:1574-1590`).

### 8. Bending the world onto a planet
- **File:** `src/world/planet.js`
- **Mapping:** equirectangular, `R = 160 m` (`:31`), centre `(0, −R, 0)`. `x` corresponds to longitude (circumference 1005 m), `z` to latitude. The railway lies on the equator (z = 0), so it is a great circle that closes without deformation.
  ```js
  normalAt(x,z) = ( sin(x/R)·cos(z/R), cos(x/R)·cos(z/R), sin(z/R) )
  positionAt(x,y,z) = CENTER + normalAt(x,z)·(R + y)
  basisAt: up = normal, east = (cos λ, −sin λ, 0), north = (−sin λ sin φ, −cos λ sin φ, cos φ)
  ```
- **`bakeToPlanet`** (`:269-366`) runs once at the end and the builders know nothing about the planet:
  - **regular meshes:** the geometry is converted to world space, then `subdivideLongEdges(maxEdge=4 m)` repeatedly halves the longest edge of a triangle (at most 12 passes), including **preserving material groups** (`:121-230`; losing them once made 54 signs invisible). Finally every vertex is remapped through `positionAt` and the normals are recomputed. The mesh gets an identity transform and **exact frustum culling** (the bounding sphere is already in world space).
  - **InstancedMesh:** each instance is rigidly re-seated on the surface (rotation of the tangent frame × the original rotation) and is **never culled**.
  - **`planetRigid`:** animated rigs (crossing barriers, cat, train wheels) stay in the plane and the whole group is re-seated at once, so the pivots survive.
  - The **train** (`train.js:407-425`) rotates around the planet axis `T(C)·Rz(−x/R)·T(−C)`.
- **Inverse `flatAt`:** gameplay (collisions, heights, player) runs entirely in flat coordinates and only the camera and render are on the sphere.
- **Sphere:** `IcosahedronGeometry(R, 30)`, 5.4 m facets with a sagitta of 30 mm, 19 220 triangles. The normals are **radial, not facet**, so the terminator is not stair-stepped. Triangles are cut out of the sphere under the canal trench.
- **Effect:** at an eye height of 1.62 m the ground horizon is `sqrt(2Rh) ≈ 23 m`. The small planet thus **clips the view distance by itself** and replaces the distant city, hills and tree line, which were deleted (`index.js:339-341`).
- **Cost:** subdivision in JS at startup. Everything is non-indexed (3 vertices per triangle). Anything that goes around the whole planet is not culled: the railway sends ~900k triangles every frame, wherever the camera looks.
- **Limitations:** the equirect converges toward the poles (a district with |z| < 60 m has < 5 % compression), the lights are pinned to the local frame and the scale is toy-like.

### 9. Bake, merge and instancing
- **`bake(parts)`** (`util.js:46-74`): clones the geometries, applies the matrices, reconciles indexed and non-indexed (when mixed, it converts everything to non-indexed), keeps only the common attributes and calls `mergeGeometries`. The result is **one draw call per material and object**.
- **Vegetation of the whole world:** one merged mesh of trunks and branches plus **three InstancedMeshes of crowns** (three blossom tones), whose instances are icosahedra of detail 1 (`trees.js:20-190`). Each tree has 26–35 blobs and the tone is chosen by height in the crown (light on top, dark at the bottom, a 22 % random shift). Groves, cedars, bamboo and bushes use the same pattern.
- **The "multi-part prop instancing" pattern** (`makeBikeRack`, `props.js:844-880`): one bicycle is baked into **three geometries by material** (dark, frame, brite) and each is instanced across the whole row. The frame colour changes per instance. The authors explicitly write that `makePlanter` (11 meshes) and `makeBicycle` (14 meshes) have not been converted to this style yet and that it is a "~1000 draw calls" saving.
- **Petals:** 980 instances in three InstancedMeshes with `DynamicDrawUsage`. The **update runs on the CPU every frame** (`petals.js:80-110`): a matrix per petal and an upload of the whole buffer. A passing train "blows them away" (`train.gust`).
- The material cache by signature means that shared materials let three.js sort by program.

### 10. Characters and animation
- **There are no characters** and it is deliberate: "no depictions of people anywhere" (README). The code has no SkinnedMesh, no AnimationMixer and no bones.
- Animations are purely **procedural transforms** in `ctx.update` closures:
  - the cat (`index.js:661-685`): sinusoidal breathing and tail twitching, a "stretch" on interaction via exponential smoothing `stretch += (target − stretch)·(1 − exp(−dt·3.5))`
  - crossing barriers and lights driven by the **position of the train on the circle**, not by a timer: one lap is one cycle (`index.js:699-732`)
  - train wheels, shutter, vending machine (a falling can)
  - the e-bike with lean in turns (`ebike.js`)
  - the player's head bob (`player.js:297-314`)
- **Player:** FPS with pointer lock, eyes at 1.62 m, circle R = 0.34 m. Collisions are a push-out of the circle against a **linear list of AABBs** with `top`/`bottom`. Step height 0.38 m (`player.js:18-20, 172`). The height is taken from `world.heightAt(x, z, fromY)`.
- **Trap:** once the bake "folds" a mesh into root space, its `rotation` no longer rotates it around its own pivot (the train wheels then orbited the world origin). Animated parts must have a `planetRigid` hub (`CLAUDE.md:728`).

### 11. Dev tooling: `__shot` and verification
- **`POST /__shot`** (`vite.config.js:8-38`): a dev-only middleware accepts JSON `{name, data: dataURL}` and writes a JPG into `.shots/`.
- **`window.__shot(name, W, H, opts)`** (`main.js:265-329`):
  - `opts`: `pos`, `y`, `yaw`, `pitch`, `orbit/tilt/dist` (planet view), `ink`, `grade` (pass switches), `scale` (forced supersampling), `outW`, `quality`
  - the function re-syncs the camera with the player, re-seeds the lights, renders one frame at the given resolution, downsizes it via a 2D canvas, sends it to the server and returns the file path
- **Workflow according to `CLAUDE.md` §"Verifying visual changes":**
  - the agent could not screenshot the browser, because it was not composited and rAF did not run, so it **steps the world by hand** (`for … world.update(1/60)`) and then calls `__shot`
  - there is a list of about **60 named cameras** ("an establishing shot of each district"), which are shot before and after every visual change, as manual golden images
  - **"Can this be seen?" is answered by a raycast, not a screenshot**: builders are imported in Node, `document` is a stub that no-ops all Canvas2D calls, and a ray from the eye finds which mesh covers the target
  - numerical invariants: `hillSafety` (hill overlap into buildings, target 0.00), `lakeLeakCheck` (water leak), **FLOODFILL** lists in the district headers (e.g. `nichome.js:106-120`: points that must be reachable on foot from the spawn; the flood-fill tool itself is not in the repo)
  - draw-call measurement on a fixed set of views, with a table in `NEXT.md` at every change
- The table **"Traps that have already bitten"** (`CLAUDE.md:721+`) summarises dozens of concrete bugs with cause and symptom.

## Performance

### What they do against draw calls
1. **Merge per material per object** (`bake`) in all generators. `bake(` is called 30× in `nanachome.js` alone.
2. **Instancing** of repeated elements: sleepers, fence posts, blossom blobs, cedar whorls, petals, wheels in racks, ema plaques, reeds, ivy. Vegetation is collected globally into one set of instances.
3. **Exact frustum culling** of baked meshes. According to the authors, turning it off cost **~8 ms** at ~5000 meshes.
4. **No hull where it cannot be seen** (cars, except the hero kei truck).
5. **Bounded extents** of long geometry: the canal was shortened to 204 m so it could be culled, which saved 134k triangles.
6. Shared materials through the signature cache, one licence plate material for all cars.

### Memory
- The authors do not measure it. An estimate from the code: everything is **non-indexed** (`subdivideLongEdges` calls `toNonIndexed`, the hill meshes are non-indexed on purpose). 1.74M triangles is therefore ~5.2M vertices × (position + normal + often UV) ≈ 24–32 B, in total **~125–170 MB of vertex data** (my estimate, not a measurement).
- On top of that tens to hundreds of uncompressed Canvas textures (RGBA8, 512×256 ≈ 0.5 MB, with mipmaps ~0.7 MB).

### What NOT to take and why
1. **The R = 160 m equirect planet and lights pinned to the local frame.** It works only as a toy: a 23 m horizon, converging poles, a sun that "travels with the player". For a large procedural planet we need a cube-sphere, a real sun and cascaded shadows.
2. **Synchronous build of the whole world at startup, with no streaming and no LOD.** Unusable for a GTA-like city. We use a region → district → cell hierarchy with streaming.
3. **Hand-entered coordinates in code** (`houseDefs`, hundreds of `{x, z, …}` with comment essays). The 49k lines of `world/` are mostly manual composition and the "generators" are thin templates. It does not scale. We generate (tensor-field streets, CGA) and only curate by hand.
4. **Non-indexed geometry everywhere** (3× more vertices). We do flat shading differently: a `nointerpolation` normal with a provoking vertex, or a normal from `ddx/ddy(worldPos)` in the pixel shader, and indexed buffers stay.
5. **String-patching of shaders (`onBeforeCompile`) and a program per tint.** For us the tint is data.
6. **Inverted hull on all shop walls and roofs.** Every hull is a draw call. For us only screen-space lines (depth, normal, ID) and a hull for at most a few hero objects, ideally in the same instanced draw with a second pipeline.
7. **Instanced meshes without culling and a CPU update of petals over the whole buffer every frame.** For us culling per cell and particles in a compute shader.
8. **Three stacked ground surfaces with micro-gaps of 15–65 mm** against z-fighting. A source of dozens of bugs (the sphere poking through the road, surfaces in the canal). For us one heightfield per cell with explicit "holes" (tunnels, trenches) as mesh patches and with one height function for render and physics.
9. **System fonts** (the result differs by OS) and **uncompressed, unatlased textures with a material per sign.**
10. **A linear list of AABB colliders** (783 boxes + ~600 trees walked every frame). For us a spatial hash per cell.
11. **Simplified FXAA on a bilinearly downsized SS buffer.** For native resolution we need SMAA/TAA.
12. **Documentation as 30 % comments in the code.** The lesson "write down why, with numbers" is good, but it belongs in `docs/` and in lints, not in 50-line essays above a constant.

## How it achieves quality

### What is visible in the screenshots (`docs/hero-1…4.jpg`, 1600×900)
- **hero-1 (crossing):** train, barriers, vending machines, 止まれ on the road, sakura. Strong composition and legible layers (foreground, middle, background). Purple tree shadows on the asphalt, bright black-violet outlines, petals in the air.
- **hero-2 (shotengai):** the perspective of the alley, awnings, a "そば" noren, lanterns on wires, a van, bicycles in a rack, a sakura at the end as a focal point. Lots of signs.
- **hero-3 (onsen street):** wooden facades, vertical signs "こけし堂", lanterns, a kokeshi on a table, a stone lantern as a focal point.
- **hero-4 (shrine):** torii, steps, stone lanterns, bamboo, shimenawa.

### Why it looks good
1. **A coherent style instead of realism.** A narrow palette, coloured (not grey) shadows, ink lines and a split-tone grade unify otherwise very simple geometry (boxes, cylinders, icosahedra) into a "painted background". According to the authors the hue shift in shadow is "most of what separates anime cel from low-poly 3D" and the screenshots prove them right.
2. **Signs carry the detail.** Japanese typographic signs on every facade replace texture detail. The eye reads text and signs, not the surface.
3. **Composition and manual placement.** Every thing stands where it does work in the shot ("the pole that carries the eye up out of frame", `index.js:65-73`). This is the strength of the screenshots and at the same time a weakness for scale.
4. **Depth instead of stickers.** Shop recesses, glass in front of the interior, a cabin narrower than the body, parapets on flat roofs. The geometry is built so the ink and shadow have something to draw.
5. **Clean shadows.** A 2048² map over ±34 m ≈ 3.3 cm/texel. Sharp cast shadows of trees are one of the strongest elements of the image.
6. **Atmosphere:** fog, ink fade, a slightly quantised sky gradient and flat clouds. The background dissolves in a "painterly" way.

### An honest comparison with our bar (GTA III / World of Warcraft)
- **Where Sakura is above GTA III:** legibility, palette coherence, the "appeal" of a static shot. As a stylised picture it feels more mature than raw GTA III.
- **Where it is below the bar:**
  - **Surfaces without textures.** WoW stands on hand-painted textures (plaster, stone, wood, grass) and GTA III on photo textures. Sakura has one colour on walls, roads and roofs. In motion and up close (hero-3 on the left: large grey areas) it is empty. **Key for us: AI textures + code post-processing are necessary. This style is only half a solution.**
  - **Vegetation as "balloons".** Clusters of faceted icosahedra work well in an anime look, but WoW trees (alpha cards with painted foliage) are a class richer.
  - **No characters, NPCs or moving traffic.** GTA III is about people and cars in motion. Here 18 parked cars stand still and the whole area has not a single person.
  - **Scale.** A planet circumference of 1 km, a district ~120 m across, a horizon of 23 m. In size it is closer to a diorama than a city. Even so they measured **2.5–10k draw calls per view** and ~20 ms on the crossing. At the density of a GTA city (hundreds of buildings in shot, view distance 300+ m) this approach (merge per object, not per cell) **would not pass**.
  - **AA and resolution:** SSAA + simplified FXAA into CSS pixels. Native resolution on HiDPI is not reached. The shadow camera does not snap to texels, so shimmering is to be expected.
- **For us this means:** take the **style layer** (ramp + tint, ink, grade, palette, signage, "depth built outward") and the **verification culture**. Do not take the **world architecture** (manual composition, bake of the whole planet, planet-scale merged meshes). We will meet the GTA III/WoW bar only with textures and with streamed, cell-merged geometry.

## Open questions
1. **On what hardware did the authors measure** ~20 ms at 3050 calls and 33–42 ms in the newer state? Without this we cannot estimate how many draw calls SDL_GPU/Metal can handle on our target hardware. We have to do our own microbenchmark: draws/frame with 1, 2, 4 uniform pushes per draw.
2. **Ink in deferred:** are depth 2nd difference + normals + material-ID enough, or will we also want "crease" edges from geometry (feature edges baked into vertices)? How does ink behave with TAA (jitter vs thin lines)?
3. **Toon ramp vs. the WoW look:** do we want the ramp as a global style, or a per-material "band count" with the option of smooth Lambert? How does the tint combine with an AI texture (multiply the albedo, or only the direct light)?
4. **Text and fonts:** do we embed one open-licence CJK/latin font (an SDF atlas), or generate our own "lettering" by code because of the "everything by code" principle? How big an atlas of signs per cell?
5. **Slope limiter across cell boundaries:** is a 1-cell halo enough, or do we need a global pre-pass at region level (the limiter is non-local, it propagates up to a distance h/(slope·CELL))?
6. **Water surfaces on a large planet:** the "contour above a datum" is elegant for lakes in hills. How to combine it with the sea and rivers, and where will the leak lint run (per region)?
7. **Bake bend vs. native generation on a sphere:** with R in kilometres the curvature on a cell is on the order of cm. Is it enough to generate in the tangent plane of the cell and ignore it (with a "skirt" at the seams), or should we bend like Sakura?
8. The authors have **no reachability flood-fill** in the repo, only lists of points. What format of assert points do we want from district generators and what navigation model (circle R = 0.34, step 0.38 m like them)?
9. **Shadow shimmering:** the claim of a "snapped grid" in `main.js` is not fulfilled by the code. Confirm in our prototype that snapping cascades to texels is necessary even for a stylised look (probably yes).
10. **How much of the "quality" is composition?** The screenshots are from hand-chosen cameras in hand-composed scenes. For a procedural city we will need shot metrics (focal object, layering, sign density) and contact sheets from random cameras, not only from hero cameras.
