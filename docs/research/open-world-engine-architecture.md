# Build layers, handles and ports only at the seams

For an open-world engine in C17 on top of SDL3 and SDL_GPU, I recommend a **layered architecture after Gregory, enforced by CMake targets with one-way dependencies**. Do not use hexagonal architecture (ports & adapters) as the overall style. Take only its idea, applied at **five coarse seams**: platform, GPU, asset I/O, physics and audio. Add one driving port for game code. Inside the layers, data-oriented design applies. Do not build a generic ECS framework. Instead, take the split from GTA and RAGE into shared *archetypes* and cheap *instances* stored in SoA arrays per cell, Bitsquid's data managers owned by individual systems, and **generational 32-bit handles instead of pointers**. Solve parallelism with a **work-stealing job system with atomic counters and the rule "wait = help", without fibers for now**. On macOS ARM64, context switching and TLS are risky, and SDL_GPU command buffers are bound to a thread. Still, shape the API like Naughty Dog's so fibers can be added later. Build streaming as a **refcounted resource graph that feeds swappable "strategies"** (the Horizon Zero Dawn pattern), over cells of 128–256 m. Handle LOD with a tree as in GTA V: the parent LOD stays visible until its children arrive. The renderer has two layers, a **thin custom RHI with handles over SDL_GPU and a light render graph of a few hundred lines**. A GTA V-style deferred pipeline can be built on SDL_GPU. Fully GPU-driven rendering works only in a limited form, because bindless was rejected again in June 2026. Hot reload pays off for the game DLL (Handmade Hero style) and for shaders, not for the whole engine. What follows is a comparison of approaches, the concrete module structure and eight implementation milestones.

## The hexagon belongs only at the seams, Gregory's layers hold the whole

Cockburn's original intent for hexagonal architecture is that the application can be driven equally well by a user, a program or an automated test, and developed in isolation from its runtime devices ([Cockburn](https://alistair.cockburn.us/hexagonal-architecture/)). That is a valuable property for an engine. But Cockburn himself prefers **"a small number, two, three or four ports"** ([Cockburn](https://alistair.cockburn.us/hexagonal-architecture/)). The research found no single engine, AAA or indie, built explicitly as hexagonal. A search returns only a toy implementation of Game of Life ([serfer2/game-of-life-ports-and-adapters](https://github.com/serfer2/game-of-life-ports-and-adapters)). Practitioners warn that abstraction easily goes too far in games ([Wayline](https://www.wayline.io/blog/breaking-rules-clean-code-hurts-game-development)). An author who built a game with clean architecture recommends leaving out surplus mappers ([Medium](https://medium.com/@yankalbaska/how-clean-should-your-architecture-be-b2157eeea737)).

The idea of a port itself is standard in engines, just under other names. Gregory's "Platform Independence Layer" "shields the higher layers from knowledge of the platform" ([extract of Gregory's diagram](https://tams.informatik.uni-hamburg.de/lectures/2026ss/seminar/engine/doc/GameEngineCourseExtract.pdf)). Godot has "Servers" addressed by opaque RID handles ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html)) and below them RenderingDevice with drivers for Vulkan, D3D12 and Metal ([Godot rendering architecture](https://docs.godotengine.org/en/latest/engine_details/architecture/internal_rendering_architecture.html)). Granularity decides. Niklas Gray of Our Machinery writes that abstract interfaces add "a bit of verbosity and a performance cost (no inlined functions)". So the cost of abstraction is paid only for high-level objects, and **"anything we have a lot of is managed behind the API in raw buffers"** ([Gray pt.2](https://ruby0x1.github.io/machinery_blog_archive/post/little-machines-working-together-part-2/)). A port called a few times per frame with a batch of data (submit a draw list, read the input state, issue N asynchronous reads) costs nothing measurable. A virtual `get_position()` called for every entity is exactly where clean architecture hurts.

Cockburn's terminology maps onto the engine like this:

| Cockburn's term | In this engine | Adapter |
|---|---|---|
| Application core | `world` + gameplay (cells, instances, actors, rules) | — |
| Driving (primary) ports | game API for the DLL, input, replay/test harness, editor later | SDL events, file with recorded input |
| Driven (secondary) ports | GPU, asset I/O, physics, audio, time/threads | SDL_GPU / null GPU, loose files / pack, physics library / null |

From enterprise clean architecture, **do not take** DTO mapping layers, a port for every use case, DI containers or repository abstractions over in-memory data. The engine moves data in bulk, and copying between a "domain" and an "infrastructure" model every frame is exactly the cost that data-oriented authors warn about. The real benefit of the hexagon is elsewhere: **headless runs over a null GPU and replaying recorded input into the game DLL**. That is Cockburn's "driven by an automated test" in practice.

### Gregory's stack as the skeleton, Bitsquid as the rule for neighbors

Gregory's runtime architecture is a strict bottom-up stack. On top of hardware, drivers, the OS and third-party SDKs sits the Platform Independence Layer. Above it are Core Systems and the Resources/Assets Manager. Then comes a band of peer subsystems (low-level renderer, profiling, collision and physics, animation, HID, audio, online), above them the scene graph and culling, then gameplay foundations and finally game-specific systems ([extract from Game Engine Architecture](https://tams.informatik.uni-hamburg.de/lectures/2026ss/seminar/engine/doc/GameEngineCourseExtract.pdf)). Gregory himself does not address how peers on the same level should talk to each other. Bitsquid gives the answer: **"Instead of connecting low-level systems directly, use a high-level system that pours data between them"** ([Frykholm, Managing Coupling](https://bitsquid.blogspot.com/2011/01/managing-coupling.html)). Two more rules follow from the same text. A little duplication is better than coupling. Global frameworks (root classes, RTTI, global serialization) tie the whole engine together, so **every system has its own `save()`/`load()`** and no global reflection is built. Unreal enforces the same discipline through the build system: modules with `Public`/`Private` folders, explicit dependencies in `Build.cs` and a startup/shutdown function ([Unreal docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules)). In C17 with CMake that means one target per module, `include/` public and `src/` private. A private header is then not on another module's include path at all.

### Our Machinery and Handmade Hero: take the shape, not the whole machinery

The Machinery is the closest primary model of a modular engine in C. Its APIs are structs of function pointers registered by name in a central registry. Plugins are DLLs with `load_xxx(reg, reload)`/`unload_xxx(reg, reload)`. Unique names allow linking both statically and dynamically from the same code ([Gray pt.1](https://gamedeveloper.com/programming/little-machines-working-together-part-1-), [pt.2](https://ruby0x1.github.io/machinery_blog_archive/post/little-machines-working-together-part-2/)). The physical design has a machine-checkable rule: **"headers must not include other headers"** (except `<inttypes.h>` and `<stdbool.h>`). OS types are opaque blobs such as `struct tm_file_o {uint64_t opaque;}` and the APIs are bulk APIs following the motto "where there is one, there are many" ([Physical Design](https://ruby0x1.github.io/machinery_blog_archive/post/physical-design/)). The authors describe hot reload in practice as painful, though. Objects holding their own function pointers have to be tracked and patched ([DLL Hot Reloading in Theory and Practice](https://ruby0x1.github.io/machinery_blog_archive/post/dll-hot-reloading-in-theory-and-practice/)). A changed function signature also silently crashes the old DLL, which is why API versioning came later ([API Versioning](https://ruby0x1.github.io/machinery_blog_archive/post/api-versioning/)).

Handmade Hero turns the library model around. The platform executable owns the window, audio, input and memory, and calls a hot-reloadable game DLL. The rule is **"no static data in the game DLL"**: all state lives in memory allocated by the platform, so only a change of data layout does not survive a reload ([Handmade Hero forum](https://hero.handmade.network/forums/code-discussion/t/253/p/1529)). Calls from the game into the platform are fine as long as the API is narrow ([Možeiko](https://handmade.network/forums/t/8796/p/29649)). For a solo developer this means a combination of both. Game code will be a DLL as in Handmade Hero. Engine modules get the Machinery shape (API structs, `xxx_load(reg, reload)`, opaque types, bulk APIs), but they are linked by a static "registry", that is, a plain struct of pointers to all APIs, assembled in `runtime`. Postpone the full registry with string lookup until you want third parties or hot reload of engine modules. Also note that **The Machinery ended in 2022**, so its blog is a proven design, not a live project.

| Approach | What it brings | What it costs | Verdict for this engine |
|---|---|---|---|
| Hexagonal / clean | isolation of technologies, testability | indirection, mappers, DI; no documented engine | **only at 5 seams + the game port** |
| Gregory's layers | clear dependency direction, maps onto CMake | does not address neighbors by itself | **skeleton of the whole engine** |
| Data-oriented design | cache, batches, simplicity | less "domain modeling" | **rule inside modules** |
| Generic ECS (flecs etc.) | flexible composition, fast queries | framework, own scheduler, spatial structures are outside anyway | **not in the core**, at most later in `game` |
| Our Machinery plugins | C ABI, hot reload, mocking | registry, versioning, patching pointers | **API shape yes, dynamic registry later** |
| Handmade (game DLL) | fast gameplay iteration | state must live outside the DLL | **yes, from milestone M5** |

## No generic ECS: archetypes, instances and handles after GTA

Acton formulates DOD as a data transformation: "If you don't understand the data, you don't understand the problem." Concrete rules follow: solve the most common case, not the most general one, and **store each kind of state separately instead of a bool flag on the object**. A bool in a 64-byte struct means "90% waste" of the cache line. A rough budget is about 200 cycles per L2 miss times the number of misses times the number of objects ([Acton, CppCon 2014](https://neil3d.github.io/assets/img/ecs/DOD-Cpp.pdf)). With 30,000 objects and two misses per object, that serially gives roughly 12 million cycles, that is, units of milliseconds. Scattered reads per object are therefore the first lever. Fabian adds that **two data layouts can have a bigger impact than the choice of algorithm**. Lookup keys belong in their own array and mutations are batched before reads ([Fabian, Searching](https://www.dataorienteddesign.com/dodbook/node7.html)).

Generic ECS has two main variants. Archetype ECS (flecs, Unity, Bevy) stores entities in tables. It iterates fast, but when a component is added or removed it moves the whole entity, and it fragments with many combinations. Sparse-set ECS (EnTT) has cheap add and remove, but multi-component iteration needs checks or "groups" ([Mertens, ECS FAQ](https://github.com/SanderMertens/ecs-faq); [skypjack](https://skypjack.github.io/2019-03-07-ecs-baf-part-2/)). The strongest argument for ECS here is flecs: **C99, MIT, no dependencies, build under 5 seconds, over 13,000 tests in CI** ([flecs](https://github.com/SanderMertens/flecs)). Three things stand against it. It has its own scheduler that overlaps with your job system. It is debugged through a generic table layer instead of plain arrays. And spatial structures do not live in ECS anyway: the ECS FAQ itself says quadtrees and octrees are typically not stored in ECS ([ECS FAQ](https://github.com/SanderMertens/ecs-faq)). An open world stands precisely on spatial queries.

RAGE and its predecessors offer a better model. GTA III separates the **archetype** (`CBaseModelInfo`: collision model, 2D effects, texture dictionary, refcount, LOD distances) from the instance, which carries only a 16-bit `m_nModelIndex`, a transform and flags. Archetypes live in fixed typed stores, for example `CStore<CSimpleModelInfo,5000>` ([plugin-sdk CModelInfo.h](https://github.com/DK22Pac/plugin-sdk/blob/master/plugin_III/game_III/CModelInfo.h)), and entities in typed pools `CPool<CPed>`, `CPool<CVehicle>` ([CPools.h](https://github.com/DK22Pac/plugin-sdk/blob/master/plugin_III/game_III/CPools.h)). In San Andreas a placement instance in the binary IPL takes 40 bytes ([GTAMods: Item Placement](https://gtamods.com/wiki/Item_Placement)). The archetype is shared flyweight data and its refcount drives streaming. This is a different meaning of the word "archetype" than in ECS. GTA III also shows the costs of OOP pools from 2001. `CEntity` has around 40 one-bit flags including `bImBeingRendered` and `bStreamingDontDelete`, plus `CReference` back-reference lists and pointer lists in sectors ([CEntity.h](https://github.com/DK22Pac/plugin-sdk/blob/master/plugin_III/game_III/CEntity.h)). All of these are workarounds for unsafe pointer lifetimes, and generational handles with deferred deletion replace them systematically.

The recommended model has three classes of objects. **Static instances** (buildings, props, tens of thousands of pieces) are not entities. They are records in SoA arrays owned by a cell: archetype index, transform, bounds, flags and the index of the LOD parent. They are referenced by the pair `(cell_id, local_index)` with the cell generation, and are freed all at once with the whole cell. **Dynamic actors** (pedestrians, vehicles, pickups, mission entities, hundreds to low thousands) live in global generational pools that cells only index spatially. Their header may be deliberately "fat": handle, type, archetype index, transform index. States such as "in vehicle" or "ragdoll" belong in separate arrays, though, not in bits that every loop branches on. **System data** is owned by the systems, following Bitsquid: render instances, physics bodies, animation poses, each in a layout that suits the given system. The rule here is that **"there is no such thing as an abstract component"** ([Bitsquid: Data-Oriented Entity System](https://bitsquid.blogspot.com/2014/08/building-data-oriented-entity-system.html)).

Handles follow one scheme, which Bitsquid (22-bit index, 8-bit generation, index reuse only after 1024 freed), floooh (generation per slot, slot retired on overflow, different handle types as different `struct`s) and GTA III (`index<<8 | 7-bit id`) all arrived at ([Bitsquid](https://bitsquid.blogspot.com/2014/08/building-data-oriented-entity-system.html); [floooh](https://floooh.github.io/2018/06/17/handles-vs-pointers.html); [CPool.h](https://github.com/DK22Pac/plugin-sdk/blob/master/plugin_III/game_III/CPool.h)). For the runtime I recommend `typedef struct { uint32_t v; } eng_actor_h;` with a split of 20 bits for the index and 12 for the generation. That gives over a million live slots and 4096 recycles per slot. In save files, store a 64-bit variant. A pointer obtained from a handle is never stored. Spawns and despawns from streaming go into queues and are applied at a single synchronization point in the frame.

For spatial queries, take the GTA structure, but with dense arrays. San Andreas has an HD grid of 120×120 sectors of 50 units and a separate LOD grid of 30×30 of 200 units ([gta-reversed](https://github.com/gta-reversed/gta-reversed)). GTA III keeps a separate list of "big buildings" for the distant city ([CWorld.h](https://github.com/DK22Pac/plugin-sdk/blob/master/plugin_III/game_III/CWorld.h)). Static geometry gets an offline-built BVH for each cell. Dynamic actors go into a uniform hash grid, or into a loose quadtree if object sizes differ a lot. According to Ulrich, a loose quadtree handles dynamic objects without "hotspots", and for static geometry the author recommends ordinary trees ([Ulrich](http://tulrich.com/geekstuff/partitioning.html)).

## Work-stealing without fibers and overlapping frames

Naughty Dog built the engine of The Last of Us Remastered on fibers: 6 workers locked to cores, 160 fibers, atomic counters as the only synchronization and **800–1000 jobs per frame**. The key gain, however, did not come from fibers. It came from **pipelining phases across different frames** (game logic N+2, render N+1, GPU N), which cut the CPU frame from **25 ms to 15.5 ms**. Add to that "the frame as data" (FrameParams) and a tagged heap with 2 MiB blocks per worker, where 99.9% of allocations need no lock ([Gyrling, GDC 2015](https://media.gdcvault.com/gdc2015/presentations/Gyrling_Christian_Parallelizing_The_Naughty.pdf)). Gyrling himself describes the cost of fibers. System synchronization primitives stop working because a fiber migrates between threads. The compiler may also cache the TLS address, and a fiber resumed on another thread then reads someone else's data.

On your platforms the risks are even bigger. Apple effectively removed ucontext on ARM ([Apple Developer Forums](https://developer.apple.com/forums/thread/823121)), so what remains is custom assembler for each ABI or minicoro. That is a C library with asm for ARM64 and x86-64, whose switch costs about 9 cycles on Linux. But it warns against `thread_local` inside coroutines ([minicoro](https://github.com/edubart/minicoro)). SDL_GPU also requires a command buffer to be used and submitted on the thread that acquired it ([SDL_AcquireGPUCommandBuffer](https://wiki.libsdl.org/SDL3/SDL_AcquireGPUCommandBuffer)). That does not tolerate migrating fibers. Apple also explicitly advises to **remove spin-locks and yield loops** and to use work-stealing for custom pools, because with a static split the P- and E-cores finish at different times ([Apple: Tuning for Apple silicon](https://developer.apple.com/documentation/apple-silicon/tuning-your-code-s-performance-for-apple-silicon)). A fiber system that spins on counters goes directly against this.

Decision: **a per-worker Chase-Lev deque, atomic counters for job groups, continuations and "wait = help"** (a waiting thread takes or steals another job). Park idle workers on a semaphore. Molecular Matters shows that in this model allocation and the lock-free deque are what matter. A thread-local job allocator and a lock-free deque sped up 65,000 separate jobs from **18.5 ms to 2.93 ms** ([Molecular Matters pt.3](https://blog.molecular-matters.com/2015/09/25/job-system-2-0-lock-free-work-stealing-part-3-going-lock-free/)). The same text says that on ARM, Push needs a real memory fence, not just a compiler barrier. On the M4 Pro this is directly relevant. Keep global queues simple, with a mutex. The lock-free FIFO in Our Machinery "failed completely" ([Our Machinery](https://ruby0x1.github.io/machinery_blog_archive/post/fiber-based-job-system)) and Wicked Engine measured a mutex faster than a spinlock ([Wicked](https://turanszkij.wordpress.com/2018/11/24/simple-job-system-using-standard-c/)). **But shape the API like Gyrling and Machinery**: `jobs_run(decls, n, &counter)` and `jobs_wait(counter)`. The caller then does not know whether the wait helps or switches a fiber, and fibers can be added later without changing callers. A ready-made solution exists in the form of enkiTS (C API, zlib, dependencies, pinned tasks for IO threads), but its core is C++11 and Mac/ARM is "less frequently tested" ([enkiTS](https://github.com/dougbinks/enkiTS)). A custom system is small: Our Machinery's fit under 300 lines. You also want QoS and parking on Apple Silicon under your control, so I recommend writing your own.

Platform details have concrete consequences in code. On macOS a thread cannot be pinned to a core. Intent is expressed with a QoS class via `pthread_set_qos_class_self_np` ([Apple](https://developer.apple.com/documentation/apple-silicon/tuning-your-code-s-performance-for-apple-silicon)). SDL3 offers only the coarse `SDL_SetCurrentThreadPriority` ([SDL3 wiki](https://wiki.libsdl.org/SDL3/SDL_SetCurrentThreadPriority)), so set QoS natively inside `platform`. Put game workers on user-interactive, and IO and decompression on utility. When splitting work, generate at least three times as many tasks as there are cores. Verify the M4 Pro configuration (8P+4E in the brief) on your machine, since Apple does not guarantee the split into P- and E-cores. Take threads, mutexes and semaphores from SDL3, not from C11 `<threads.h>`. MSVC ships them as a separate `vcruntime140_threads.dll` ([MSVC blog](https://devblogs.microsoft.com/cppblog/c11-threads-in-visual-studio-2022-version-17-8-preview-2/)) and unnamed POSIX semaphores are deprecated on macOS arm64 ([Apple forums](https://developer.apple.com/forums/thread/823121)). Hide `<stdatomic.h>` behind your own `atomics.h`. MSVC supports it only experimentally via `/experimental:c11atomics`, lock-free only up to 8 bytes, and `__STDC_NO_ATOMICS__` stays defined even with the flag on ([MSVC blog](https://devblogs.microsoft.com/cppblog/c11-atomics-in-visual-studio-2022-version-17-5-preview-2/)). So do not use a 16-byte DCAS, and solve ABA with an index plus generation packed into 64 bits.

The frame structure is based on Fiedler's fixed timestep. An accumulator, simulation with a fixed `dt` and render interpolation via `alpha = accumulator / dt`, with `frameTime` clamped to 0.25 s against the "spiral of death" ([Gaffer On Games](https://gafferongames.com/post/fix_your_timestep/)). The simulation (jobified, 60 Hz) produces an immutable FrameParams snapshot. Render-prep (culling, LOD selection, pose finalization, building draw packets, again as jobs) builds POD command packets from it. A single thread then translates them into SDL_GPU calls and submits. This is a safer variant of the Unreal render → RHI pattern ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/parallel-rendering-overview-for-unreal-engine)). The swapchain must also be acquired on the window thread ([SDL_gpu.h](https://raw.githubusercontent.com/libsdl-org/SDL/main/include/SDL3/SDL_gpu.h)), so the main thread does the submit. Enable the pipelining "sim N+1 ‖ render-prep N" only in a later milestone. But introduce the data separation via FrameParams and memory tagged with the frame number, released after the GPU fence, right away. Without it you cannot add pipelining afterwards.

## Streaming as a refcounted graph, cells of 128–256 m and fallback LOD

The streamer from the 3D GTA era is a surprisingly good model for a small engine. San Andreas has one global ID space for all resources (models, TXD, collision, IPL, animations, scripts), 26,316 entries in total in one static array. The memory budget is 50 MB, it uses two I/O channels and merges **up to 16 files that lie consecutively on disk** into one read. It frees by LRU over resources with a zero refcount, and geometry behind the camera goes first ([gta-reversed](https://github.com/gta-reversed/gta-reversed)). The request radius is `min(LODmultiplier × archetype drawDistance, 80 outdoors / 40 indoors)`. Large buildings are thus loaded from far away and small props from up close without any further logic. When the camera climbs above 50 units over the ground, the streamer switches to LOD only. Teleports and cutscenes use a blocking `LoadScene` (same source). GTA V then generalized the two-level HD/LOD pairing to an **n-level tree per instance** with the fields `parentIndex`, `lodDist`, `childLodDist`, `lodLevel` and `numChildren` in ymap files, which are themselves streamed ([FiveM docs](https://docs.fivem.net/docs/assets-manual/beginner-series/part-6/); [CodeWalker export](https://gist.github.com/Stuyk/d31aa4f901c9c7532316b937c329d2c0)). Rockstar published nothing primary about the inside of RAGE. Everything about its scheduler and budgets is therefore unverified, and this report does not build on it.

The most portable idea comes from Horizon Zero Dawn. Guerrilla separates **"what is loaded"** (an acyclic file graph with refcounts, where "no object is ever loaded twice") from **"why it is loaded"**, which is determined by strategies evaluated every frame. They are AlwaysLoaded, TileBased with four rings of tiles (9 High, 9 Medium, 9 Low, 12 Very Low always loaded), AreaBased and ProgramBased. An object is loaded in phases deserialize → link-resolve → init → activate. A precomputed "prefetch" description of the whole graph takes about **20 MiB** and lets you know the dependencies of any root without reading files. During development nothing is packed, and files go over a socket from the PC. The game ships as PackFiles with **256 KiB compressed blocks** in depth-first graph traversal order ([Guerrilla, HZD slides](https://d3d3g8mu99pzk9.cloudfront.net/AstridHuntjens/Streaming%20the%20world%20of%20Horizon%20Zero%20Dawn.pdf)). Under pressure, RenderData memory shrinks in steps of 64 MiB by **dropping optional LODs and low-priority mips** (same source). UE5 World Partition arrives at the same shape. It has a 2D runtime grid (documentation examples: cell 256 m, loading range 768 m) and multiple streaming sources with a target state of *Loaded* or *Activated* ([UE World Partition](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition-in-unreal-engine)). Unloaded cells are replaced by HLOD ([UE HLOD](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition---hierarchical-level-of-detail-in-unreal-engine)). According to secondary sources, Spider-Man divided New York into roughly **800 tiles of 128 m** ([Engadget](https://engadget.com/2018/09/07/spider-man-ps4-game-new-york-city)).

All three approaches converge on the same pattern: full detail in the cells near the player, prebaked merged proxies for distant cells and an always-resident lowest level for the horizon. Concretely for your engine this means a **streaming cell of 128–256 m and an HLOD cell of 1–2 km**. The `world` module owns the strategies, that is, `strategy_update()` functions that add and release references to root IDs. The `asset` module handles dependencies, I/O and refcounts. Have two target states at different radii, Loaded and Activated (physics, AI and scripts run). The parent LOD is drawn until all children are resident, so late streaming creates no holes, only less detail. Order priorities by class: collision around the player > cell instance lists > LOD/HLOD proxies > HD meshes > top mips > ambient pedestrians and cars. As your own, unverified recommendation, add a **second streaming source at the predicted point** `position + velocity × 1–2 s`. For cars and planes this is simpler than a directional formula. Take the "LOD only" mode above a given height or speed from GTA.

Coordinate precision is solved together with cells. UE5 moved to double positions on the CPU, but Niagara stores a float inside the cell and a cell identifier separately ([UE LWC](https://dev.epicgames.com/documentation/en-us/unreal-engine/large-world-coordinates-in-unreal-engine-5)). Star Citizen spent roughly 8 months moving to 64-bit positions and ended up with camera-relative rendering, because the GPU stays 32-bit ([GamersNexus](https://gamersnexus.net/gg/2622-star-citizen-sean-tracy-64bit-engine-tech-edge-blending)). The float32 step is about 0.49 mm at 4,096 m and 0.98 mm at 8,192 m. **A map the size of GTA V (around 8×8 km) fits into float32 if rendered relative to the camera.** I recommend storing the position as `int32 cell_x, cell_y` plus a `float` local offset, where the cell is directly the streaming cell. Send only camera-relative matrices to the GPU and never absolute positions. Do depth as reversed-Z; GTA V uses logarithmic reversed-Z ([Courrèges](https://www.adriancourreges.com/blog/2015/11/02/gta-v-graphics-study/)).

Build I/O on `SDL_AsyncIO`. On Linux it uses io_uring, on Windows 11 IoRing and elsewhere a thread pool. Results arrive in completion order and one queue per thread is recommended ([SDL3 wiki: AsyncIO](https://wiki.libsdl.org/SDL3/CategoryAsyncIO)). One IO thread blocks in `SDL_WaitAsyncIOResult` and, acting as an "interrupt handler" (Gyrling), only spawns jobs for decompression and parsing. Upload to the GPU goes in batches through a copy pass. A runtime asset is a relocatable blob: a header and sections with 32-bit offsets from a base, so after a single read no fix-up is needed. The pack has the format `[header][directory hash64 → block, offset, size][compressed blocks 64–256 KiB]` and the files in it are sorted by cell and then by dependencies. A patch is an overlay pack as in HZD. The research did not verify the codec (LZ4 or zstd) on shipped titles, so measure it. During development, load loose cooked files with the same IDs and leave packing as a pre-release step.

## A thin RHI over SDL_GPU and a render graph in a few hundred lines

SDL_GPU is a deliberately conservative API in the style of Metal. It has vertex, fragment and compute stages, storage buffers, indirect draw and dispatch, automatic "cycling" and at most 3 frames in flight. Per stage it allows **16 samplers, 8 storage textures, 8 storage buffers and 4 uniform slots** ([SDL_sysgpu.h](https://raw.githubusercontent.com/libsdl-org/SDL/main/src/gpu/SDL_sysgpu.h)). It has no **bindless, no timestamp or occlusion queries, no GPU-side draw count and no mesh shaders**. The maintainers closed the bindless issue again in June 2026 as "not planned", and slouken answered "use Vulkan directly" ([SDL #11148](https://github.com/libsdl-org/SDL/issues/11148)). The critical detail for you is in the Metal backend: multi-draw indirect there is a **CPU loop with one call per draw** ([SDL_gpu_metal.m](https://raw.githubusercontent.com/libsdl-org/SDL/main/src/gpu/metal/SDL_gpu_metal.m)). Vulkan uses native multi-draw only with an optional feature, and D3D12 uses `ExecuteIndirect` ([SDL_gpu_vulkan.c](https://raw.githubusercontent.com/libsdl-org/SDL/main/src/gpu/vulkan/SDL_gpu_vulkan.c); [SDL_gpu_d3d12.c](https://raw.githubusercontent.com/libsdl-org/SDL/main/src/gpu/d3d12/SDL_gpu_d3d12.c)). "One indirect call for the whole scene" therefore costs O(N) encoder calls on your M4 Pro.

Still, write your own RHI (the `gpu` module) over SDL_GPU, for reasons other than portability. SDL already handles that. There are four reasons: SDL types do not leak into engine headers, you get a null backend for headless tests, you get deferred destroy tied to a fence, and the path to a native backend stays open if bindless or timestamps become critical. The model is sokol_gfx: **typed 32-bit handles with generation over pools**, descriptive structs with designated initializers and a stateless pass/pipeline/bindings/draw model ([floooh, handles](https://floooh.github.io/2018/06/17/handles-vs-pointers.html)). Its Vulkan backend has "a bit over 3 kloc" and inserts barriers lazily based on tracked resource access ([floooh: Sokol Vulkan backend](https://floooh.github.io/2025/12/01/sokol-vulkan-backend-1.html)). Design the binding abstraction as "small per-draw data + a few storage buffers + a set of material textures". Today it maps 1:1 onto SDL_GPU slots, and tomorrow onto bindless or a root-pointer model, as Aaltonen describes ([No Graphics API](https://www.sebastianaaltonen.com/blog/no-graphics-api)). The reverse does not work: you cannot implement a root-pointer-only model on SDL_GPU. Material code therefore must not know SDL slot numbers.

A render graph makes sense, but in a smaller version. Frostbite's FrameGraph and Granite pay off mainly through automatic barriers, layout transitions and transient memory aliasing. The author himself calls Granite a "3 ksloc behemoth" ([themaister](https://themaister.net/blog/2017/08/15/render-graphs-and-vulkan-a-deep-dive/)). SDL_GPU hides barriers and layouts and does not allow aliasing. So the graph here does only five things: it orders passes, removes unused ones, chooses load/store operations, pools transient textures by description and decides on `cycle` flags. That is roughly a few hundred lines of C. But introduce the interface **"a pass declares what it reads and what it writes" from day one**. It is a precondition for generating barriers in a future native backend and for dumping the graph while debugging. For an open world with hundreds of render targets (GTA V has **88 render targets and 4155 draw calls per frame**) ([Courrèges](https://www.adriancourreges.com/blog/2015/11/02/gta-v-graphics-study/)), a declarative graph greatly simplifies switching effects off and scaling resolution.

The renderer content follows GTA V, because its whole frame is feasible on SDL_GPU. It contains a deferred G-buffer with 4 LDR MRTs and depth (fits the documented limit of 4 color targets), 4 CSM cascades in one 1024×4096 atlas, a 128×128 cubemap refreshed every frame, SSAO at half resolution and LOD transitions by **dithering ("alpha stippling")** instead of alpha blending ([Courrèges](https://www.adriancourreges.com/blog/2015/11/02/gta-v-graphics-study/)). GPU-driven culling will work only in a reduced form. Instance data will be in a persistent storage buffer and meshes in large vertex and index buffers. A compute pass does frustum and Hi-Z culling and LOD selection, and writes `SDL_GPUIndexedIndirectDrawCommand` into fixed slots with a zero instance count for culled objects. Drawing then takes one indirect call per combination of pipeline and texture set. Do not combine `first_instance` with `SV_InstanceID`; the wiki explicitly says that only 0 is portable ([SDL wiki](https://wiki.libsdl.org/SDL3/SDL_GPUIndexedIndirectDrawCommand)). Put material textures into 2D_ARRAYs grouped by format and size. Virtual texturing in the RedLynx style ([Advances in RTR 2015](https://advances.realtimerendering.com/s2015/index.html)) is the closest to bindless, but postpone it. A visibility buffer is feasible, but deferred takes priority.

Write shaders in HLSL and translate them offline with SDL_shadercross or DXC to SPIR-V and DXIL, and with SPIRV-Cross to MSL ([SDL_shadercross](https://github.com/libsdl-org/SDL_shadercross)). In addition, generate a sidecar with the resource counts that `SDL_CreateGPUShader` requires. According to the wiki, the most common mistake is a wrongly laid out register layout ([SDL wiki](https://wiki.libsdl.org/SDL3/CategoryGPU)), so enforce it with macros for `space0`–`space3`. Shader hot reload in the dev build: shadercross linked as a library, file watching, a new pipeline, handle swap at the frame boundary and release of the old pipeline after the fence. Shadercross has no formal release, so expect a rolling version. GPU timing cannot be measured with timestamps yet ([Sunrisepeak/mui #3](https://github.com/Sunrisepeak/mui/issues/3)). Put `gpu_timer` into the RHI as a no-op and rely on fence-to-fence timing and Xcode GPU capture.

## Thirteen CMake targets with one-way dependencies

The structure converts Gregory's layers into targets. Bitsquid's rule that a higher layer pours data between neighbors is entrusted to a single mediator, `runtime`. Machinery contributes the physical rules.

```
engine/
├─ CMakeLists.txt              # options: ENG_HOT_RELOAD, ENG_HEADLESS, ENG_UNITY
├─ cmake/                      # warnings.cmake, check_public_headers.cmake
├─ external/                   # SDL3; SDL_shadercross (tools + dev only)
├─ src/
│  ├─ base/     include/eng/base/{types.h, assert.h, math.inl, atomics.h, handle.h}
│  ├─ platform/ include/eng/platform.h   src/{sdl_window.c, sdl_input.c, sdl_fs.c,
│  │                                          sdl_thread.c, qos_macos.c, dylib.c}
│  ├─ core/     include/eng/{mem.h, jobs.h, log.h, profile.h, containers.h}
│  ├─ asset/    include/eng/asset.h      src/{vfs_loose.c, vfs_pack.c, resource_db.c, io.c}
│  ├─ gpu/      include/eng/gpu.h        src/{gpu_sdl.c, gpu_null.c}
│  ├─ render/   include/eng/render.h     src/{graph.c, render_world.c, passes/, shaders/}
│  ├─ phys/     include/eng/phys.h       src/{phys_<lib>.c, phys_null.c}
│  ├─ audio/    include/eng/audio.h      src/{audio_sdl.c, audio_null.c}
│  ├─ anim/     include/eng/anim.h
│  ├─ world/    include/eng/world.h      src/{cells.c, archetypes.c, instances.c, actors.c,
│  │                                          spatial.c, strategies.c, lod.c}
│  ├─ runtime/  include/eng/engine_api.h src/{init.c, frame.c, frame_params.c, api.c}
│  └─ app/      main.c, game_loader.c
├─ game/                       # SHARED in dev build, STATIC in release
├─ tools/                      # cook/, shaderc/, pack/
└─ tests/                      # unit/, replay/ (headless: gpu_null + phys_null)
```

| Target | Type | May depend on | SDL headers | Role |
|---|---|---|---|---|
| `eng_base` | INTERFACE | — | no | types, assert, inline math, atomics wrapper, handle macros |
| `eng_platform` | STATIC | base, SDL3 (PRIVATE) | **yes** | OS adapter: window, input, time, files/AsyncIO, threads, QoS, DLL loading |
| `eng_core` | STATIC | base, platform | no | tagged heap, arenas, job system, containers, log, profiler |
| `eng_asset` | STATIC | core | no | VFS (loose/pack), resource DB, refcount graph, IO queue, **`asset_type_handler` port** |
| `eng_gpu` | STATIC | core, SDL3 (PRIVATE) | **yes** | RHI with handles; SDL_GPU and null backend |
| `eng_render` | STATIC | gpu, asset | no | render graph, render world, passes, materials |
| `eng_phys` | STATIC | asset | no | physics port + library adapter + null |
| `eng_audio` | STATIC | asset, platform | no | audio port + adapter |
| `eng_anim` | STATIC | asset | no | skeletons, clips, blending (jobs) |
| `eng_world` | STATIC | asset | no | cells, archetypes, instances, actor pools, spatial, strategies, LOD |
| `eng_runtime` | STATIC | all of the above | no | mediator: init/shutdown order, FrameParams, data pouring, `engine_api` |
| `app` / `game` | EXE / SHARED | runtime / only `engine_api.h` + base | app yes | composition root, hot reload loader / gameplay |

The rules that hold the structure together apply without exceptions. **Modules on the same level (`render`, `phys`, `audio`, `anim`, `world`) do not link against each other.** `world` does not know that render exists. When a cell is activated, `runtime` takes a batch of instances from `world` and hands it to `render_world_add_instances()`. It pours dynamic transforms once per frame through FrameParams. The only real dependency inversion is in `asset`. It defines the `asset_type_handler` port (load, unload, size, dependencies) and `render`, `phys` and `anim` implement it for meshes, textures, collisions and clips. The resource DB thus does not need to know the GPU. **Public headers may include only `eng/base/types.h`** (plus `<stdint.h>`, `<stdbool.h>`, `<stddef.h>`), and declare foreign types by forward declaration. A CI script guards the rule, as Machinery did ([Physical Design](https://ruby0x1.github.io/machinery_blog_archive/post/physical-design/)), with a single exception for `math.inl`, because of `static inline` vector math. SDL3 is linked `PRIVATE` only into `platform`, `gpu` and `app`. The initialization order is hand-written in `runtime/init.c` (`xxx_init(const xxx_desc*, eng_allocator*)`) and shutdown runs in the reverse order. The platform reserves large arenas and nobody else calls `malloc`. A unity build (one TU per module) is an optional speed-up tactic; the header rule handles coupling.

The game port is the only header the DLL sees. It matches Handmade Hero and is also Cockburn's driving port for replay tests:

```c
typedef struct eng_api {
    uint32_t version;                     /* versioning after Our Machinery */
    const struct eng_world_api *world;    /* spawn/despawn, bulk queries */
    const struct eng_input_api *input;
    const struct eng_audio_api *audio;
    const struct eng_jobs_api  *jobs;
    const struct eng_debug_api *debug;
} eng_api;

/* exports of game.dylib/.so/.dll – no static data in the DLL */
void game_load(const eng_api *api, struct game_memory *mem, bool reload);
void game_fixed_update(struct game_memory *mem, const struct eng_frame_input *in, float dt);
void game_unload(struct game_memory *mem, bool reload);
```

This research did not evaluate a physics library. If you choose a C++ library, all of it belongs in an adapter behind `phys.h` and C++ leaks nowhere else. The claim that RAGE used Bullet comes only from a forum and is not verified ([NeoGAF](https://www.neogaf.com/threads/why-rockstar-rage-engine-outclasses-commercial-tech.1699203/latest)).

## Eight milestones: the first city comes only after the core and assets

The order follows the dependencies in the layers. Each milestone ends in a verifiable state on all three OSes. Set up CI for macOS, Linux and Windows from M0, because MSVC atomics and thread differences would otherwise surface late.

| Milestone | Content | Done when |
|---|---|---|
| **M0 Skeleton** | CMake targets, `base`, `platform` (window, input, time), CI header check, `gpu` with only a screen clear | empty window with a clear color on macOS/Linux/Windows; breaking the header rule fails CI |
| **M1 Core** | tagged heap and arenas, job system (Chase-Lev, counters, wait=help, parking, QoS), log, profiler hooks | `parallel_for` over 1M elements scales on both P and E cores; deque stress test without errors under TSan |
| **M2 RHI and shaders** | handles, deferred destroy, null backend, HLSL → SPIR-V/DXIL/MSL + reflection, shader hot reload, minimal render graph (read/write declarations) | textured cube, camera-relative matrices, reversed-Z; an HLSL edit shows up at runtime |
| **M3 Assets** | cooker into relocatable blobs, loose VFS, resource DB with refcount graph, `asset_type_handler`, SDL_AsyncIO + IO thread | headless test loads and releases 10k assets without a leak; a mesh streams asynchronously |
| **M4 World** | archetypes/instances, cells of 128–256 m, cell+float coordinates, strategies (rings + always-loaded), LOD tree with fallback, spatial grid, cell debug visualization | flythrough of a synthetic 4×4 km city without holes and without blocking loads |
| **M5 Game** | fixed step + interpolation, FrameParams, actor pools with handles, game DLL with hot reload, physics adapter, input replay | a car drives around the city; gameplay code changes without a restart; replay is deterministic in a headless build |
| **M6 Open-world renderer** | deferred G-buffer, CSM atlas, GPU culling into fixed slots, texture arrays, HLOD, dither transitions | 30k+ instances in the scene; the number of draw calls grows with the number of material buckets, not objects |
| **M7 Scaling** | pipelining sim N+1 ‖ render-prep N, pack files with block compression, budgets and LRU eviction, predictive streaming source, profiling on Linux/Windows | stable frame at 200 km/h across the whole map; memory holds the budget |

Audio, animation and tools (editor, inspectors) run in parallel from M5 as the game needs them. Nothing in the earlier milestones depends on them.

## Conclusion

Neither the hexagon nor ECS arrives in its pure form, yet both ideas remain in the design, just in different places than one would expect. Ports & adapters survive as five adapters and one game port. The main reward is not swapping technologies, since SDL already does that, but **deterministic headless replay**, which replaces QA for a small team. The composition that ECS promises breaks down in an open world anyway on spatial queries and streaming. The archetype/instance split and per-cell ownership therefore do more work than any generic storage model. Generational handles meanwhile solve lifetime, serialization and hot reload at once.

The biggest risk is not in the engine architecture, but in SDL_GPU. On Metal, multi-draw is a CPU loop and bindless will not come. A fully GPU-driven open world in the Ubisoft style therefore cannot be built on the M4 Pro through SDL_GPU. Before M6, measure the cost of empty indirect draws on Metal. If it turns out to be a limit, the thin RHI with the binding "per-draw data + storage buffers + a set of textures" will be the place where a native Metal or Vulkan backend can be added without changing the renderer above it. It is good to keep this possibility in mind from M2, even if you never use it. Uncertainties that remain: RAGE internals are not documented, nobody among the cited sources verified the benefit of parallel command buffer recording in SDL_GPU, and the status of C11 atomics in newer MSVC needs to be checked in the current documentation.
